## 1. Alembic 权威迁移

结构变更以 **Alembic** 为权威工具（规范 §13.1），随框架自带：

- 框架仓库根 `alembic/`（`env.py`、`script.py.mako`、`versions/`）+ `alembic.ini`；
- 安装：`pip install "flower-web-infrastructure[migrate]"`（`[migrate] = ["alembic>=1.13"]`，属运维/部署工具，非运行时依赖）；
- `alembic/env.py` 复用框架 `load_env_file` 自动加载项目根 `.env`，支持异步引擎（`mysql+aiomysql` / `sqlite+aiosqlite`）与同步 URL（`mysql+pymysql` / `sqlite`），按 URL 驱动类型自动选择；
- **autogenerate 依据**：业务模型需在 `alembic/env.py` 导入注册到 `Base.metadata`（框架库不集中定义业务实体，`target_metadata = Base.metadata`，业务项目取消注释示例导入业务模型模块）。

```python
# alembic/env.py（业务项目接入点）
# 在 target_metadata = Base.metadata 之前导入业务模型模块：
#   import business_models  # 业务模型模块，继承 web_infra.capabilities.db.mysql_base.Base
```

框架自带迁移脚本示例（`alembic/versions/0001_message_outbox.py`，Outbox 表基线迁移）关键结构——revision/down_revision 链、跨方言列类型（SQLite INTEGER / MySQL BIGINT 自适应）、唯一约束与表注释：

```python
"""基线迁移：创建 message_outbox 表

Revision ID: 0001
Revises:
"""
from typing import Sequence, Union
import sqlalchemy as sa
from alembic import op
from sqlalchemy.dialects import mysql

revision: str = "0001"
down_revision: Union[str, None] = None

def upgrade() -> None:
    op.create_table(
        "message_outbox",
        sa.Column("id", sa.BigInteger().with_variant(sa.Integer(), "sqlite"),
                  autoincrement=True, nullable=False, primary_key=True),
        sa.Column("msg_id", sa.String(64), nullable=False),
        sa.Column("biz_id", sa.String(64), nullable=False),
        sa.Column("topic", sa.String(128), nullable=False),
        sa.Column("payload", sa.Text(), nullable=False),
        sa.Column("status", sa.SmallInteger().with_variant(mysql.TINYINT(), "mysql"),
                  nullable=False, server_default=sa.text("0")),
        sa.Column("created_at", sa.DateTime(), nullable=False),
        sa.UniqueConstraint("msg_id", "biz_id", name="uk_msg_biz"),
        mysql_engine="InnoDB", mysql_charset="utf8mb4",
        mysql_comment="Outbox 本地事务表",
    )

def downgrade() -> None:
    op.drop_table("message_outbox")
```

> 框架迁移链按历史演进重建（`0001` 建基线列、`0002` 补 `next_retry_at` 与联合索引），`upgrade head` 后的表结构与基线 SQL 文件当前形态等价——**Alembic 为权威迁移，基线 SQL 仅作参考**（规范 §13.1）。

## 2. 迁移命令

单体（项目根目录执行，`alembic.ini` 在根）：

```bash
alembic upgrade head                 # 升级到最新版本
alembic revision --autogenerate -m "add_xxx_table"   # 对比模型与库表生成迁移脚本
alembic history                      # 迁移历史
alembic downgrade -1                 # 回滚一个版本
alembic upgrade head --sql           # 离线模式生成 SQL（不连库）
```

> `alembic.ini` 的 `sqlalchemy.url` 留空（防硬编码），由 `env.py` 注入（见 §3）；`env.py` 已把项目 `src` 加入 `sys.path`，未以 editable 安装也能导入 `web_infra`。

执行输出示例（`alembic upgrade head`，异步引擎自动选用 `aiomysql`）：

```text
INFO  [alembic.runtime.migration] Context impl MySQLImpl.
INFO  [alembic.runtime.migration] Will assume non-transactional DDL.
INFO  [alembic.runtime.migration] Running upgrade  -> 0001, 基线迁移：创建 message_outbox 表
INFO  [alembic.runtime.migration] Running upgrade 0001 -> 0002, Outbox 增量：新增 next_retry_at 列
```

离线生成 SQL（不连库，`--sql` 走 `run_migrations_offline`，输出可直接交 DBA 评审）：

```bash
alembic upgrade head --sql > upgrade_head.sql
```

**autogenerate 注意事项**：

- `alembic revision --autogenerate` 以 `Base.metadata` 与库表结构对比生成——业务模型必须已导入注册（§1）；未注册的模型不会被自动检测（漏迁移）；
- 生成的脚本需人工评审：核对新增/修改列、索引、唯一约束；自动生成默认不含表级 COMMENT 等 MySQL 方言细节，可手工补 `mysql_engine`/`mysql_charset`/`mysql_comment`；
- 新环境建议"基线 SQL + 迁移链合流"验证一次（§6.1），确保 `upgrade head` 后结构一致。

## 3. 数据库 URL 解析优先级

`alembic/env.py` 的 `_resolve_url()` 解析顺序（迁移命令单独执行同样生效，无需预先导出）：

```
进程/容器环境变量 DATABASE_URL > 项目根 .env 的 DATABASE_URL > alembic.ini 的 sqlalchemy.url（留空）
```

```dotenv
# .env（推荐）
DATABASE_URL=mysql+aiomysql://root:root@127.0.0.1:3306/flower_monomer
```

- `.env` 加载为幂等且不覆盖已存在的环境变量（与应用启动行为一致）；
- 缺失 URL 时抛 `RuntimeError`（提示设置环境变量或配置 ini），避免误连错误库。

URL 常用写法（异步驱动自动选中）：

| 数据库 | URL | 说明 |
| ---- | ---- | ---- |
| MySQL（默认） | `mysql+aiomysql://user:pass@host:3306/dbname` | 异步（`env.py` 按驱动自动选择异步引擎） |
| MySQL（同步） | `mysql+pymysql://user:pass@host:3306/dbname` | 同步兼容 |
| SQLite（异步） | `sqlite+aiosqlite:///./data/app.db` | 本地/测试 |
| SQLite（同步） | `sqlite:///./data/app.db` | 同步兼容 |

**迁移执行环境检查**（执行前确认，避免误连/半途失败）：

- `alembic current` / `alembic history` 确认目标库当前 revision 与预期一致（防止连错库/漏版本）；
- 目标库连接账号具备 DDL 权限（MySQL 迁移需 `CREATE/ALTER/DROP/INDEX`，DML 需对应表写权限）；
- 大表/生产变更按 [§7 生产变更流程建议](#7-生产变更流程建议) 走评审与低峰执行；迁移命令在项目根目录执行（`.env` 与 `alembic.ini` 解析依赖 cwd）。

## 4. db/init 基线 vs db/versions 增量

框架与脚手架统一双轨制（规范 §13.2）：

| | `db/init/`（基线） | `db/versions/`（增量） |
| ---- | ---- | ---- |
| 用途 | 大版本初始结构（新环境初始化） | 已发布环境的演进变更 |
| 变更规则 | **禁止回改**（只随大版本重建） | 只新增版本脚本，不改已发布脚本 |
| 命名 | `001-模块-init-ddl.sql` / `001-模块-init-dml.sql` | `V{版本}-{模块}-{描述}-ddl/dml.sql` |
| 执行方式 | docker-compose 首次初始化自动执行（`init-mysql.sh` 按文件名序执行 ddl 再 dml） | 手动执行（生产变更流程见 §7） |
| DDL/DML | 基线可无 DML（新表无数据） | **DDL 与 DML 同版本成对提供**；涉及存量数据语义变更（回填/清洗/转换）必须提供**幂等 DML** |

**基线执行方式**（docker-compose 首次初始化，参考微服务脚手架 `db/init/init-mysql.sh`）：MySQL 容器官方 entrypoint 在首次启动时按文件名序执行 `/docker-entrypoint-initdb.d` 下脚本，`init-mysql.sh` 依次执行 `ddl/*.sql` 再 `dml/*.sql`（脚本内自带 `USE <database>` 切换服务分库）：

```bash
#!/bin/sh
set -e
for f in /docker-entrypoint-initdb.d/ddl/*.sql; do
  echo "==> 执行基线 DDL: $f"
  mysql -uroot -p"$MYSQL_ROOT_PASSWORD" < "$f"
done
for f in /docker-entrypoint-initdb.d/dml/*.sql; do
  echo "==> 执行基线 DML: $f"
  mysql -uroot -p"$MYSQL_ROOT_PASSWORD" < "$f"
done
echo "==> 数据库基线初始化完成"
```

**基线 DDL 示例**（`db/init/ddl/001-user-init-ddl.sql` 风格，脚本头统一 `@Author / @Date / @Description`）：

```sql
CREATE TABLE IF NOT EXISTS t_user (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,
    username    VARCHAR(64)  NOT NULL COMMENT '登录名',
    password    VARCHAR(255) NOT NULL COMMENT '密码哈希（bcrypt）',
    created_at  DATETIME NOT NULL COMMENT '创建时间',
    updated_at  DATETIME COMMENT '更新时间',
    UNIQUE KEY uk_username (username)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '用户表';
```

幂等 DML 示例（框架 `db/versions/V0.2.0-mq-outbox-next-retry-dml.sql`，带 WHERE 过滤已处理行，可重复执行）：

```sql
UPDATE message_outbox
SET next_retry_at = NOW()
WHERE status = 0            -- 仅待发送消息
  AND next_retry_at IS NULL -- 幂等：已初始化的行不重复处理
;
```

纯加列（nullable/带默认值）且不改变存量语义时，DML 可为空，但必须在变更说明中声明"无数据迁移"。

**增量 DDL 完整示例**（框架 `db/versions/V0.2.0-mq-outbox-next-retry-ddl.sql`，演示"基线不可回改、版本脚本演进"）：

```sql
-- =====================================================================
-- Outbox 增量脚本（示例）：新增 next_retry_at 列（规范 §13.2 / S9-4 指数退避）
-- @Author: 花海
-- @Date: 2026/08/15 10:00
-- @Description: 示例增量 DDL（db/versions/）：message_outbox 增加"下次可重试时间"列，
--               与 OutboxPublisher 指数退避语义（S9-4，mark_failed 写入）对齐。
--               基线脚本 db/init/ddl/001-mq-init-ddl.sql 不含此列（基线不可回改），
--               通过本版本脚本增量演进；配套 DML 见同版本 -dml.sql。
-- =====================================================================

ALTER TABLE message_outbox
    ADD COLUMN next_retry_at DATETIME NULL
        COMMENT '下次可重试时间（指数退避 base*2^retry_count，S9-4；NULL 表示无需退避）'
        AFTER retry_count;
```

要点：① 头部统一 `@Author / @Date / @Description` 与"基线不可回改"说明；② 文件命名 `V{版本}-{模块}-{描述}-ddl.sql` 与配套 DML 同名后缀 `-dml.sql`；③ 新增列 nullable/带默认值保持向后兼容（[§7 回滚预案](#7-生产变更流程建议)）。

## 5. 框架内置表初始化

框架提供两张内置表的基线 SQL（`db/init/`，需随项目库初始化）：

### 5.1 Outbox 本地事务表（`db/init/ddl/001-mq-init-ddl.sql`）

`message_outbox`：最终一致性可靠投递的事务表（本地事务内写业务数据 + 追加消息，定时轮询投递）。关键字段：

| 字段 | 说明 |
| ---- | ---- |
| `msg_id` / `biz_id` | 消息幂等键组成（`uk_msg_biz` 唯一，规范 §9.2） |
| `topic` / `tag` / `payload` | 目标 Topic / Tag / 消息体（JSON） |
| `status` | 0 待发送 / 1 已发送 / 2 失败超限 / 3 死信队列 |
| `retry_count` / `next_retry_at` | 重试次数 / 下次可重试时间（指数退避 base×2^n，S9-4） |
| `created_at` / `updated_at` / `cleaned_at` | 创建（清理判断依据）/ 最近投递重试 / 清理时间 |

新表无初始数据（DML 无需提供）；已发送记录保留 7 天后由 `outbox_cleaner` 清理。初始化后迁移链由 Alembic 管理（`0001` 基线 + `0002` 增量补 `next_retry_at` 列与 `idx_status_next_retry` 索引，见 §1 示例）。

### 5.2 AI 模型配置表（`db/init/ddl/002-ai-model-config-init-ddl.sql` + `dml/002-ai-model-config-init-dml.sql`）

`ai_model_config`：模型配置入库（`app.ai.store.type: db` 时使用），`model_code` 唯一、`api_key` **仅存 `env:VAR` 引用**（如 `env:LLM_API_KEY`，真实密钥经环境变量注入，禁止明文落盘）。初始 DML 幂等（`INSERT IGNORE` 按唯一键去重，不覆盖已修改配置），预置示例模型 `deepseek-v4-flash`。

字段与用途（页面化配置新增/修改经 upsert 幂等落库，模型逻辑名与供应商映射在 SPI 注册表声明、参数在此管理）：

| 字段 | 说明 |
| ---- | ---- |
| `model_code` | 模型逻辑名（唯一，业务引用标识，`uk_model_code`） |
| `provider` | 供应商逻辑名（缺省 `openai_compatible`） |
| `api_base` / `api_key` | 供应商 API 基地址 / Key 引用（`env:VAR`，禁止明文） |
| `model_id` | 厂商侧真实模型 ID（缺省使用 `model_code`） |
| `max_tokens` / `temperature` / `top_p` / `timeout` | 生成参数（最大 Token/采样温度/核采样/超时秒） |
| `input_price_per_1k` / `output_price_per_1k` | 输入/输出 Token 单价（元/1K，AI 规范 §5.2 成本计量） |
| `created_at` / `updated_at` | 创建/更新时间 |

```sql
-- 幂等 DML 要点（db/init/dml/002-ai-model-config-init-dml.sql）
INSERT IGNORE INTO ai_model_config (model_code, model_name, provider, api_base, api_key, ...)
VALUES ('deepseek-v4-flash', 'DeepSeek V4 Flash', 'openai_compatible',
        'https://api.deepseek.com/v1', 'env:LLM_API_KEY', ...);
```

> 启用 `app.ai.store.type: db` 时，应用启动生命周期自动从表注册模型（`register_from_store`）；注册失败仅记 error 日志不阻断启动，调用回落 `E4-AI-001`（见 [排障指南](./05-排障指南.md) §6）。

## 6. 多服务多库管理

微服务脚手架为 Monorepo 多服务分库（`flower_user` / `flower_order`），各服务自带 `alembic/` 与 `alembic.ini`，**迁移命令统一在仓库根执行**（`-c` 指定服务 ini；`env.py` 自动加载仓库根 `.env`，URL 支持服务专属变量）：

```bash
# 升级到最新版本（URL 解析：USER_DATABASE_URL / ORDER_DATABASE_URL > DATABASE_URL > alembic.ini）
alembic -c services/user-service/alembic.ini upgrade head
alembic -c services/order-service/alembic.ini upgrade head

# 生成迁移（业务模型已在各服务 alembic/env.py 导入注册到 Base.metadata）
alembic -c services/user-service/alembic.ini revision --autogenerate -m "add_xxx"
alembic -c services/user-service/alembic.ini history       # 迁移历史
alembic -c services/user-service/alembic.ini downgrade -1  # 回滚一个版本
```

```dotenv
# 仓库根 .env（服务专属 URL 优先）
USER_DATABASE_URL=mysql+aiomysql://root:root@127.0.0.1:3306/flower_user
ORDER_DATABASE_URL=mysql+aiomysql://root:root@127.0.0.1:3306/flower_order
DATABASE_URL=
```

要点：

- **分库边界**：user-service 只迁移 `flower_user`、order-service 只迁移 `flower_order`，互不越界；应用侧连接库名由 `APP_DB_USER_MYSQL_DATABASE` / `APP_DB_ORDER_MYSQL_DATABASE` 区分；
- 每个服务独立的 `alembic/versions/` 序列（`0001_user_init.py` / `0001_order_init.py`），版本号互不相关；
- 脚手架 `db/init/`（基线）+ `db/versions/`（增量）规则与框架一致，基线由 docker-compose 首次初始化执行（见 [部署与 Docker](./01-部署与Docker.md) §4）。

### 6.1 新环境初始化时序

| 步骤 | 动作 | 命令/说明 |
| ---- | ---- | ---- |
| 1 | 拉起外部依赖（MySQL 等） | `docker compose up -d`（脚手架本地；生产由运维提供） |
| 2 | 基线初始化 | MySQL 容器首次启动自动执行 `db/init`（`init-mysql.sh` 依次 ddl → dml，建库/建表/预置数据） |
| 3 | Alembic 迁移到 head | 各服务分别 `alembic -c services/<svc>/alembic.ini upgrade head`（与基线合流，见 §1 说明） |
| 4 | 验证 | `/health/ready` 依赖连通；`SELECT * FROM message_outbox LIMIT 1` 等核对内置表 |

> 已存在数据的环境（升级部署）**只走步骤 3**（增量迁移），禁止重跑基线（基线禁止回改，重建会覆盖存量）。

**升级部署完整命令序列**（微服务形态，仓库根执行）：

```bash
# 1) 仓库根 .env 已配 USER_DATABASE_URL / ORDER_DATABASE_URL（§3）
# 2) 按依赖顺序迁移（先用户库后订单库，订单库迁移不依赖用户库内容则无先后）
alembic -c services/user-service/alembic.ini upgrade head
alembic -c services/order-service/alembic.ini upgrade head
# 3) 核对迁移链（两库分别确认都在最新 revision）
alembic -c services/user-service/alembic.ini current
alembic -c services/order-service/alembic.ini current
# 4) 验证
curl http://127.0.0.1:8001/health/ready
curl http://127.0.0.1:8002/health/ready
```

## 7. 生产变更流程建议

| 阶段 | 动作 | 检查项 |
| ---- | ---- | ---- |
| 评审 | 增量脚本走 MR 评审 | 命名规范（`V{版本}-{模块}-{描述}-ddl/dml.sql`）、DDL/DML 成对、幂等性、向后兼容（新列 nullable/带默认值）、回滚方案 |
| 预演 | test/stage 执行 `alembic upgrade head` + 数据校验 | 迁移链完整（`alembic history` 核对）、无历史脚本改动 |
| 灰度 | 先迁一个实例/服务，旧代码跑新结构 | 新结构向后兼容（先加列后回填，禁止先删列/改类型） |
| 上线 | 低峰期执行，**先 DDL 后 DML** | 大表变更评估在线 DDL 工具；DML 幂等可重跑 |
| 记录 | 变更日志归档 | 脚本版本/执行人/时间/影响行数/回滚预案 |
| 回滚 | 见下方回滚预案 | — |

**核心流程要点**：

1. **评审与预演**：DDL/DML 脚本走 MR 评审（命名规范、幂等性、回滚可行性）；先在 test/stage 环境执行并验证（`alembic upgrade head` + 数据校验）；
2. **先 DDL 后 DML**：同一版本脚本内 DDL 先于 DML 执行（加列→回填）；DML 必须幂等，可重复执行（执行失败重跑不产生脏数据）；
3. **灰度**：多实例/多服务先迁移一个服务实例验证（旧代码兼容新结构，如新增 nullable 列），再全量迁移；**只前向演进**——已发布的迁移脚本禁止回改，问题用新版本脚本修正（规范 §13.1 权威迁移）；
4. **回滚预案**：
   - 应用回滚（代码回旧版）时，数据库保持新版结构——增量变更需保证**向后兼容**（新列 nullable/带默认值，禁止先删列/改列类型）；
   - 迁移回滚：`alembic downgrade -1` 仅限未发布验证阶段；已上生产的结构变更回滚走**补偿 DDL**（新版本脚本反向操作 + 数据修复 DML），不依赖 downgrade；
   - 大表变更（加索引/改列）建议低峰期执行，必要时评估在线 DDL 工具；
5. **记录**：每次生产变更记录脚本版本、执行人、时间、影响行数、回滚预案，归档运维日志（与基线/增量脚本同目录管理）。
