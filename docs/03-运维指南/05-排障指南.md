## 1. 启动失败

**症状**：应用启动即抛 `ConfigError` 或告警后异常退出。

**定位**：查看启动日志错误类型（配置装配期快速失败为框架设计——未知 type/能力/中间件不静默回落默认实现）：

| 错误特征 | 根因 | 处置 |
| ---- | ---- | ---- |
| `ConfigError: app.db.type=xxx 未注册组件实现`（cache/db/storage/mq/registry 同型） | 组件 type 拼写错误或未注册自定义实现 | 核对 `application.default.yml` 合法值（`memory/redis`、`mysql/sqlite`、`local/minio`、`rocketmq`、`nacos`）；自定义实现需 `xxxRegistry.register` 后装配 |
| `ConfigError: 能力装配校验失败：未注册的能力/能力依赖循环` | `app.capabilities.enabled` 声明了未知能力或依赖环 | 查 `CapabilityRegistry.names()` 合法能力名；删去非法声明 |
| `ConfigError: 未注册的 Web 中间件: xxx` | `app.web.middlewares` 拼写错误 | 合法内置：`trace_id/auth/rate_limit/idempotency/security_headers` |
| `ConfigError: 日志配置错误` | `app.logging.sinks` 未注册通道名 / `output=file` 缺路径 | 按 `LogSinkRegistry` 注册自定义通道；`output` 与 `file` 配对 |
| `ConfigError: app.ai.store.type=xxx 未注册模型配置来源` | AI store type 拼写错误 | 合法内置：`yml` / `db`；自定义经 `ModelConfigStoreRegistry.register` |
| 告警「未显式指定 APP_ENV」 | 漏配环境 | 生产 `APP_ENV=prod`（见 [配置管理](./02-配置管理.md) §5） |

**处置**：按错误 key 定位配置段修正后重启；`ConfigError` 均携带 `key` 字段（如 `app.capabilities.enabled`）便于检索。

**实际日志示例**（启动失败定位）：

```text
web_infra.infra.error.config_error: 组件类型 app.db.type=postgresql 未注册组件实现（内置：mysql, sqlite；
自定义实现经对应注册表 register 注册后装配）
web_infra.core.application: ConfigError: 能力装配校验失败：未注册的能力: pay1；能力依赖循环: pay -> authz -> pay
web_infra.core.application: ConfigError: 日志配置错误: 未注册的日志通道 elk（LogSinkRegistry 按名解析）
```

**处置顺序建议**：① 读报错 `key` 定位配置段；② 与 `application.default.yml` 合法值比对（type 拼写/能力名/中间件名/日志通道）；③ 自定义组件确认已 `register` 注册；④ 修正后重启，逐条消错。业务代码自检示例（`CapabilityRegistry.names()` 查合法能力名）：

```python
from web_infra import CapabilityRegistry
print(sorted(CapabilityRegistry.names()))
```

## 2. 依赖连接失败

**症状**：`/health/ready` 返回 503（组件 `DOWN`）；接口调用报数据库/缓存/MQ 连接错误；服务间 Feign 调用超时。

**定位**：

```bash
curl http://127.0.0.1:8001/health/ready     # 503 响应体 components 字段标出 DOWN 组件
```

**实际响应示例**（`/health/ready` 503，`components` 直接指出故障组件）：

```json
{"status": "DOWN", "service": "user-service",
 "components": {"cache": "UP", "db": "DOWN", "storage": "UP", "mq": "UP", "registry": "UP"}}
```

`/health/ready` 逐个探测已装配组件的 `health_check()`（MySQL/Redis/Nacos/MinIO 等），`components` 字典直接给出 DOWN 组件名。连通性自检：

```bash
# MySQL
mysql -h <host> -P 3306 -u<user> -p<pass> -e "SELECT 1"
# Redis
redis-cli -h <host> -p 6379 ping
# Nacos（HTTP 8848 管理面 + gRPC 9848 必须都可达，nacos-sdk-python v2 用 gRPC）
curl http://<nacos-host>:8848/nacos/v1/console/health/liveness
# MinIO
curl http://<minio-host>:9000/minio/health/live
```

**常见根因与处置**：

| 现象 | 根因 | 处置 |
| ---- | ---- | ---- |
| 容器内连 `127.0.0.1` 失败 | `application.yml` 默认值指向本机，容器内未覆盖 | 用服务名/编排网络地址覆盖（`APP_DB_MYSQL_HOST` 等） |
| MySQL SSL 报错 | 框架默认 `use_ssl: true`，本地无证书 | 有证书配 `ssl_ca`；无证书环境显式 `use_ssl: false`（生产开启） |
| Nacos 注册成功但发现失败 | gRPC 端口 9848 未放行（只开了 8848） | 放行 9848；`server_addresses` 支持逗号分隔多地址 |
| Feign 调用超时 | 注册 IP 是容器内网 IP（外部不可达） | 显式注入 `POD_IP` / `HOST_IP` / `NACOS_REGISTER_IP`（见 [部署与 Docker](./01-部署与Docker.md) §7） |
| 偶发连接超时 | 连接池耗尽/慢查询占满 | 见 [§7 性能问题](#7-性能问题) |

**诊断端点 403**（`/metrics`、`/capacity`）：生产环境 IP 白名单未命中（`E4-SYS-004`），排查见 [监控与告警](./03-监控与告警.md) §5。

## 3. 内存版组件误上生产

**症状**：重启后缓存/消息/注册数据丢失；多实例间数据不一致；订单事件丢失。

**根因**：`app.cache.type: memory`（重启丢缓存）、`app.mq.type: memory`（进程内队列，重启丢消息、多实例不互通）、`app.registry.type: memory`（实例列表仅本进程）、内存幂等存储/内存 JWT 状态存储（单实例有效）。

**处置**：

```yaml
# 生产必须切换外部实现（微服务脚手架形态）：
app:
  cache: { type: redis }        # + app.cache.redis 连接
  mq: { type: rocketmq }        # + app.mq.rocketmq.name_server
  registry: { type: nacos }     # 注册中心禁止内存实现
  storage: { type: minio }      # 持久化对象存储
```

- 幂等中间件多实例切 `store_type: redis`；JWT 登出/消息幂等存储换 Redis 实现（见 [部署与 Docker](./01-部署与Docker.md) §9.3）；
- 排查清单：核对 `application.yml` 各组件 type 与 `.env` 连接注入（[配置管理](./02-配置管理.md) §1 优先级——环境变量覆盖生效需重启）。

**快速核对命令**（确认实际装配了什么实现）：

```bash
# 启动日志中核对组件装配类型
grep -E "cache|mq|registry|storage" logs/app.log | head -n 20
# /metrics 确认注册中心实例数（memory 实现无 registry_instances 指标，可反证）
curl -s "http://127.0.0.1:8000/metrics?format=text" | grep "^registry_" || echo "未装配 Nacos/实例指标"
```

## 4. 消息丢失 / 重复

**症状**：下游未收到事件（丢失）；同一条消息被消费多次（重复）。

**定位与处置**：

1. **Outbox 状态**（`message_outbox.status`：0 待发送 / 1 已发送 / 2 失败超限 / 3 死信）：

```sql
-- 待发送积压 / 失败超限 / 死信分布
SELECT status, COUNT(*) FROM message_outbox GROUP BY status;
-- 卡在待发送超时的消息（next_retry_at 已到仍 0）
SELECT id, msg_id, biz_id, topic, retry_count, status, next_retry_at
FROM message_outbox WHERE status = 0 ORDER BY id DESC LIMIT 20;
```

   - 大量 `status=0`：检查 Outbox 定时任务是否注册（`register_outbox_tasks` 装配 `message-outbox-publish`，多实例需分布式锁防重复投递，见 [部署与 Docker](./01-部署与Docker.md) §9.2）；
   - `status=2`：投递重试超限（`max_retry`），检查 MQ 连通性、Topic 是否存在；
   - `status=3`：已进死信主题（`dead_letter_topic`，如 `web-dlq-topic`），从 DLQ 消费处置后手动补发。

2. **幂等键**：消费侧以 `bizId + msgId` 为幂等键（`IdempotentConsumer`，保留 7 天）——重复消息被跳过属**预期行为**（日志 `message_duplicate_skipped`），确认业务是否已正确处理（重复事件 = 幂等跳过；业务失败回滚幂等键允许重试）。

3. **指标**：`mq_pending`（积压）、`rate(mq_dlq_messages_total[5m])`（死信速率）、`mq_errors_total`（消费错误，phase 标签定位阶段）。

**处置**：修复根因（连通性/任务装配/锁）后，对 `status in (2,3)` 的待补发消息走人工确认后重投或业务补偿；重复消费无需处理（幂等兜底）。

**DLQ 消费与补发示例**（`status=3` 已投死信主题，`dead_letter_topic` 如 `web-dlq-topic`）：

```bash
# 1) 核对死信速率（确认是否持续产生）
curl -s "http://127.0.0.1:8000/metrics?format=text" | grep "^mq_dlq"
# 2) 查看死信明细（Outbox 表）
SELECT id, msg_id, biz_id, topic, retry_count, status, updated_at
FROM message_outbox WHERE status = 3 ORDER BY updated_at DESC LIMIT 10;
# 3) 人工确认 payload 后：消费死信主题消息并补偿业务（幂等键保证重放安全）
#    框架提供 DlqConsumer（dlq_consumer.py）按主题消费，处置后手动 ACK
```

**关键检查点**：`mq_pending`（积压）与 `mq_dlq_messages_total`（死信）指标、`message_outbox` 状态分布、Outbox 任务是否注册（`register_outbox_tasks` 装配 `message-outbox-publish`/`message-outbox-cleanup`）。

## 5. 支付回调 401

**症状**：微信支付回调返回 401（微信侧将重试）；业务侧日志 `微信回调…拒绝`。

**定位**：回调验签链路（`WeChatCallbackVerifier.parse`，验签失败/解密失败/解析失败统一返回 None → 调用方回 401）逐项排查：

| 日志特征 | 根因 | 处置 |
| ---- | ---- | ---- |
| 「缺少签名头，拒绝」 | 回调未带 `wechatpay-*` 头（网关剥离/转发丢失） | 确保回调转发透传全部 `wechatpay-timestamp/nonce/signature/serial` 头 |
| 「时间戳超窗，拒绝」 | 时间戳容差超窗（防重放，`CALLBACK_SIGN_EXPIRE_SECONDS`） | 服务器时钟校准（NTP）；回调经多跳转发产生延迟时核对链路耗时 |
| 「无匹配验签凭据 serial=xxx」 | 平台证书缺失/未更新 | `platform_cert_dir` 放置最新平台证书；或开启 `cert_auto_download: true`（验签遇未知序列号自动调 `/v3/certificates` 获取） |
| 「验签失败 serial=xxx」 | `api_v3_key`/私钥/证书不匹配 | 核对商户参数（`APP_PAYMENT_WECHAT_*`）：`api_v3_key`、商户私钥、平台证书序列号对应关系 |
| 「报文解密/解析失败」 | `api_v3_key` 错误 / 报文被篡改 | 核对 `api_v3_key`；抓原始报文比对 |

**处置**：按表修正配置/证书后，微信侧会自动重试（未重试可在商户平台手动重发通知）。回调处置另见 [订单兜底策略.md](../订单兜底策略.md) 与开发文档 [支付](../02-开发者指南/19-支付.md)。

**本地自测**（框架提供回调模拟器，验证业务分发链路，不触网）：

```python
from web_infra.capabilities.payment.testing import PaymentCallbackSimulator
# 构造合法/篡改回调报文分别验证：合法应 200 分发，篡改应 401 拒绝
```

> 401 是微信回调验签的**预期失败语义**（验签失败返回 401 让微信重试）——排查重点在"为什么验签失败"，而非"如何让 401 变 200"。

## 6. AI 调用失败

**症状**：AI 接口报错（错误码定位：`E3-THIRD-*` 可重试 / `E4-AI-*` 业务不可重试）。

| 错误码 | 根因 | 处置 |
| ---- | ---- | ---- |
| `E3-THIRD-001/002/003`（模型供应商服务不可用/超时/限流） | 供应商故障/网络/配额，**可重试**（框架模型网关主备降级自动切换备份） | 确认 `api_base` 可达、网络代理；看 `ai_llm_calls_total{outcome="degraded"}` 降级率；超时参数 `app.ai.connection_pool.*` |
| `E4-AI-001`（模型/供应商未配置） | 模型未注册（`app.ai.store.type=db` 时表未初始化/注册失败；yml 清单缺失） | 检查 `ai_model_config` 表数据（见 [数据库变更管理](./04-数据库变更管理.md) §5.2）与启动日志 `ai_model_config_db_register_failed`；yml 模式核对 `app.ai.models` |
| `E4-AI-002`（输出内容未通过安全审核 BLOCK） | 内容审核拦截（`rule_based_content_guard` 等） | 调整业务提示词/输入；这是业务防护行为，非故障 |
| `E4-AI-005`（成本配额已耗尽） | 配额用尽（`app.ai.quota` 或 db 配额） | 提升/重置配额后重试；排查异常消耗（`rate(ai_cost_total[5m])`） |

**定位辅助**：`/metrics` 的 AI 分组（调用量 outcome 拆分、TTFT P95、Token/成本）；日志 `error_code` 字段聚合。重试语义：E3 可重试、E4 不可重试（出网错误码见 [常量与错误码.md](../常量与错误码.md)）。

**可重试/降级相关配置**（`app.ai.*`，见 [配置管理](./02-配置管理.md) 与开发文档 [AI模型网关](../02-开发者指南/15-AI模型网关.md)）：

```yaml
app:
  ai:
    enabled: true
    store: { type: db }                    # 模型配置入库（E4-AI-001 时先查此表）
    model_gateway:
      default_scene: chat
      routes:
        chat:
          primary: deepseek-v4-flash       # 主模型
          backups: [deepseek-v4-lite]      # 备选：主模型失败自动降级（outcome=degraded）
    connection_pool:
      connect_timeout_seconds: 1.0         # E3-THIRD-002 超时优化
      stream_read_timeout_seconds: 30.0
    quota:
      max_cost: 1000.0                     # 配额耗尽 E4-AI-005 时核对/调整
      window_seconds: 3600
```

**E4-AI-001 专项**（模型未配置时）：`store.type: db` 场景启动日志 `ai_model_config_db_register_failed` → 查 `ai_model_config` 表是否有对应 `model_code` 记录（[数据库变更管理](./04-数据库变更管理.md) §5.2）；`store.type: yml` 场景核对 `app.ai.models` 清单与路由 `primary/backups` 引用名一致。

## 7. 性能问题

**症状**：接口变慢/超时、CPU/内存水位高、连接池打满。

**定位四步**（全部数据来自 `/metrics`，详见 [监控与告警](./03-监控与告警.md) §2）：

1. **慢 SQL**：`rate(slow_sql_total[5m])` 按 severity 拆分；HTML 页「慢请求与慢 SQL」分组看明细（最近 20 条：耗时/SQL/severity）→ 定位 SQL 并优化（索引/改写/缓存）；
2. **慢请求**：`slow_request_total` + 慢请求样本（含 TraceId/各阶段耗时）→ 定位是 DB/缓存/第三方哪一段（`request_phase_duration_seconds`）；
3. **连接池水位**：`mysql_pool_active_connections / mysql_pool_connection_total` ≥ 80% 且持续（对应 PoolAlert 80%/5min 双条件）→ 连接泄漏查 `mysql_pool_connection_leak_total`、扩 `pool_size/max_overflow`、排查慢查询占用；
4. **容量评估报告**：`/capacity`（或 CLI `python -m web_infra.capabilities.capacity --json`）读 `utilization_ratio` 与 `static.bottleneck`（瓶颈组件）→ 对瓶颈维度扩容/拆分；`theoretical_max_qps` vs `safe_qps` 判断余量。

**实际命令示例**（按序执行）：

```bash
# 1) 慢 SQL / 慢请求速率与明细
curl -s "http://127.0.0.1:8000/metrics?format=text" | grep -E "^slow_(sql|request)"
# 2) 连接池水位（活跃/总数/泄漏）
curl -s "http://127.0.0.1:8000/metrics?format=text" | grep -E "^mysql_pool"
# 3) 容量报告（JSON）
curl -s "http://127.0.0.1:8000/capacity?format=text" | python -m json.tool | grep -E "bottleneck|utilization|safe_qps|theoretical"
# 4) 慢请求样本取 TraceId -> 日志平台拉全链路
curl -s "http://127.0.0.1:8000/metrics?format=html" -o /tmp/m.html   # 浏览器打开看明细
```

**处置**：按瓶颈定位结果处置（SQL 优化 / 连接池参数调整 / 扩容 / 限流 `rate_limit` 中间件接入）；处置后重跑 `/capacity` 验证利用率回落。

## 8. 日志排查

- **trace_id 全链路检索**：`app.logging.format: json` 下每条日志含 `trace_id` 字段，检索时以 TraceId 聚合一条请求的完整链路（中间件生成/透传，贯穿服务间调用）；
- **error_code 字段**：错误日志按 `error_code` 聚合（业务 `logger.error(..., extra={"error_code": "E4-AI-001"})`），与出网错误码对应；
- **敏感信息误脱敏**：框架日志自动脱敏（`masking.py`/`sensitive_data_filter.py`）——若发现业务字段被脱敏导致排查困难，属预期安全行为，需按脱敏规则调整字段分类，**不要关闭脱敏**；反之若日志出现明文敏感信息，检查是否绕过框架 logger 直打 print/第三方库日志；
- **文件日志**：`app.logging.output: both/file` + `app.logging.file`（默认 `logs/app.log`，`retention_days` 30 天）；自定义通道经 `app.logging.sinks` 接入集中平台（见 [监控与告警](./03-监控与告警.md) §8）。

**检索示例**（日志平台 / 本地 grep）：

```bash
# 按 TraceId 拉一条请求全链路（JSON 单行日志）
grep "a1b2c3d4e5f6" logs/app.log
# 按错误码聚合
grep '"error_code": "E4-AI-001"' logs/app.log | head -n 20
# 聚合统计（PowerShell）
Select-String -Path logs/app.log -Pattern '"error_code": "E4-[A-Z]+-[0-9]+"' -AllMatches |
  ForEach-Object { $_.Matches.Value } | Group-Object | Sort-Object Count -Descending
```

## 9. 优雅停机异常

**症状**：停机时存量请求被中断；组件关闭顺序异常（如插件依赖的 Redis 提前关闭）；等待窗口未生效即退出。

**定位与处置**：

| 现象 | 根因 | 处置 |
| ---- | ---- | ---- |
| 等待窗口未走完即被杀 | 编排层超时小于 `app.graceful_shutdown_wait_seconds` + 关闭耗时 | K8s `terminationGracePeriodSeconds` 大于等待窗口（建议 ≥ 30s）；`app.graceful_shutdown_wait_seconds` 生产 ≥ 10s（见 [部署与 Docker](./01-部署与Docker.md) §6） |
| 存量请求未排空被中断 | 摘流量时机晚于触发停机 | 编排层 `preStop` 先摘流（注册中心下线/就绪摘除）再触发停机 |
| 扩展点 shutdown 异常 | 扩展点 `shutdown` 钩子依赖已关闭的框架组件 | 框架按**逆拓扑序**执行扩展点停机、先于框架组件 close（源码 `_lifespan`）；业务插件勿在 shutdown 后访问框架组件 |
| 组件 close 报错 | 连接已断/重复关闭 | 组件 `close/stop` 应幂等；日志定位具体组件，核对连接参数 |

**排查命令**（停机时序核对）：

```bash
# 停机日志时序（应有 等待窗口 -> 逐组件 close 的顺序记录）
grep -E "shutdown|close|graceful" logs/app.log | tail -n 20
# 编排层参数核对（K8s）
kubectl get deploy order-service -o jsonpath='{.spec.template.spec.containers[0].lifecycle}'
kubectl get deploy order-service -o jsonpath='{.spec.template.spec.terminationGracePeriodSeconds}'
# 等待窗口配置核对
grep -A2 "graceful_shutdown_wait_seconds" application.yml
```

> 停机流程三段（源码 `Application._lifespan`）：容量采样停止 → 扩展点逆序 shutdown → 组件 `close/stop`；`/health/ready` 随组件关闭自然返回 DOWN（无独立就绪开关）。

## 10. 排查工具清单

| 工具 | 路径/命令 | 用途 |
| ---- | ---- | ---- |
| 存活/就绪探针 | `GET /health/live`（进程存活）、`GET /health/ready`（依赖连通性，503 带 components 明细） | 容器编排探活 + 依赖故障定位（[部署与 Docker](./01-部署与Docker.md) §5） |
| 指标端点 | `GET /metrics?format=text`（生产需内网来源） | RED/慢 SQL/连接池/AI/容量指标全量抓取（[监控与告警](./03-监控与告警.md) §2） |
| 容量评估 | `GET /capacity?format=text`、CLI `python -m web_infra.capabilities.capacity --json [--remote]` | 瓶颈定位与容量规划（§7 第 4 步） |
| HTML 可视化 | 浏览器 `GET /metrics?format=html`、`GET /capacity?format=html` | 慢 SQL 明细、分位数、分组导航（免装 Grafana 快速排障） |
| 应用日志 | `logs/app.log`（文件）或日志平台（JSON 按 `trace_id`/`error_code` 检索） | 全链路排查（§8） |
| 数据库 | `SELECT ... FROM message_outbox`（消息状态）、`SHOW PROCESSLIST`（慢查询） | 消息/性能定位（§4/§7） |
| 外部依赖自检 | `mysqladmin ping` / `redis-cli ping` / Nacos 8848+9848 / MinIO health | 连通性分层确认（§2） |

> 提示：所有诊断端点命令均为只读探测，可安全在任何环境执行；生产环境访问 `/metrics`/`/capacity` 需在白名单网段（[监控与告警](./03-监控与告警.md) §5），否则先经内网代理或临时追加 CIDR。

> 以上端点与配置均以源码与脚手架真实实现为准；文档引用详见 [部署与 Docker](./01-部署与Docker.md)、[配置管理](./02-配置管理.md)、[监控与告警](./03-监控与告警.md)、[数据库变更管理](./04-数据库变更管理.md)。

**排障三原则**：

1. **先探针后日志**：`/health/ready`（组件级）→ `/metrics`（量化水位）→ `/capacity`（容量瓶颈）→ 日志（TraceId 全链路），自下而上收敛；
2. **先连通后配置**：外部依赖连通性（MySQL/Redis/Nacos 9848/MinIO）确认无误后，再查连接参数与白名单类配置，避免在错误层反复；
3. **先恢复后根治**：生产故障优先恢复（回滚/降级/扩容），问题根因记录归档后按 §1~§9 章节专项处置，不在恢复过程现场深挖。
