## 1. 目标与原则

订单是资金相关核心链路，任意一环（参数校验 / 服务间调用 / 落库 / 事件发布 / 事件消费 / 状态流转 / 查询缓存）都可能出问题。兜底设计遵循三条原则：

1. **默认兜底**：框架组件内置默认降级/重试/幂等策略，业务不传参即生效（如 FeignClient 默认 503 兜底、MQ 消费失败自动重试进死信）。
2. **不丢事件**：业务数据落库与事件记录同本地事务（Outbox 模式），MQ 故障不丢消息，投递失败指数退避重试、超限进死信队列。
3. **幂等兜底**：接口级（API 幂等键）与消息级（bizId+msgId 幂等键）双重幂等，重试/重投不产生副作用。

## 2. 订单链路全景

订单创建链路（order-service 演示）各环节与兜底责任方：

| # | 环节 | 风险点 | 兜底机制 | 责任方 |
|---|------|--------|---------|--------|
| 1 | 请求入口参数校验 | 非法参数 / 重复提交 | Pydantic 校验 + 全局异常处理器；`IdempotencyMiddleware` 幂等键 | 框架 |
| 2 | 服务间调用（user-service） | 实例不可用 / 超时 / 慢调用 / 上游 5xx | 注册中心发现 + 负载均衡 + 指数退避重试 + 熔断 + 默认 503 兜底 | 框架 FeignClient |
| 3 | 订单落库 | DB 故障 / 并发写冲突 | `orm_session` 自动提交/回滚；唯一约束（order_no） | 框架 + 业务 |
| 4 | 订单事件发布 | **订单已落库但 MQ 发布失败 → 事件丢失** | Outbox 本地事务表（同事务写入）+ 轮询投递重试/死信 | 框架 Outbox |
| 5 | 订单事件消费 | 重复投递 / 消费失败 / 不可重试错误 | `IdempotentConsumer` 幂等键 + `RetryableConsumer` 异常分类重试 + DLQ | 框架 |
| 6 | 订单状态流转 | 非法流转（如 已取消 → 已支付） | 状态机组合表校验（`StateMachine` + `StateMachineRegistry`） | 框架 |
| 7 | 订单查询缓存 | 缓存穿透 / 缓存与 DB 不一致 | 空值占位防穿透（规范 §8.2）；TTL 兜底 | 框架 + 业务 |
| 8 | 支付下单/回调 | 重复下单 / 验签失败 / 金额/attach 篡改 / 重复回调入账 / 回调丢失掉单 | 渠道骨架（下单幂等/关单查单确认/回调强校验/流水落库）+ 验签失败回 401 + 无处理器静默 + 审计留痕 | 框架 payment |
| 9 | 超时关单（§5.5） | 超时未支付订单长期挂起 / 关单时订单已支付 | 定时关单任务：查单确认未支付 → 关单；查单失败跳过不强行关单 | 框架 payment |
| 10 | 对账（§6） | 回调丢失漏入账 / 本地误记 / 金额状态不一致 | T+1 对账：账单 vs 本地流水对齐 → 查单确认后补记/冲正；金额不一致挂账 P0 告警人工 | 框架 payment |
| 11 | 冲正（§7.5） | 不应记/误记的本地账务 | 反向冲正流水 + 原流水标记 + 幂等 + 冲正事件（下游补偿） | 框架 payment |
| 12 | 风控限额（§9） | 大额/高频异常交易 | 单笔/日/月限额 + 频次 + 可疑拆分（E4-PAY-005/006/007） | 框架 payment |

## 3. 各环节兜底策略明细

### 3.1 请求入口参数校验（✅ 框架兜底）

- **风险**：非法参数、恶意构造请求体、重复提交。
- **兜底**：FastAPI + Pydantic 自动校验 → 框架全局异常处理器返回统一错误响应（`web_infra.error.handler`）；重复提交由 `IdempotencyMiddleware` 兜底（幂等键 + 请求摘要 + 结果缓存，重复请求重放首次结果，摘要不一致返回 409）。
- **配置**：`app.web.middlewares.idempotency`（见 5.2）。
- **注意**：幂等键按「userId + Idempotency-Key」隔离，**生产必须启用认证中间件**注入真实用户标识，否则多用户共键空间互相重放。

### 3.2 服务间调用（✅ 框架兜底）

- **风险**：上游实例不可用、网络超时、慢调用拖垮本服务、上游 5xx。
- **兜底**（`web_infra.http.feign_client`）：
  - 服务发现 + 轮询负载均衡；
  - 可重试错误（连接/超时/5xx/429）指数退避重试（`retries` 默认 3 次尝试）；
  - 熔断（`circuit_breaker` 配置段）按服务维度隔离，OPEN 期间走降级；
  - **默认兜底** `default_service_fallback`：未显式传 fallback 时统一返回 HTTP 503 + `E5-SYS-002`「服务不可用」；业务可传 `fallback` 参数自定义降级（如返回缓存数据）。
- **客户端归一化**（脚手架示例 `order_service/client/user_client.py`）：404 → None（用户不存在）；5xx/兜底 503 → 统一抛 `SYS_UNAVAILABLE`；业务不重复实现兜底。
- **配置**：`app.feign` 段（timeout / retries / retry_delay / circuit_breaker）。

### 3.3 订单落库（✅ 框架兜底）

- **风险**：DB 故障、连接池耗尽、并发插入冲突。
- **兜底**：`orm_session()` 上下文自动提交/回滚/关闭（`web_infra.db`）；唯一约束（order_no）防重复；连接池上限与慢 SQL 告警（`monitoring.metrics`）。
- **注意**：多实例部署雪花 ID 必须配置唯一 `worker_id`，否则同毫秒可能生成重复订单号。

### 3.4 订单事件发布（⚠️→✅ 本次已落地 Outbox）

- **风险**（历史缺口）：订单落库提交后直接 `mq.publish`，MQ 发布失败 → 下单接口 500 但订单已落库，**事件永久丢失**，且客户端重试会重复下单。
- **兜底**（规范 §21.3 Outbox 模式）：
  - 订单落库与订单事件写入 `message_outbox` **同一本地事务**（`OrderService.create_order` + `OrderEventPublisher.append_created(record, session=...)`），任一失败整体回滚；
  - `OutboxPublisher.publish_pending()` 定时轮询投递 MQ（`register_outbox_tasks` + `TaskScheduler`），投递成功 `mark_sent`；
  - 投递失败按指数退避设置 `next_retry_at`（`retry_backoff_seconds × 2^n`），重试超限投递死信主题并置 `DLQ` 状态（P0-3/S9-7）；
  - 已发送记录保留 `retain_days`（默认 7 天）由 `OutboxCleaner` 清理。
- **落地位置**：
  - 表：`services/order-service/alembic/versions/0002_order_outbox.py` + `db/versions/V0.2.0-order-outbox-ddl.sql`（`message_outbox`，字段对齐框架 DDL）；
  - 装配：`order_service/main.py#_build_outbox_scheduler`（读取 `app.mq.outbox` 配置段）；
  - 业务接入：见 5.1。
- **已知局限**：`OutboxRecord` 当前不含 `partition_key` 字段，投递消息退化为 topic 级分区；生产 RocketMQ 场景如需按订单分区串行（S9-2），需扩展 `OutboxRecord.partition_key`（框架层）。

### 3.5 订单事件消费（✅ 框架兜底）

- **风险**：MQ 重复投递、消费业务失败、不可重试的业务校验错误。
- **兜底**：
  - `IdempotentConsumer`：以 `biz_id + msg_id` 为幂等键（`biz:bizId`），重复消费跳过；业务失败回滚幂等键允许重试（规范 §9.6）；
  - 消费失败治理（S9-1）：`InMemoryMessageQueue` 内置异常分类——可重试异常指数退避重新入队、超限进死信主题；不可重试（`NonRetryableError`）直接进死信；
  - 外部 MQ（RocketMQ）场景：`RetryableConsumer` 封装异常分类重试 + DLQ，与 `IdempotentConsumer` 组合使用。
- **落地位置**：`order_service/mq/order_event_consumer.py` —— 已组合 `IdempotentConsumer` + `RetryableConsumer`（`dlq_publisher=mq` 内存队列），重试超限/不可重试投递死信主题（P0-3/S9-7）。

### 3.6 订单状态流转（✅ 已接入状态机）

- **风险**：`update_status` 裸 update，非法流转（如 已取消 → 已支付）无拦截。
- **兜底**：框架状态机（`web_infra.state_machine`）——`StateRouter` 声明「状态×事件 → 目标状态」合法组合表，`StateMachine` 引擎流转前校验，非法流转抛 `E4-STATE-001`；`StateMachineRegistry` 注册表（RLock 双重检查并发安全）进程内单例缓存引擎。
- **落地位置**：order-service 已接入——`order_service/state/order_state_machine.py`（`OrderStatus`/`OrderEvent`/`OrderStateRouter` 组合表 + 事件处理器落库），`OrderService.transition` 驱动（支付回调 → `OrderEvent.PAY` 推进订单已支付）；测试见 `test_state_machine_module.py`。

### 3.7 订单查询缓存（✅ 框架兜底）

- **风险**：缓存穿透（不存在订单被高频查询）、缓存与 DB 短暂不一致。
- **兜底**：空值占位防穿透（`set_empty` + 短 TTL 60s，规范 §8.2）；正常缓存 TTL 300s；状态更新后主动失效缓存。

### 3.8 支付下单/回调（✅ 框架兜底）

- **风险**：重复下单、回调验签失败、解密失败、无业务处理器、金额/attach 篡改、重复回调入账、回调丢失掉单。
- **兜底**（`web_infra.payment`）：
  - 渠道骨架（§3.10）：下单幂等、关单查单确认、回调金额/attach/状态机强校验、退款幂等与超额约束、流水落库（唯一键幂等）、能力位拦截（`E4-PAY-008`）；
  - `WeChatCallbackVerifier`：验签/解密失败返回 None → 回调入口回 401 → 微信自动重试；时间戳容差 300s 防重放；
  - 平台证书自动下载：未知序列号自动拉取（`cert_auto_download`），下载失败不阻断、验签失败回 401；
  - `PaymentCallbackDispatcher`：无处理器静默兜底（日志告警），回调入口不抛错；
  - 回调业务处理幂等由业务保证（order-service 已接入订单状态机 + `IdempotentConsumer`）；
  - 审计留痕（§8.3）：骨架 final 入口注入 `audit_store` 后自动记录成功/失败（原始报文仅落审计，§8.6）。
- **入口约定**：渠道验签解密后的业务回调入口先经骨架 `validate_callback`（金额/attach/状态机校验，E4-PAY-002/003）通过后再分发业务处理器——order-service 回调接口已按此编排。

### 3.9 支付渠道调用（下单/查单/退款，✅ 本次已落地重试兜底）

- **风险**：网络抖动、微信服务端 5xx、限流 429、业务错误（参数/状态冲突）。
- **兜底**（`WeChatPayClient`，`web_infra/payment/provider/wechat/wechat_pay_client.py`）：
  - **可重试故障自动重试**：网络异常 / 微信 5xx / 429 按指数退避（`base × 2^n`，含抖动防重试风暴）自动重试，默认 `retries=2`（`WechatPayConfig.retries` 可调，`0` 关闭）；
  - **4xx 业务错误不重试**：参数错误、订单状态冲突等重试无意义，直接抛 `E3-PAY-000`（渠道错误码，`retryable=True`），由调用方按业务处理；
  - **重试耗尽**：统一抛 `E3-PAY-000`，对外收敛为「服务暂时不可用，请稍后重试」，业务可据此提示用户重试或走补偿；
  - **幂等保障**：下单 `out_trade_no`、退款 `out_refund_no` 天然幂等，重试安全不会重复扣款/重复退款；失败后建议业务侧调用 `query_order` 查单确认实际状态再决策（补偿或提示重试）；
  - **降级边界**：支付调用**不建议返回假数据降级**（虚假支付风险），正确兜底 = 重试 + 幂等 + 清晰错误码 + 状态机补偿（查单/关单）。
- **配置**：
  ```yaml
  app:
    payment:
      wechat:
        retries: 2             # 渠道失败重试次数（0 关闭）
        retry_delay_base: 0.5  # 重试退避基数（秒）
        retry_delay_max: 4.0   # 重试退避上限（秒）
  ```

### 3.10 支付渠道骨架兜底（✅ 本次已落地，规范 §3.1/§4/§5）

- **风险**：重复下单、重复回调入账、关单时订单已支付、退款超额、回调金额/attach 被篡改、结果未知掉单。
- **兜底**（`PaymentChannelTemplate` 渠道骨架，`web_infra/payment/payment_channel_template.py`）：
  - **下单幂等**（§4.2）：本地订单 SUCCESS/进行中/EXCEPTION → 拒绝重复下单（`E4-PAY-003`），不透传渠道；
  - **关单查单确认**（§5.5）：关单前先查单，渠道已支付抛冲突禁止关单；查单失败异常向上抛，关单任务捕获后跳过该单（不强行关单防已支付被关闭）；
  - **回调强校验**（§4.3/§4.5）：金额不符 `E4-PAY-002`、attach 不符拒绝入账、支付状态机校验（CLOSED 后回调抛 `E4-PAY-003`，重复回调幂等返回）；
  - **退款幂等与超额约束**（§5.3）：同 `out_refund_no` 拒绝重复申请；已退 + 本次 > 实付金额拒绝（`COMMON_CONFLICT`）；
  - **流水落库**（§5.2）：回调入账/关单/退款申请均写支付流水（BOOKED/PENDING/CLOSED），重复写入由（out_trade_no + event_type）唯一键幂等；
  - **能力位拦截**（§3.4）：调用未声明能力（如无 refund）→ `E4-PAY-008`，不透传渠道；
  - **下单不盲目重试**（§7.2 红线）：`request(retryable=False)`，失败由业务先查单确认再决策（防重复下单/重复扣款）。
- **降级边界**：骨架未注入 `flow_store`/`order_store` 时仅降级跳过校验/流水（日志告警），资金链路强一致需业务注入本地事务表实现。
- **默认实现**：`InMemoryPaymentGateway` 已骨架化（测试/单机注入内存存储即获全套兜底）；生产渠道（如微信 `WeChatPayProvider`）继承骨架填充 `_do_*` 即可。

### 3.11 对账 / 冲正 / 风控兜底（✅ 本次已落地，规范 §6/§7.5/§9）

- **风险**：回调丢失（掉单）、本地误记/渠道未支付、金额/状态被篡改、退款未入账、大额/高频异常交易。
- **兜底**：
  - **对账（§6）**：`ReconciliationService` T+1 对账——账单 vs 本地流水逐笔对齐（订单号 + 事件类型 + 金额）；五类差异分类（§6.3）；自动处理（§6.4：渠道有本地无 → 查单确认后补记；本地有渠道无 → 查单确认未支付后冲正；金额/状态不一致 → 挂账 P0 告警人工，**未确认不处理资金**）；差异清单/处理动作审计落库只增不改（§6.6）。
  - **冲正（§7.5）**：`reversal_flow` 新增反向冲正流水（不可删原流水 + 原流水标记）+ 幂等 + 冲正事件钩子（下游业务补偿失败不阻塞冲正流水）。
  - **风控限额（§9）**：`PaymentRiskGuard` 下单前校验单笔/日/月限额（E4-PAY-005）、频次（E4-PAY-006）、可疑拆分（E4-PAY-007）；Decimal 精确累计 + 原子（防并发超限）；拦截留痕（审计）可申诉。
  - **账单文件（§6.7）**：`BillFileManager` 完整性校验（文件头/长度/校验和）失败丢弃重下、按账期组织、保留期 ≥ 90 天归档。
- **落地方式**：框架提供 SPI + 内存默认实现；生产接入 MySQL 本地事务表 / Redis 计数 / 对象存储 / RBAC 审批（见合规报告 §7 遗留）。

## 4. 框架兜底组件速查表

| 组件 | 位置 | 兜底能力 | 默认启用 |
|------|------|---------|---------|
| `FeignClient` + `default_service_fallback` | `web_infra/http/feign_client.py` | 重试 + 熔断 + 统一 503 降级 | 熔断需配置，兜底默认 |
| `CircuitBreaker` | `web_infra/resilience/circuit_breaker.py` | 错误率 + 慢调用比例双维度熔断 | 配置 `app.feign.circuit_breaker` |
| `WeChatPayClient`（重试） | `web_infra/payment/provider/wechat/wechat_pay_client.py` | 网络/5xx/429 指数退避重试，4xx 不重试 | 默认 `retries=2` |
| `PaymentChannelTemplate`（骨架） | `web_infra/payment/payment_channel_template.py` | 下单幂等 + 关单查单确认 + 回调金额/attach/状态机校验 + 退款幂等/超额约束 + 流水落库 + 能力位拦截 | 渠道继承骨架；注入存储全量生效 |
| `PaymentGatewayRegistry`（能力位校验） | `web_infra/payment/payment_gateway_registry.py` | 缺必选能力拒注册，refund 未配套 query_refund 告警 | 注册时自动 |
| `ReconciliationService` + `run_reconciliation` | `web_infra/payment/reconciliation/` | T+1 对账：差异分类 + 查单补记/冲正 + 审计留痕 + 任务防重 | 业务装配定时任务 |

### 4.1 默认策略 vs 自定义（可配置性接口）

所有兜底组件均遵循「默认策略开箱即用 + 提供覆盖接口」：

| 兜底组件 | 默认策略 | 自定义 / 覆盖方式 |
|---------|---------|------------------|
| FeignClient 降级 | `default_service_fallback`（统一 503 + E5-SYS-002） | 构造传 `fallback` 参数（业务自定义降级，如返回缓存数据） |
| FeignClient 重试 / 熔断 | 重试 3 次尝试、退避含抖动；熔断需配置 | `retries` / `retry_delay_*` / `circuit_breaker_config` 参数或 yml `app.feign` |
| WeChatPayClient 重试 | 网络/5xx/429 重试 2 次 | `WechatPayConfig.retries`（0 关闭）/ 构造参数覆盖 |
| Outbox 投递 | 指数退避重试 3 次，超限进死信 | `MqConfig(max_retry / retry_backoff_seconds / dead_letter_topic)` 或 yml `app.mq.outbox` |
| 消息消费幂等 | `IdempotentConsumer`（bizId 键，保留 7 天） | 注入 store（内存 / Redis 跨实例） |
| 消费失败重试 / DLQ | 内存 MQ 内置治理（S9-1） | `RetryableConsumer(max_retries / backoff / dlq_topic)`；`NonRetryableError` 标记不可重试 |
| API 幂等 | `IdempotencyMiddleware`（内存 store 默认） | yml `app.web.middlewares.idempotency.store_type: redis`（复用 cache 组件 Redis 客户端，多实例原子）；TTL 可配 |
| 状态机引擎 | 自研 `StateMachine`（组合表校验） | `StateMachineRegistry.register_engine_factory` 替换第三方引擎（SPI） |
| 支付回调 | 验签失败回 401 / 无处理器静默 | 注入自定义 `PaymentCallbackVerifier` / `PaymentCallbackHandler`（SPI） |
| 支付骨架 | 注入内存存储即获下单幂等/关单确认/回调校验/流水落库 | 业务注入本地事务表实现（MySQL）替换内存存储；`audit_store` 注入开启审计 |
| 对账 | `ReconciliationService` 差异分类 + 查单补记/冲正（可配 `auto_handle=False` 仅输出清单） | 注入 `query_order`/`query_refund` 回调（渠道权威状态）；审计存储换 MySQL 表 |
| 冲正 | `reversal_flow` 反向流水 + 幂等 | 注入 `event_callback`（下游业务补偿投递，失败不阻塞） |
| 风控限额 | 未注入 guard 不限制（配置化） | `PaymentLimitConfig.upsert` 配置规则；计数存储换 Redis（跨实例） |
| 全局异常 | 错误码 → HTTP 状态统一映射 | `register_global_exception_handlers` 装配，业务自定义异常处理器追加 |

## 5. 落地指引

### 5.1 接入 Outbox（事件可靠投递，规范 §21.3）

1. **建表**：新增 Alembic 迁移创建 `message_outbox`（复制框架 DDL，见 3.4）。
2. **装配存储**（order-service 示例）：
   ```python
   from web_infra.mq import MysqlOutboxStore

   store = MysqlOutboxStore(_session_factory(db))  # db 为 MySQLDatabase，见 main.py
   ```
   其中 `_session_factory` 动态读取 `db.session_factory`（async_sessionmaker，引擎懒加载首次连接后就绪）。
3. **同事务写入**：业务事务内追加记录（订单落库 + 事件同事务）：
   ```python
   async with db.orm_session() as session:
       order = await repository.create(order, session=session)          # 订单落库
       await publisher.append_created(order, session=session)           # 事件同事务写入 Outbox
   ```
4. **注册轮询任务**（startup 启动 / shutdown 停止）：
   ```python
   scheduler = TaskScheduler()
   register_outbox_tasks(scheduler, store, mq_publisher, config=MqConfig(...),
                         publish_interval_seconds=5.0, cleanup_interval_seconds=3600.0)
   scheduler.start()   # startup
   await scheduler.stop()  # shutdown
   ```
5. **配置**（`application.yml`）：
   ```yaml
   mq:
     outbox:
       enabled: true
       max_retry: 3
       retry_backoff_seconds: 30
       dead_letter_topic: web-dlq-topic
       publish_interval_seconds: 5
       cleanup_interval_seconds: 3600
       retain_days: 7
   ```

### 5.2 启用 API 幂等（防重复下单，规范 §12.6）

`application.yml` 中间件配置（键按 userId + Idempotency-Key 隔离，**生产启用认证**）：
```yaml
app:
  web:
    middlewares:
      idempotency:
        ttl_seconds: 86400   # 幂等结果保留 24h（覆盖重试窗口）
```
调用方携带 `Idempotency-Key` 请求头；重复请求重放首次结果，摘要不一致返回 409。
多实例部署将 `InMemoryIdempotencyStore` 替换为 `RedisIdempotencyStore`（跨实例原子占用）。

### 5.3 消费重试 / DLQ（外部 MQ 场景）

```python
from web_infra.mq import IdempotentConsumer, RetryableConsumer

# 业务处理包幂等，再包异常分类重试；重试超限/不可重试进死信主题
retryable = RetryableConsumer(dlq_publisher, max_retries=3, retry_backoff_seconds=5)
await retryable.consume(message, lambda m: idempotent.consume(m, handle_order_event))
```
内存 MQ（`InMemoryMessageQueue`）已内置等效治理（S9-1），无需重复包裹。

### 5.4 接入状态机（订单状态流转合法性，推荐）

定义订单状态/事件与合法流转组合表，注册到 `StateMachineRegistry`，业务更新状态前经引擎校验：

```python
from web_infra.state_machine import StateMachineRegistry, StateRouter
from web_infra.state_machine.state_route_params import StateRouteParams

class OrderStatus:
    CREATED, CONFIRMED, PAID, CANCELLED, REFUNDED = 1, 2, 3, 4, 5

class OrderEvent:
    CONFIRM, PAY, CANCEL, REFUND = "confirm", "pay", "cancel", "refund"

@StateMachineRegistry.register
class OrderRouter(StateRouter[OrderStatus, OrderEvent, Any]):
    def get_state_event_target_config(self) -> dict:
        return {
            OrderStatus.CREATED: {OrderEvent.CONFIRM: OrderStatus.CONFIRMED,
                                  OrderEvent.PAY: OrderStatus.PAID,
                                  OrderEvent.CANCEL: OrderStatus.CANCELLED},
            OrderStatus.CONFIRMED: {OrderEvent.PAY: OrderStatus.PAID,
                                    OrderEvent.CANCEL: OrderStatus.CANCELLED},
            OrderStatus.PAID: {OrderEvent.REFUND: OrderStatus.REFUNDED},
        }

    def get_event_dispatcher(self) -> dict:
        return {
            OrderEvent.CONFIRM: lambda state, p: self._persist(OrderStatus.CONFIRMED),
            # ... 各事件处理器：持久化订单状态并返回目标状态
        }

# 业务调用：非法流转（如 CANCELLED + PAY）由引擎抛 E4-STATE-001
engine = StateMachineRegistry.get(OrderStatus, OrderEvent, Any)
target = await engine.fire_async(current_status, OrderEvent.PAY, StateRouteParams(order_id=...))
```
要点：处理器内完成订单状态持久化（与业务事务一致）；状态机校验失败即拒绝执行，杜绝状态错乱。

### 5.5 生产环境注意事项

1. **多实例**：内存态组件（`InMemoryJwtTokenStore` / `InMemoryIdempotencyStore` / `InMemoryMessageQueue` / `InMemoryQuotaStore`）仅单实例有效，多实例部署替换为 Redis / RocketMQ 等共享实现。
2. **Outbox 分区键**：当前 `OutboxRecord` 无分区键字段，生产 RocketMQ 如需按订单分区串行需扩展（见 3.4 已知局限）。
3. **幂等键隔离**：`Idempotency-Key` 与用户身份联合唯一，生产必须启用认证中间件。
4. **雪花 ID**：多实例必须配置唯一 `worker_id`（环境变量 `SNOWFLAKE_WORKER_ID`），防止订单号重复。
5. **回调幂等**：支付回调业务处理接入幂等（`IdempotentConsumer` 或业务去重表），配合状态机保证重复回调不重复入账。框架侧已有三层幂等兜底：回调唯一键幂等（out_trade_no + event_type，§4.3）、状态机幂等重复对（§4.5）、业务状态机拦截（order-service `OrderEvent.PAY` 重复流转忽略）。
