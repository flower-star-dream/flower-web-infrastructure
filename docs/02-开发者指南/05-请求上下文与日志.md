# 请求上下文与日志

> 一次用户请求从网关到服务到数据库，如何串起来查？如何知道「是谁、在哪个租户下、调了多久」？
> 本文讲透请求上下文（TraceId/用户/租户）与日志体系（格式/脱敏/扩展）。

---

## 1. 请求上下文（RequestContext）

基于 `contextvars` 的请求级上下文，跨异步自动透传，全程无需手动传递参数。

### 1.1 上下文字段

| 字段 | 获取方法 | 说明 |
| ---- | -------- | ---- |
| trace_id | `RequestContext.get_trace_id()` | 链路追踪 ID，一次请求全局唯一 |
| user_id | `RequestContext.get_user_id()` | 当前用户；无上下文返回 `"anonymous"` |
| scope | `RequestContext.get_scope()` | 权限范围（空格分隔，如 `read write`） |
| client_id | `RequestContext.get_client_id()` | 客户端标识 |
| service_id | `RequestContext.get_service_id()` | 调用方服务标识 |
| tenant_id | `RequestContext.get_tenant_id()` | 当前租户（多租户场景） |

```python
from web_infra import RequestContext

@app.get("/whoami")
def whoami():
    return Result.success(data={
        "user_id": RequestContext.get_user_id(),
        "trace_id": RequestContext.get_trace_id(),
    })
```

### 1.2 来源与注入

- **中间件自动注入**：`TraceIdMiddleware` / `RequestContextMiddleware` 从请求头（`X-Trace-Id` / `X-User-Id` / `X-Scope` / `X-Client-Id` / `X-Service-Id` / `X-Tenant-Id`）透传，缺失时生成新 TraceId；
- **统一鉴权中间件覆盖**：`AuthMiddleware` 解析 token 后以 payload 注入 user_id / scope / client_id（业务禁止自行解析凭证）；
- 响应头回写 TraceId，前端/日志系统可关联。

### 1.3 跨线程/异步任务传递

`contextvars` 只随 asyncio 任务透传。跨线程池（如后台任务、线程池调用）需**显式快照/恢复**：

```python
from web_infra import RequestContext

snapshot = RequestContext.snapshot()   # 捕获当前上下文
# …… 在线程池/新任务中：
RequestContext.restore(snapshot)
```

## 2. 日志体系

### 2.1 快速使用

```python
from web_infra import get_logger, configure_logging

logger = get_logger(__name__)   # 自动加 web_infra. 前缀，便于过滤
logger.info("用户下单", extra={"order_id": "20260818001"})
```

配置（application.yml）：

```yaml
app:
  logging:
    level: INFO
    format: text        # text | json
    output: both        # both | console | file
    file: ${APP_LOGGING_FILE:logs/app.log}
    retention_days: 30
```

### 2.2 统一日志格式

文本格式自动携带链路字段：

```
[2026-08-18 10:00:00,123] [INFO] [trace-abc123] [biz] [order_service] [main.py.get_order] [user-1] 用户下单
```

字段依次为：时间、级别、`trace_id`、`phase`（阶段）、模块、文件与函数、`user_id`、消息。

JSON 格式（生产推荐，便于采集解析）：

```json
{
  "time": "2026-08-18T02:00:00.123Z",
  "level": "INFO",
  "trace_id": "trace-abc123",
  "module": "order_service",
  "user_id": "user-1",
  "error_code": "",
  "message": "用户下单"
}
```

错误日志约定：`logger.error(..., extra={"error_code": "E4-ORDER-001"})` 将错误码写入 JSON 的 `error_code` 字段。

### 2.3 敏感信息脱敏（自动）

框架为日志统一挂载脱敏过滤器，自动处理三类敏感信息：

| 类型 | 规则 | 示例 |
| ---- | ---- | ---- |
| 密钥类 | 统一替换为 `******` | `password=123456` → `password=******`（覆盖 yml `key: value`、query `key=value`、JSON `"key":"value"`） |
| 手机号 | 中间 4 位打码 | `138****5678` |
| 身份证 | 保留前 6 后 4 | `110101********1234` |
| 银行卡 | 仅留后 4 位 | `****5678` |

手动脱敏：

```python
from web_infra import mask
mask("联系 13812345678")   # → "联系 138****5678"
```

> 数值参数（int/float/bool）不脱敏（防止 `%.3f` 格式化崩溃）；参数值绝不进入日志（SQL 预览只保留语句骨架）。

### 2.4 阶段计时（PhaseTimer）

请求各阶段耗时（网关→鉴权→业务→数据库→RPC→总耗时）：

```python
from web_infra import PhaseTimer

PhaseTimer.start()
# ……业务处理……
PhaseTimer.mark("biz")
# ……RPC 调用……
PhaseTimer.mark("rpc")
PhaseTimer.mark_total()
```

指标 `request_phase_duration_seconds` 与日志 `phase_*_ms` 字段自动产出，用于定位「慢在哪一段」。

### 2.5 自定义日志通道（LogSink SPI）

内置通道：`console`、`file`（按天轮转，保留 retention_days 天）。自定义通道（如 Kafka / 云日志）：

```python
from web_infra import LogSinkInterface, LogSinkRegistry
import logging

class KafkaSink(LogSinkInterface):
    def create_handler(self, options: dict) -> logging.Handler:
        return KafkaHandler(options)   # 返回标准 logging.Handler

LogSinkRegistry.register("kafka", KafkaSink())
```

配置启用：

```yaml
app:
  logging:
    sinks:
      kafka: { topic: app-logs, servers: "kafka:9092" }
```

> 未注册的通道名配置期快速失败（ValueError → ConfigError）。

## 3. 请求日志（访问日志）

启用 `LoggingMiddleware` 后：

- 关闭 uvicorn 原生访问日志（避免重复打印）；
- 输出唯一访问日志：真实客户端 IP（智能识别可信代理头）、路径归一化（UUID/数字段 → `{id}`，防高基数标签）、耗时、状态码、阶段耗时；
- 采集 RED 指标（请求量/错误/延迟）与慢请求样本（>5000ms 记 `slow_request_total`）。

```python
from web_infra import setup_logging_middleware

setup_logging_middleware(app, service_name="order-service")
```

## 4. 链路在微服务间的传递

服务间调用自动透传链路上下文（无需手工设置头）：

- 框架 `FeignClient` 自动从 `RequestContext.snapshot()` 注入 `X-Service-Id / X-User-Id / X-Trace-Id / X-Client-Id / X-Tenant-Id / X-Scope` 请求头；
- 并**剥离 `Authorization` 用户凭证头**（服务间调用禁止裸传用户凭证）；
- 对端 `TraceIdMiddleware` 识别并透传，链路 ID 贯穿全链路。

## 5. 常见问题

**Q：日志里 trace_id 是 `-`？**
A：说明该条日志不在请求上下文中产生（如启动日志、后台线程）。如需关联，先 `RequestContext.snapshot()` 并在线程内 `restore()`。

**Q：JSON 格式怎么接入采集？**
A：每行一条 JSON，字段含 time/level/trace_id/user_id/error_code；对接 Elasticsearch/云日志直接按字段解析即可。

**Q：如何定位慢请求？**
A：三处线索：`slow_request_total` 指标、`slow_sql_total` 指标、访问日志 `duration_ms` 字段；配合 `request_phase_duration_seconds` 直方图定位慢的阶段。
