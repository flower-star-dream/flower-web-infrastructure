## 1. 多租户模型选择

框架同时支持两种主流多租户模型，可按业务规模与合规要求选择或组合：

| 模型 | 实现 | 适用场景 | 成本 |
| ---- | ---- | ---- | ---- |
| **共享库 + 租户列** | `TenantAwareMixin` + `TenantQueryFilter`（SQL 条件自动注入） | 中小规模 SaaS，租户量大、单租户数据量小；运维简单（单库备份/扩容） | 隔离强度中等（依赖 SQL 注入完整性）；全表扫描风险需靠 `tenant_id` 联合索引兜底 |
| **独立库 / Schema 路由** | `TenantDatabaseRouter` + `DatabaseManager`（`app.db.router` / `app.db.instances`） | 大租户、强合规（数据物理隔离）、租户数据量大 | 库数量多，连接池/迁移/备份成本高；需在租户开通/注销时动态维护 |

> 决策建议（详见 [第 10 节](#10-适用场景决策建议与常见坑)）：绝大多数 SaaS 起步选**共享库+租户列**；仅当单租户数据规模、合规审计或大客户 SLA 要求物理隔离时，才为指定租户升级独立库（`TenantDatabaseRouter` 支持按 mapping 逐租户切换，两种模型可共存）。

## 2. 租户上下文（RequestContext / X-Tenant-Id）

租户标识统一经请求头 `X-Tenant-Id`（`AuthConstant.AUTH_HEADER_TENANT_ID`）透传：

- **入站**：`RequestContextMiddleware` 读取请求头 `X-Tenant-Id`（仅当请求头存在时注入）写入 `RequestContext` 的 `tenant_id` 字段（`set_tenant_id` / `get_tenant_id`，基于 contextvars，随 asyncio 任务自动传递）；
- **出站（服务间调用）**：`FeignClient` 自动透传 `X-Tenant-Id`/`X-Scope` 等上下文请求头（上下文无值则跳过注入，不抛错），保证多服务链路租户上下文不丢失；
- **跨线程/异步任务**：用 `RequestContext.snapshot()` / `restore(snapshot)` 显式携带（线程池场景 contextvars 不自动传递）。

```python
from web_infra.infra.context import RequestContext

tid = RequestContext.get_tenant_id()      # 空串表示无租户上下文
RequestContext.set_tenant_id("t1001")     # 测试/内部任务场景手动设置
```

## 3. TenantGuard：租户守卫

`TenantGuard`（`web_infra.capabilities.db.tenant_guard`）是数据访问层租户上下文校验的统一入口：

| 方法 | 行为 |
| ---- | ---- |
| `current_tenant()` | 返回当前租户；无租户返回 `NO_TENANT`（`"no-tenant"`）占位，**不抛错** |
| `require_tenant(tenant_id=None, strict=False)` | 显式指定或从请求上下文取租户；有值则返回；无值时 `strict=True` 抛 E2-PERM-000（403），否则返回 `no-tenant` 占位 |

`NO_TENANT = "no-tenant"` 是全局统一的无租户占位（tenant_guard.py），兼容单租户/非租户场景，配合 `strict` 开关使用。

```python
from web_infra.capabilities.db.tenant_guard import TenantGuard

# 取当前租户（无租户返回 no-tenant，不抛错）
tid = TenantGuard.current_tenant()

# 强隔离：无租户上下文直接 403
tid = TenantGuard.require_tenant(strict=True)

# 显式指定租户 + 强隔离
tid = TenantGuard.require_tenant(tenant_id="t1001", strict=True)
```

## 4. TenantAwareMixin：租户感知模型

业务 ORM 模型继承 `TenantAwareMixin`（SQLAlchemy 声明式模型），自动获得：

- **`tenant_id` 列**：`VARCHAR(64)`、`NOT NULL`、默认单列索引，注释明确"联合索引首列，禁止 NULL"（`__init_subclass__` 惰性注入，延迟导入 SQLAlchemy）；
- **联合索引声明辅助**：`__tenant_compound_indexes__` 声明以 `tenant_id` 为首列的联合索引列名，`tenant_indexes()` 生成 `Index`，业务模型在 `__table_args__` 中展开使用。

```python
from sqlalchemy import Index, String
from sqlalchemy.orm import DeclarativeBase, mapped_column
from web_infra.capabilities.db.tenant_aware_mixin import TenantAwareMixin


class Base(DeclarativeBase):
    pass


class Order(TenantAwareMixin, Base):
    """订单（租户感知模型）"""

    __tablename__ = "orders"
    # 联合索引声明（首列必须是 tenant_id）
    __tenant_compound_indexes__ = [("tenant_id", "biz_id")]
    # 联合索引在类体内手写声明（等价的自动生成方式见下方说明）
    __table_args__ = (Index("idx_orders_tenant_biz_id", "tenant_id", "biz_id"),)

    id: Mapped[int] = mapped_column(primary_key=True)
    biz_id: Mapped[str] = mapped_column(String(32))
    # tenant_id 列由 TenantAwareMixin 自动注入（VARCHAR(64) NOT NULL + 单列索引），业务不要重复声明


# tenant_indexes() 按 __tenant_compound_indexes__ 生成以 tenant_id 为首列的等价联合索引
# （类定义后调用；类体内无法直接引用类名，故 __table_args__ 中按上方手写 Index 声明）：
#   Order.tenant_indexes() -> [Index('idx_orders_tenant_biz_id', 'tenant_id', 'biz_id')]
```

> 多租户规范 §8 后端红线：业务代码**禁止**裸写 `AND tenant_id = ?` / `where(tenant_id == ...)`——租户条件由 `TenantQueryFilter` 统一注入（原因：手写拼接容易漏、容易造成跨租户数据泄漏，且与自动注入的 INSERT 填充产生语义冲突）。

## 5. TenantQueryFilter：SQL 条件自动注入

`TenantQueryFilter`（`web_infra.capabilities.db.tenant_query_filter`）是共享库+租户列模型的注入引擎，基于 SQLAlchemy 事件：

| 事件 | 注入行为 |
| ---- | ---- |
| `do_orm_execute`（SELECT） | 查询目标含租户模型（`TenantAwareMixin` 子类或显式注册模型）时，自动附加 `where(tenant_id == 当前租户)` |
| `do_orm_execute`（UPDATE/DELETE） | 目标表为租户模型表时，重写语句附加 `where(tenant_id == 当前租户)`（按表名匹配，兼容 ORM 包装语句） |
| `before_flush`（INSERT） | 新对象 `tenant_id` 为空自动填充当前租户；**strict 模式**下对象已有值且与当前租户不一致 → 抛 E2-PERM-000（跨租户写入禁止） |
| `before_flush`（对象级 DELETE） | strict 模式下校验删除对象归属租户，越权删其他租户数据 → 抛 E2-PERM-000 |

行为细节：

- `register_model(model)`：未继承 `TenantAwareMixin` 但含 `tenant_id` 字段的模型显式注册（返回 self 可链式）；
- `install(session_factory)`：挂载到会话工厂（同步/异步均可，SQLAlchemy 事件统一触发），引擎初始化后经 `MySQLDatabase.install_tenant_filter` 自动挂载；
- `require_context()`：会话创建入口校验——strict 模式无租户上下文时在**创建阶段**即被拒绝（E2-PERM-000），不必等到执行 SQL；
- 无租户上下文时：strict 抛 E2-PERM-000，兼容模式（默认）用 `no-tenant` 占位（即隔离到 no-tenant 命名空间，不与任何真实租户数据串扰）。

```python
from web_infra.capabilities.db.tenant_query_filter import TenantQueryFilter

# 手动装配（Application 启用 app.tenant.enabled 后自动完成，业务一般无需手写）：
filter_ = TenantQueryFilter(strict=True)          # 强隔离
filter_.register_model(SomeLegacyModel)           # 可选：非 Mixin 模型显式注册
mysql_db.install_tenant_filter(filter_)           # 挂载到数据源会话工厂（引擎初始化后自动生效）

# 会话创建入口校验（strict 无租户上下文时抛 E2-PERM-000）：
current = filter_.require_context()
```

> `tenant_column_name` 参数可自定义租户字段名（默认 `tenant_id`，规范要求全系统统一，建议不修改）。

## 6. 独立库路由：TenantDatabaseRouter + DatabaseManager

### 6.1 TenantDatabaseRouter

`TenantDatabaseRouter`（`web_infra.capabilities.db.database_router`）实现租户 → 数据源名的解析：

- **显式映射优先**：`mapping: {租户: 数据源名}`（`register(tenant_id, datasource_name)` 可动态维护）；
- **未命中按命名模板生成**：`pattern` 默认 `"tenant_{tenant_id}"`（对齐规范 §4 Schema 命名统一模板）；
- **租户注销**：`unregister(tenant_id)` 移除显式映射（幂等）；按模板生成的租户无映射可移除，需配合 `DatabaseManager.unregister_tenant` 释放连接完成实际回收（规范 T-4：租户删除/归档后 24h 内路由注销 + 连接释放 + 缓存失效）；`registered_tenants()` 返回显式映射租户列表（注销审计）。

```python
from web_infra.capabilities.db.database_router import TenantDatabaseRouter

router = TenantDatabaseRouter(
    mapping={"t1001": "db_tenant_001"},   # 大租户走独立库
    pattern="tenant_{tenant_id}",          # 其余租户按模板解析数据源名
)
router.register("t1002", "db_tenant_002")  # 动态注册显式映射
name = router.route("t1001")               # "db_tenant_001"
name = router.route("t9999")               # "tenant_t9999"（模板生成）
router.unregister("t1001")                 # 注销显式映射
```

### 6.2 DatabaseManager.route：租户权限校验

`DatabaseManager`（`web_infra.capabilities.db.database_manager`）持有多个数据源连接，`route(tenant_id)` 按路由解析并返回目标连接。**数据源切换必须经租户权限校验**（整改 T-1，多租户规范 §2）：

- 当前请求上下文无租户 → 抛 `PermException`（E2-PERM-000，403）；
- 当前上下文租户与目标租户不一致 → 抛 `PermException`（越权切换数据源被拒绝）；
- 校验可用构造参数 `enforce_tenant_check=False` 关闭（仅供测试/内部无上下文路径）；
- 未配置路由（`router=None`）或路由目标数据源不存在 → `RuntimeError`（快速失败）。

```python
db: DatabaseManager  # 装配产物（app.state.db），见 [数据库](./06-数据库.md)

# 按租户路由取连接（自动校验当前上下文租户 == 目标租户）
conn = db.route(RequestContext.get_tenant_id())
async with conn.session() as session:
    ...

# 按名获取（不路由，多数据源场景）
async with db.session("audit") as session:
    ...

# 租户注销（租户删除/归档流程）：注销路由映射 + 释放连接 + 缓存失效（可注入 cache_invalidator 按租户前缀清缓存）
await db.unregister_tenant("t1001")
```

### 6.3 配置多租户独立库

```yaml
app:
  db:
    # 方式一：混合多数据源（app.db.instances，每实例带 type 字段，支持异构数据库并存）
    instances:
      default: { type: mysql, host: 127.0.0.1, port: 3306, database: app_main }
      db_tenant_001: { type: mysql, host: 127.0.0.1, port: 3306, database: app_tenant_001 }
    # 方式二（向后兼容）：app.db.mysql.instances 全 MySQL 多源
    # mysql:
    #   instances:
    #     db_tenant_001: { host: ..., database: app_tenant_001 }
    router:
      mapping: { t1001: db_tenant_001 }   # 显式映射（优先）
      pattern: "tenant_{tenant_id}"       # 未命中按模板生成数据源名
```

装配规则（`Application._build_db`）：`app.db.instances` 非空 → 按 `DatabaseManager` 装配（每实例带 `type`，缺省 mysql）；否则 `app.db.mysql.instances` 非空 → 同样走 `DatabaseManager`（向后兼容）；否则按 `app.db.type` 单源装配。路由配置 `app.db.router.mapping` / `app.db.router.pattern` 只在多源场景生效。

## 7. 缓存 Key 租户隔离（TenantKeyBuilder）

规范 T-3（整改）：**租户相关数据缓存必须经 `TenantKeyBuilder` 生成含租户维度的 Key，禁止裸用 `CacheKeyBuilder` 存储租户数据**（否则跨租户缓存串扰）。

```python
from web_infra.capabilities.cache.tenant_key_builder import TenantKeyBuilder

# 1. 模板方式：模板必须包含 {tenant_id} 占位符，否则抛 ParamException
key = TenantKeyBuilder.build(
    "web:common:v1:order:{tenant_id}:detail:{order_id}",
    # tenant_id 缺省自动从 RequestContext 取
)

# 2. 三段式便捷方法：{prefix}:{tenant_id}:{biz_key}
key = TenantKeyBuilder.build_with_tenant(
    prefix="web:common:v1:order",
    tenant_id=None,            # None 自动取上下文租户
    biz_key="detail:1001",
)

# 3. 强隔离场景：无租户上下文直接报错（require_tenant=True）
key = TenantKeyBuilder.build_with_tenant(
    prefix="web:common:v1:order",
    tenant_id=None,
    biz_key="detail:1001",
    require_tenant=True,       # 无租户抛 ParamException
)
```

行为要点：

- 租户缺省从 `RequestContext.get_tenant_id()` 读取；无租户时默认用 `no-tenant` 占位（`NO_TENANT_PLACEHOLDER`），标识该 Key 未绑定租户，避免跨租户串扰；
- `require_tenant=True` 时无租户上下文抛 `ParamException`（多租户强隔离场景必须使用）；
- 与 `CacheKeyBuilder`（`web:{module}:v1:{biz}` 模板，见 [07-缓存](./07-缓存.md)）的关系：租户数据在 `CacheKeyBuilder` 模板基础上叠加租户段，由 `TenantKeyBuilder` 统一完成。

## 8. 启用配置与装配

```yaml
app:
  tenant:
    enabled: false      # 默认关闭，需业务显式开启
    strict: true        # 启用后默认强隔离：无租户上下文拒绝数据访问（E2-PERM-000）
```

装配行为（`Application._setup_tenant`，`app.tenant.enabled=true` 时）：

1. 构造 `TenantQueryFilter(strict=strict)`；
2. 若 `db` 为 `DatabaseManager`：遍历 `db.names`，对每个提供 `install_tenant_filter` 能力的数据源挂载过滤器；否则对单数据源调用 `install_tenant_filter`；
3. 按能力判断（`install_tenant_filter`）而非具体类型装配，兼容 MySQL/PostgreSQL 等任何提供租户过滤能力的数据库实现（`DatabaseFactoryInterface` 扩展能力）。

> `strict: true` 是默认值——启用多租户即默认强隔离（无租户上下文抛 E2-PERM-000）；非严格场景（如单租户系统只是借用 X-Tenant-Id 分流）可显式 `strict: false`，无租户时数据收敛到 `no-tenant` 命名空间。

## 9. 与其他能力的联动

### 9.1 搜索引擎：索引前缀租户隔离

`app.search` 启用后（见 [17-搜索引擎](./17-搜索引擎.md)）：

- 真实索引名 `{index_prefix}_{tenant_id}_{index_name}`（如 `web_t1001_products`），租户维度前缀隔离，禁止跨租户命中；
- `tenant_id` 为可选参数：显式传则按租户隔离；缺省读请求上下文（`TenantGuard.current_tenant()`）；再无回落 `no-tenant` 占位（单租户所有数据收敛同一命名空间）；
- 命名约束：`tenant_id` 与 `index_name` 均不能含下划线 `_`（命名空间分隔符保留），否则抛 `ValueError`。

```python
engine = SearchEngineRegistry.create("elasticsearch", Settings())
await engine.create_index("t1001", "products", mappings={...})   # 真实索引 web_t1001_products
await engine.search(None, SearchQuery(keyword="苹果", index_name="products"))  # 缺省读上下文租户
```

### 9.2 AI 能力：配额/计费租户维度

`web_infra.capabilities.ai`（见 [15-AI模型网关](./15-AI模型网关.md)）：

- **配额租户维度必查**：`ModelGateway._check_quota` 对 `"tenant"` 维度调用 `check_and_consume("tenant", tenant_id or "no-tenant")`——租户维度必查、缺省 `no-tenant` 占位，user/scene 维度仅在有值时参与；
- **用量计费**：`_consume_usage` 记录用量时透传 `tenant_id` 聚合维度（AI-3）；
- **AI 缓存租户隔离**：`AiCache._build_key` 生成 `{prefix}{tenant_id}:{digest}`，租户维度明文可见、参与哈希隔离；
- **模型访问策略**：`ModelAccessPolicy` 的 `check_access(model_name, tenant_id, user_id, scene)` 中 `tenant_id` 可选（None/空串表示无租户主体，单租户系统；策略实现可忽略或按全局放行）。

### 9.3 数据库读写分离 / 其他

- 多租户独立库模式与读写分离（`read_replica=True`，见 [06-数据库](./06-数据库.md)）正交，按数据源实例各自配置；
- `mysql.instances`（多租户独立库）为向后兼容旧格式，新项目推荐 `app.db.instances` 统一写法。

## 10. 适用场景决策建议与常见坑

### 决策建议

| 场景 | 推荐模型 |
| ---- | ---- |
| 通用 SaaS，租户多、单租户数据量小 | 共享库 + 租户列（`TenantAwareMixin` + `TenantQueryFilter`，strict=true） |
| 单租户数据量大 / 大客户专属实例 / 强合规物理隔离 | 独立库路由（`app.db.instances` + `app.db.router`），并为该租户注册显式 mapping |
| 混合：默认共享库、少数大租户独立库 | 两种模型共存：默认租户走共享库，大租户在 `router.mapping` 注册独立库 |
| 单租户系统（无多租户需求） | 不启用 `app.tenant.enabled`；搜索引擎/AI 自动回落 `no-tenant` 命名空间，行为不变 |

### 常见坑

- **漏继承 Mixin / 漏注册模型**：不继承 `TenantAwareMixin` 且未 `register_model` 的表不会被注入租户条件——跨租户数据泄漏源。规范要求租户相关表全部继承 Mixin。
- **手写租户条件**（规范 §8 红线）：与自动注入叠加会导致条件重复/语义冲突；INSERT 手填 `tenant_id` 在 strict 模式下还会被 before_flush 拦截（跨租户写入禁止）。
- **strict 语义**：strict=true 时**任何**无租户上下文的数据访问都抛 E2-PERM-000（含创建会话阶段），内部任务/定时任务等无请求上下文路径需先 `RequestContext.set_tenant_id(...)` 或显式传租户。
- **多实例/多线程**：`RequestContext` 基于 contextvars，线程池任务需 `snapshot()/restore()` 手动传递租户，否则租户上下文丢失后 strict 模式直接 403。
- **缓存裸 Key**：租户数据缓存必须走 `TenantKeyBuilder`，否则 TTL 命中跨租户数据（规范 T-3）。
- **租户注销流程**：删除/归档租户后 24h 内调用 `DatabaseManager.unregister_tenant(tenant_id)`（路由注销 + 连接释放 + 缓存失效，业务可注入 `cache_invalidator` 按 `web:*:{tenant_id}:*` 前缀清缓存）；模板租户（无显式映射）同样适用。
- **ES 索引命名**：租户标识与索引名不能含下划线，否则抛 `ValueError`（命名空间分隔符保留，防拼接歧义）。
