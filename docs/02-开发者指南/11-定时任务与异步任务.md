# 定时任务与异步任务

> 周期性任务（Outbox 投递、关单扫描）和一次性异步任务（发通知、跑报表）怎么可靠地跑？框架提供两套正交能力：
> `TaskScheduler`（asyncio 定时调度：分布式锁防重、超时中断、失败退避、执行记录）与 `TaskExecutor`（异步任务执行器：
> 状态机 + 心跳 + 死任务扫描 + 共享线程池）。本文覆盖两者全部机制与真实装配用例。

## 1. 是什么

| 模块 | 组件 | 职责 |
| ---- | ---- | ---- |
| `web_infra.capabilities.schedule` | `ScheduledTask` / `TaskScheduler` | 周期性任务调度：注册/启动/停止/手动触发、分布式锁防多实例重复、超时中断、失败退避与自动暂停、执行记录持久化 |
| `web_infra.capabilities.task` | `TaskExecutor` / `TaskStatus` / `TaskRecord` / `TaskRecordStoreInterface` / `SharedThreadPool` | 一次性异步任务：状态机流转、心跳与死任务扫描、乐观锁终态保护、有界共享线程池 |

两者关系：调度器可选注入 `record_store`（复用 task 模块的 `TaskRecordStoreInterface`）把每次执行写成 `TaskRecord`，满足审计留存 ≥90 天；调度器的 `SKIPPED` / `FAILED` 等状态与异步任务状态机共用 `TaskStatus`。

## 2. 定时任务 TaskScheduler

### 2.1 ScheduledTask 定义

```python
@dataclass(frozen=True)
class ScheduledTask:
    name: str                      # 全局唯一标识（如 order:job:message-outbox-publish，命名含模块归属）
    module: str                    # 模块归属（禁止匿名任务）
    interval_seconds: float        # 执行间隔（秒）
    handler: Callable[[], Awaitable[None]]   # 异步执行函数
    description: str = ""          # 任务描述（禁止匿名任务）
    timeout_seconds: float | None = None     # 执行超时（秒），超时中断并计失败
    consecutive_failure_limit: int = 3       # 连续失败阈值：达到自动暂停并告警
```

`name` / `module` / `interval_seconds` 为必填（`register` 校验，非法抛 `ValueError`），重复 `name` 注册覆盖并告警。

### 2.2 核心 API

| 方法 | 行为 |
| ---- | ---- |
| `register(task)` / `register_task(name, module, interval_seconds, handler, ...)` | 注册任务（便捷版按参数构造） |
| `start()` | 启动调度循环（后台 asyncio 任务，须在运行中的事件循环内调用） |
| `await stop()` | 停止调度循环并等待退出 |
| `await run_once(name)` | 手动触发执行一次（不等待间隔，返回是否成功） |
| `is_paused(name)` / `resume(name)` | 查询暂停 / 手动恢复（连续失败自动暂停后由运维介入） |
| `next_interval(task_name, base_interval)` | 计算带失败退避的下一触发间隔 |

### 2.3 调度机制（源码事实）

- **调度循环**：`_schedule_loop` 每 `tick_seconds`（默认 0.5s）轮询 `run_all_due()`——到期判断叠加失败退避，串行 `await` 执行（单实例内天然不重叠）；
- **分布式锁防多实例重复**：构造传 `lock_factory: (task_name) -> 异步上下文管理器`（规范 §23.2，锁带租约自动释放）。多实例部署时每轮执行前 `tryLock`，**锁竞争超时跳过本轮**（记为 `SKIPPED`「lock timeout」，**不累计连续失败、不触发误暂停**——整改 S23-2）；
- **执行超时中断**：`timeout_seconds` 配置后经 `asyncio.wait_for` 包裹，超时中断并计为失败；
- **连续失败自动暂停与退避**：失败累计 `consecutive_failures`，达到 `consecutive_failure_limit`（默认 3）自动暂停（`_paused`）并告警；自动触发间隔按指数退避拉长：

```
next_interval = base_interval + min(retry_backoff_base × 2^n, max_retry_backoff)
              = base + min(30 × 2^n, 3600)          # 默认退避基数 30s、上限 3600s
```

成功执行后连续失败清零，回到原间隔；
- **执行记录持久化**：注入 `record_store`（`TaskRecordStoreInterface`）后每次执行写一条 `TaskRecord`（任务名/模块进 `payload`，`submit_at`/`start_at` 为本次触发时间，`status` 为 SUCCESS/FAILED/SKIPPED，`error` 记失败/跳过原因）；未注入不记录（向后兼容），写入失败仅告警不影响执行。

### 2.4 最小示例

```python
import asyncio
from web_infra import TaskScheduler

scheduler = TaskScheduler()   # 单实例场景不取锁

async def cleanup_old_files() -> None:
    ...  # 业务逻辑

scheduler.register_task(
    name="file:job:cleanup-expired",
    module="file",
    interval_seconds=3600.0,
    handler=cleanup_old_files,
    description="清理过期文件",
    timeout_seconds=60.0,
    consecutive_failure_limit=3,
)

scheduler.start()          # FastAPI startup 中调用
# ... 应用运行 ...
await scheduler.stop()     # FastAPI shutdown 中调用
```

多实例 + 分布式锁 + 执行记录（lock_factory 用框架韧性组件的 Redis 分布式锁 `DistributedLock`，见 [14-韧性设计](./14-韧性设计.md) 中的分布式锁 SPI）：

```python
from web_infra import TaskScheduler
from web_infra.capabilities.task import InMemoryTaskRecordStore
from web_infra.infra.resilience.distributed_lock import DistributedLock

def lock_factory(task_name: str):
    # async 上下文管理器：租约 30s 到期自动释放；tryLock 获取超时（默认 3s）抛 TimeoutError
    return DistributedLock(redis_client, key=f"task:{task_name}")

scheduler = TaskScheduler(
    lock_factory=lock_factory,                     # 多实例仅单实例执行；锁竞争超时跳过本轮（SKIPPED）
    record_store=InMemoryTaskRecordStore(),        # 每次执行写 TaskRecord（多实例换 MySQL/Redis）
)
```

## 3. 异步任务 TaskExecutor

### 3.1 任务状态机（TaskStatus）

```
PENDING ──> RUNNING ──> SUCCESS / FAILED        （执行结果）
                │
                └──> DEAD                       （心跳超时，scan_dead_tasks 判定）
PENDING ──> REJECTED                            （线程池队列满拒绝）
PENDING ──> SKIPPED                             （调度跳过：锁竞争/任务暂停）
```

终态：`SUCCESS` / `FAILED` / `DEAD` / `REJECTED` / `SKIPPED`（`is_terminal`，终态不可再流转）。枚举提供 `get_code()`（入库存 code）/ `of(code)`（反查，未知抛 ValueError）/ `description`（中文描述）。

### 3.2 核心 API 与机制

| 方法 | 行为 |
| ---- | ---- |
| `await submit(coro_factory, *, task_id=None, payload=None)` | 在当前事件循环调度执行（FastAPI 异步场景）；`coro_factory` 返回协程的工厂（延迟创建，便于捕获提交期异常）；返回初始 `PENDING` 的 `TaskRecord` |
| `submit_in_thread(coro_factory, *, task_id=None, payload=None)` | 同步上下文（脚本/测试无事件循环）提交，由共享线程池执行（`asyncio.run` 新循环）；**队列满抛 `RejectedExecutionError`** |
| `await heartbeat(task_id)` | 任务协程内周期性刷新心跳，防被误判死亡（非 RUNNING 返回 False） |
| `await scan_dead_tasks()` | 扫描心跳超时的 RUNNING 任务置 `DEAD`（`dead_threshold_seconds` 默认 600 秒），返回死亡列表 |
| `close()` | 关闭共享线程池并注销监控（应用停机时调用） |

- **执行流程**（`_run`）：确保记录已入库 → 校验 `PENDING`（非 PENDING 放弃本次调度）→ 置 `RUNNING`（写 `start_at`/`heartbeat_at`）→ 运行协程 → 置终态；
- **乐观锁终态保护**：`TaskRecordStoreInterface.update` 采用乐观锁——仅当存储中 `version` 与记录一致才写入并自增；不一致返回 `False`（视为终态已被并发保护）。`InMemoryTaskRecordStore` 还加了终态守卫：**当前终态不允许回退到非终态**（防并发/旧快照覆盖）；
- **死任务扫描**：心跳基准 `heartbeat_at or start_at or submit_at`，超时置 `DEAD` + `end_at` + `error="heartbeat timeout"`。

### 3.3 任务记录模型（TaskRecord）

```python
class TaskRecord(BaseModel):
    task_id: str                  # uuid4().hex 默认生成
    status: TaskStatus = PENDING
    submit_at: float              # unix 秒
    start_at: float | None
    end_at: float | None
    heartbeat_at: float | None
    version: int = 0              # 乐观锁版本号
    error: str = ""
    payload: dict[str, Any]       # 业务元信息

    @property
    def duration_seconds(self) -> float | None: ...   # 未结束返回 None
```

存储 SPI：`save` / `load` / `update`（乐观锁）/ `list_all`（死任务扫描遍历）。默认 `InMemoryTaskRecordStore`（`threading.Lock` 保护，`max_records` 默认 10000，超限按 `submit_at` 淘汰最旧记录）。

### 3.4 异步任务示例

```python
import asyncio
from web_infra import TaskExecutor, TaskRecord, InMemoryTaskRecordStore, TaskStatus

store = InMemoryTaskRecordStore()
executor = TaskExecutor(record_store=store, max_workers=8, dead_threshold_seconds=600)
record: TaskRecord = None

async def send_notification() -> None:
    for _ in range(3):
        await asyncio.sleep(1)
        await executor.heartbeat(record.task_id)     # 长任务周期性刷新心跳
    print("notification sent")

async def main():
    global record
    record = await executor.submit(lambda: send_notification(), payload={"type": "order-paid"})
    print(record.status)              # TaskStatus.PENDING

    await asyncio.sleep(4)
    done = await store.load(record.task_id)          # 经记录存储查询任务最新状态
    print(done.status)                               # 通常 TaskStatus.SUCCESS

    dead = await executor.scan_dead_tasks()          # 无心跳的 RUNNING 任务 -> DEAD
    executor.close()                                 # 停机：关闭共享线程池

asyncio.run(main())
```

同步上下文提交（后台脚本）：

```python
try:
    executor.submit_in_thread(lambda: send_notification())   # 无事件循环场景，共享线程池执行
except RejectedExecutionError:
    ...  # 队列满：丢弃/降级/告警（拒绝策略，不阻塞调用方）
```

## 4. 共享线程池 SharedThreadPool

统一共享线程池（规范 §14.4：禁止业务侧每次 `new ThreadPoolExecutor`），`SharedThreadPool(ThreadPoolExecutor)` 增强两点：

1. **进程内单例**：`get_shared_thread_pool(max_workers=8, max_queue_size=None)` 懒创建（`threading.Lock` 保护），参数仅**首次**生效；`shutdown_shared_pool()` 显式关闭，关闭后下次获取自动重建新实例；`TaskExecutor` 内部池即框架共享池；
2. **有界队列 + 拒绝策略**（规范 §14.2 有界队列（峰值×2））：`ThreadPoolExecutor` 原生队列无界不暴露 maxsize，此处用容量 = `max_queue_size`（默认 = `max_workers × 2`）的 gate 队列做提交前 `put_nowait` 哨兵检查——**队列已满抛 `RejectedExecutionError`（不阻塞调用方）**；worker 取走任务后释放名额；池关闭后提交抛 `RuntimeError`；提交失败自动释放占位名额防泄漏。

```python
from web_infra.capabilities.task.shared_thread_pool import (
    get_shared_thread_pool, shutdown_shared_pool, RejectedExecutionError,
)

pool = get_shared_thread_pool(max_workers=8, max_queue_size=16)
try:
    pool.submit(worker_fn, *args)
except RejectedExecutionError as e:
    logger.warning("queue_full %s", e)   # 按拒绝策略处理：丢弃/降级/告警
shutdown_shared_pool()                   # 应用停机时调用
```

> 线程池任务协程运行在**独立事件循环**中：任务内不要触达 `asyncio.Lock` 保护的内存存储（缓存/幂等/outbox 等），`asyncio.Lock` 不跨线程互斥；应改用 `threading.Lock` 或分布式实现（`InMemoryTaskRecordStore` 已使用 `threading.Lock` 正因如此）。

## 5. 真实用例：Outbox 定时任务装配

`register_outbox_tasks`（`web_infra.capabilities.mq.outbox.outbox_task_registrar`）是框架内置的定时任务真实装配入口：注册两个任务——轮询投递 `message-outbox-publish`（默认 5s 间隔）与已发送记录清理 `message-outbox-cleanup`（默认 3600s 间隔），模块归属 `mq.outbox`。默认不启用（由业务 yml 开关决定是否调用），不侵入 Application 装配。

```python
from web_infra import TaskScheduler
from web_infra.capabilities.mq import MqConfig, register_outbox_tasks

scheduler = TaskScheduler()                       # 多实例可注入 lock_factory 防重复投递
register_outbox_tasks(
    scheduler,
    store,                                        # OutboxStoreInterface（如 MysqlOutboxStore）
    publisher,                                    # MessagePublisherInterface
    config=MqConfig(
        max_retry=3,
        retry_backoff_seconds=30,                 # 投递失败指数退避
        dead_letter_topic="web-dlq-topic",
    ),
    publish_interval_seconds=5.0,
    cleanup_interval_seconds=3600.0,
    batch_size=100,
    retain_days=7,                                # 已发送记录保留 7 天
)
scheduler.start()                                 # FastAPI startup
# ...
await scheduler.stop()                            # FastAPI shutdown
```

order-service 脚手架完整装配（`services/order-service/src/order_service/main.py` 为真实示例）：`_build_outbox_scheduler` 读取 `app.mq.outbox` 段参数构造调度器，startup 处理器里 `register_service` → `scheduler.start()`，shutdown 处理器里 `deregister_service` → `await scheduler.stop()`。业务侧通用装配模式：

```python
# FastAPI 生命周期
async def _startup() -> None:
    await register_service(application, "order-service", 8002)   # 注册中心引导
    scheduler.start()                                            # 启动定时调度循环

async def _shutdown() -> None:
    await deregister_service(application)
    await scheduler.stop()
```

## 6. 配置项一览

`TaskScheduler` / `TaskExecutor` / `SharedThreadPool` 均为构造参数配置（无专属 yml 段），业务在装配代码中传参：

| 组件 | 参数 | 默认值 |
| ---- | ---- | ------ |
| `TaskScheduler` | `lock_factory` | `None`（单实例不取锁） |
| | `tick_seconds` | `0.5`（调度轮询间隔） |
| | `record_store` | `None`（不记录执行） |
| | `retry_backoff_base_seconds` | `30.0`（失败退避基数） |
| | `max_retry_backoff_seconds` | `3600.0`（失败退避上限） |
| `ScheduledTask` | `timeout_seconds` | `None`（不超时） |
| | `consecutive_failure_limit` | `3` |
| `TaskExecutor` | `record_store` | 必传 |
| | `max_workers` | `8` |
| | `dead_threshold_seconds` | `600`（心跳超时判定死亡） |
| | `max_queue_size` | `None`（默认 = `max_workers × 2`） |
| `SharedThreadPool` | `max_workers` | `8` |
| | `max_queue_size` | `None`（默认 = `max_workers × 2`） |
| `InMemoryTaskRecordStore` | `max_records` | `10000`（`<=0` 不限制） |

Outbox 定时任务关联配置段（`app.mq.outbox`，业务 yml 声明，框架默认值见 `application.default.yml`）：

```yaml
app:
  mq:
    outbox:
      enabled: true              # 仅供业务配置参考（框架不自动注册定时任务）
      max_retry: 3
      retry_backoff_seconds: 30
      dead_letter_topic: web-dlq-topic
      publish_interval_seconds: 5
      cleanup_interval_seconds: 3600
      retain_days: 7
```

## 7. 常见坑

1. **`start()` 必须在运行中的事件循环内调用**：`asyncio.create_task` 无运行循环会报错；FastAPI 放在 startup 事件处理器里最稳妥。
2. **锁竞争超时 ≠ 失败**：`SKIPPED`（lock timeout）不累计连续失败、不触发误暂停——监控告警要区分 SKIPPED 与 FAILED，避免误报。
3. **`retries`/退避只作用于自动调度**：`run_once` 手动触发不受退避影响（`next_interval` 仅用于 `run_all_due` 到期判断）。
4. **单实例内任务串行执行**：调度循环逐个 `await`，某任务执行时长超过自身间隔不会重叠（下一轮 `_last_run` 更新后才再次到期）；但**长任务会阻塞整轮调度**，耗时任务建议拆分或 `timeout_seconds` 兜底。
5. **线程池任务与 asyncio.Lock 不兼容**：`submit_in_thread` 的任务协程跑在独立事件循环，不要触达 `asyncio.Lock` 保护的内存存储；`InMemoryTaskRecordStore` 用 `threading.Lock` 正是为支持这条路径。
6. **乐观锁更新返回 False 即放弃**：`update` 失败说明版本已被并发修改（终态已保护），调用方不要再覆盖写；`_run` 中置 RUNNING 失败直接返回。
7. **死任务扫描阈值**：`dead_threshold_seconds` 默认 600 秒，长任务必须周期 `heartbeat`，否则会被误判 DEAD；心跳只在 RUNNING 状态生效。
8. **共享池参数仅首次生效**：多实例 `TaskExecutor` 用不同 `max_workers` 不会生效（进程内单例首次创建决定），需要差异化请在进程启动早期先 `shutdown_shared_pool()` 再重建。
9. **多实例执行记录**：`InMemoryTaskRecordStore` 是进程内状态，多实例/审计留存场景需扩展 MySQL/Redis 实现（SPI 相同）。
