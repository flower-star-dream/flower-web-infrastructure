# 事件总线（进程内 ApplicationEvent / @event_listener / AFTER_COMMIT）

> 对标 Spring `ApplicationEvent` / `@EventListener` 的**进程内**事件总线：同一服务内解耦（业务动作发生后，其他模块以「监听」方式响应，而非直接调用）。作为框架**核心能力，始终装配**（无 `app.event.enabled` 门控），`app.state.event`（EventBus）恒可用。**区别于 MQ（跨服务通信）**——本能力不跨进程，见文末与 MQ 的边界表。

## 1. 是什么

`web_infra.capabilities.event`（源码见 `src/web_infra/capabilities/event/`）围绕「进程内发布/订阅」提供：

| 组件 | 职责 |
| ---- | ---- |
| `ApplicationEvent` | 事件基类：子类声明 `event_name`（默认由类名推出 snake_case），`payload` 携带数据，`trace_id` 自动绑定 |
| `event_listener` | 声明式监听器装饰器：装饰函数即注册进 `EventListenerRegistry` |
| `EventListener` | 监听器契约：`event_name` / `handler` / `order` / `async_mode` / `parent_type` |
| `EventListenerRegistry` | 类级监听器注册表：按事件名聚合，order 升序执行 |
| `EventBus` | 统一发布入口：`publish` / `publish_after_commit`（事务提交后触发） |
| `EventPublisher` | 底层发布器：按 order 分发匹配监听器，异常隔离（fail_fast） |
| `EventErrorCode` | 事件总线错误码（`E4-EVNT-200`/`E4-EVNT-201`） |

**何时用**：同一服务内希望把「发生了什么」与「如何响应」解耦时（如订单创建后发送通知、更新库存、记录审计）。**何时不用**：需要跨服务、需要持久化、需要广播到多个实例的场景——应走 MQ（见 §10 边界表）。

## 2. 装配与配置（app.event）

事件总线是框架**核心能力，始终装配**（无 `app.event.enabled` 门控）：`create_app` 即装配 `EventBus` 并挂 `app.state.event`（源码：`application.py::_setup_event`），业务无需任何开启配置即可直接发布。仅 `app.event.fail_fast` 可配：

```yaml
app:
  event:
    fail_fast: false    # 单监听器异常是否阻断其余（false=记录日志继续分发）
```

- `app.event.fail_fast`：默认 `false`。`true` 时单监听器异常向上抛、阻断其余监听器；`false` 时记录 warning 日志继续分发（异常隔离）。

```python
app = create_app()              # 事件总线始终装配，无需开启配置
event_bus = app.state.event     # EventBus 实例（恒可用）

# 直接发布
await app.state.event.publish(OrderCreatedEvent(order_id="1001"))

# 或测试切片中直接构造
from web_infra import EventBus
bus = EventBus(fail_fast=False)
```

> `EventBus` 构造签名：`EventBus(*, fail_fast=False)`。

## 3. 框架内置事件

框架在既定时点自动发布一批**内置事件**，订阅方式与业务自定义事件完全一致（经 `@event_listener(事件类型)` 即可监听）：

| 类别 | 事件类（事件名） | 发布时点 | payload 要点 |
| ---- | ---- | ---- | ---- |
| 生命周期 | `ApplicationStartingEvent`（`application_starting`） | `_lifespan` 启动最前（清理上下文/接管 uvicorn 访问日志后、扩展 startup 之前） | `settings` / `app` |
| 生命周期 | `ApplicationReadyEvent`（`application_ready`） | 全部启动完成（容量采样启动后、`yield` 接受请求前） | `settings` / `app` |
| 生命周期 | `ApplicationStoppingEvent`（`application_stopping`） | `yield` 恢复后（收到停机信号）、释放资源前 | `settings` / `app` |
| 生命周期 | `ApplicationStoppedEvent`（`application_stopped`） | `_shutdown()` 完成后（最末尾） | `settings` / `app` |
| HTTP | `HttpRequestStartedEvent`（`http_request_started`） | 请求处理开始（解析真实客户端 IP 与 TraceId 后、`call_next` 前），由 `LoggingMiddleware` 发布 | `trace_id` / `method` / `path` / `query` / `client_ip` |
| HTTP | `HttpRequestCompletedEvent`（`http_request_completed`） | 请求处理结束（成功或异常）在 `finally` 统一发布 | `trace_id` / `method` / `path` / `status_code` / `duration_ms` / `is_error` |
| 认证 | `AuthTokenIssuedEvent`（`auth_token_issued`） | JWT 签发成功（`JWTUtil.generate_token`） | `user_id` / `username` / `jti` / `login_type` |
| 认证 | `AuthTokenRevokedEvent`（`auth_token_revoked`） | 指定 token 登出/撤销成功（`JWTUtil.invalidate_token` 的 revoke 返回 True） | `user_id` / `jti` |
| 认证 | `AuthLoginSuccessEvent`（`auth_login_success`） | 三方登录绑定成功并签发自有 JWT（`SocialLoginService.login` 已绑定分支） | `provider` / `user_id` / `openid` |
| 认证 | `AuthLoginFailedEvent`（`auth_login_failed`） | 三方登录整体抛异常（`SocialLoginService.login` 的 try/except） | `provider` / `reason` |

```python
from web_infra import event_listener, ApplicationStartingEvent, HttpRequestCompletedEvent

@event_listener(ApplicationStartingEvent)     # 订阅启动事件
async def on_starting(event):
    settings = event.payload["settings"]
    ...

@event_listener(HttpRequestCompletedEvent)    # 订阅 HTTP 完成事件
async def on_http_done(event):
    if event.payload["is_error"]:
        ...
```

这些事件多由**无 `app` 引用的框架组件**（`JWTUtil` / `SocialLoginService` / `LoggingMiddleware`）在既定时点发布，因此框架额外提供模块级总线持有器与发布入口：`set_current_event_bus` / `get_current_event_bus` / `clear_current_event_bus` / `publish_event`（`create_app` 装配时自动 `set_current_event_bus(event_bus)`，应用停机后清空）。业务侧一般直接用 `app.state.event.publish(...)`，无需也不应改走模块级入口；模块级入口仅供无 `app` 引用的框架组件向当前总线发布事件。

## 4. 事件：ApplicationEvent

```python
from web_infra import ApplicationEvent

class OrderCreatedEvent(ApplicationEvent):
    event_name = "order.created"     # 显式声明；缺省由类名推导（OrderCreatedEvent -> order_created_event）

    # 构造：payload 携带业务数据，trace_id 缺省取 RequestContext
    def __init__(self, order_id: str, **kwargs):
        super().__init__(payload={"order_id": order_id}, **kwargs)
```

**真实接口签名**：

```python
class ApplicationEvent:
    event_name: ClassVar[str] = ""                      # 子类覆盖；缺省由类名推导
    def __init__(self, payload: Any = None, *, trace_id: str | None = None) -> None: ...
    @classmethod
    def resolve_event_name(cls) -> str: ...             # 显式声明优先，否则由类名推导
```

要点：

- `payload`：业务数据；`trace_id`：发布时自动绑定请求链路（取 `RequestContext.get_trace_id()`），随事件透传（无需手动传）。
- `published_at`：事件创建时刻（perf_counter，monotonic，供排序/审计）。
- **事件名**：子类显式声明 `event_name`；未声明时由类名用 `_default_event_name` 推导（CamelCase → snake_case，如 `OrderCreatedEvent` → `order_created_event`）。

## 5. 监听器：@event_listener / EventListener

```python
from web_infra import event_listener

@event_listener("order.created")              # 按事件名（str）注册
async def on_order_created(event):
    order_id = event.payload["order_id"]
    ...

@event_listener(OrderCreatedEvent, order=10, async_mode=True)   # 按事件类型注册（自动推导 event_name + parent_type）
def on_order_created_by_type(event):          # async_mode=False 时同步（handler 返回 awaitable 则内部 await）
    ...
```

**真实接口签名**：

```python
def event_listener(
    event: str | type[ApplicationEvent],
    *,
    order: int = 0,
    async_mode: bool = False,
) -> Callable[[Callable[..., R]], Callable[..., R]]: ...
```

`EventListener` 契约：

```python
@dataclass
class EventListener:
    event_name: str
    handler: Callable
    order: int = 0
    async_mode: bool = False
    parent_type: type[ApplicationEvent] | None = None

    def supports(self, event: ApplicationEvent) -> bool: ...   # event_name 精确匹配 或 isinstance 匹配父类
    async def handle(self, event: ApplicationEvent) -> Any: ...  # async_mode=False 时同步调用（内部 await 若返回 awaitable）
```

要点：

- `event` 传 `str`：按事件名精确匹配；传事件类型：自动取 `resolve_event_name()` 并设 `parent_type`（isinstance 匹配，可监听事件基类）。
- `order`：同事件多监听器执行顺序（升序）。
- `async_mode`：**决定异步分发**。`False`（默认）时同步调用 handler（若返回 awaitable 则内部 await）；`True` 时以 `await handler(event)` 分发。
- 装饰函数**原样返回**（不影响函数本身），仅作注册副作用。

## 6. 发布：EventBus.publish / publish_after_commit

```python
from web_infra import EventBus

# OrderCreatedEvent 为自定义事件（见 §4）
bus = EventBus()                              # EventBus(fail_fast=False)
event = OrderCreatedEvent(order_id="1001")

await bus.publish(event)                      # 发布即触发：同步/异步监听器统一分发
await bus.publish_after_commit(event)         # 事务提交成功后才触发（回滚不触发）
```

**真实接口签名**：

```python
class EventBus:
    def __init__(self, *, fail_fast: bool = False) -> None: ...
    async def publish(self, event: ApplicationEvent) -> None: ...                     # 发布即触发
    async def publish_after_commit(self, event: ApplicationEvent) -> None: ...        # 事务提交后触发
```

- `publish`：立即把事件分发给匹配监听器（同步/异步统一，按 order 排序，异常隔离与否由 fail_fast 决定）。
- `publish_after_commit`：**仅在事务内调用**，把「发布该事件」注册为 after_commit 回调（`transaction_synchronization.register_listener`），事务提交成功后触发；**事务回滚则不触发**（事件不会发布）。

## 7. AFTER_COMMIT 语义与数据源接入

`publish_after_commit` 依赖框架的**事务同步回调**（`transaction_synchronization`，对标 Spring `TransactionSynchronization.afterCommit`）：回调栈经 ContextVar 承载（asyncio 场景安全），在**事务真正提交成功后**触发（而非提交前），避免「通知发了但事务回滚」。每次提交后清空回调栈（防跨事务累积触发）。

**三处数据源的 owner 提交路径均已接入**（源码事实，回调触发点）：

| 数据源 | 提交收尾点 | 触发方式 |
| ---- | ---- | ---- |
| `SessionScopeMixin._finalize_commit` | `await raw.commit()` 成功后 | `await trigger_after_commit()`（异步触发，可 await 回调） |
| `MySQLDatabase._finalize_commit`（覆盖父类，追加长事务审计） | `await raw.commit()` 成功后 | `await trigger_after_commit()` |
| `SqliteSessionFactory`（同步参考实现） | owner 连接 `conn.commit()` 成功后 | `trigger_after_commit_sync()`（同步触发） |

**SQLite 同步回调约束**：同步触发入口 `trigger_after_commit_sync()` 对**返回 awaitable 的回调跳过并告警**（`after_commit_sync_skip_awaitable`）——同步上下文不强行跑 asyncio（避免在非事件循环环境报错）。因此：**在 SQLite 场景使用 `publish_after_commit` 时，监听器应保持 `async_mode=False`（同步 handler）**，否则 after_commit 回调为 async 时会被跳过。

> `transaction_synchronization` 提供 `register_callback` / `register_listener` / `trigger_after_commit` / `trigger_after_commit_sync`；回调异常隔离，不阻断主链路。

## 8. 注册表：EventListenerRegistry

```python
from web_infra import EventListenerRegistry, EventListener, ApplicationEvent

EventListenerRegistry.register(listener)        # 登记监听器（按 event_name 聚合；相同 handler 覆盖）
EventListenerRegistry.match(event)             # 返回匹配该事件的监听器（event_name 精确 + 父类 isinstance），按 order 升序
EventListenerRegistry.unregister(event_name, handler)   # 注销指定监听器（不存在时静默）
EventListenerRegistry.clear()                  # 清空全部监听器（测试/生命周期清理用）
```

要点：

- 类级注册、全局装配（与 `AspectRegistry` / `CacheBackendRegistry` 同风格，类级锁保护并发 register）。
- `match` 跨 bucket 归并后仍按 `order` 升序（精确匹配优先父类）。
- 同事件名、同 handler 重复注册时**覆盖**（避免重复执行）。

## 9. 错误码（E4-EVNT-*）

| 枚举 | code | HTTP | 说明 |
| ---- | ---- | ---- | ---- |
| `EventErrorCode.LISTENER_NOT_FOUND` | `E4-EVNT-200` | 422 | 事件监听器未注册 |
| `EventErrorCode.REGISTER_CONFLICT` | `E4-EVNT-201` | 422 | 事件监听器重复注册 |

均为 `category="E4"`（业务域类，规范 §4，http_status=422，log_level=WARNING）。完整错误码说明见 [统一响应与错误码](./04-统一响应与错误码.md) 的「事件总线错误码」小节。

## 10. 与 MQ 的边界

| 维度 | 进程内事件总线（本能力） | 消息队列 MQ（`capabilities.mq`） |
| ---- | ---- | ---- |
| 跨服务 | ✗（仅同一进程/服务内） | ✔（跨服务/跨实例） |
| 跨进程 | ✗ | ✔（需 broker，如 RocketMQ / 内存队列） |
| 持久化 | ✗（事件在内存，进程退出即失） | ✔（可配置持久化 + Outbox 保证可靠投递） |
| 广播 | 服务内订阅者 | 可广播到多服务/多实例 |
| 可靠性 | 尽力送达（进程内） | 至少一次/精确一次（视实现） |
| 解耦目标 | 服务内模块解耦、同步链路拆分 | 服务间解耦、异步/削峰 |
| 典型场景 | 订单创建后发通知、更新库存、记审计 | 下单后通知下游订单服务、同步搜索索引、跨服务事件驱动 |

> **何时用哪个**：服务内、非持久、可容忍进程重启丢失 → 事件总线；跨服务、需持久/重试/顺序保证 → MQ。两者可结合：服务内用事件总线解耦，需要跨服务时在监听器里发布 MQ 消息。

## 11. 最小可运行示例

```python
# events.py —— 定义事件与监听器
from web_infra import ApplicationEvent, event_listener

class OrderCreatedEvent(ApplicationEvent):
    event_name = "order.created"

@event_listener("order.created", order=10)         # 同步监听器
def notify_user(event):
    order_id = event.payload["order_id"]
    send_notification(user, order_id)              # 同步响应

@event_listener(OrderCreatedEvent, order=20, async_mode=True)   # 异步监听器
async def update_stock(event):
    order_id = event.payload["order_id"]
    await stock_service.deduct(order_id)
```

```python
# service.py —— 业务侧发布
from web_infra import transactional, EventBus
from web_infra.capabilities.db.transaction_propagation import current_session

@transactional()
async def create_order(order: dict):
    session = current_session()
    order_id = await session.execute("INSERT INTO t_order ...")
    # 事务提交成功后触发（回滚则不触发）
    await app.state.event.publish_after_commit(OrderCreatedEvent(order_id=order_id))
    return order_id

# 或发布即触发
await app.state.event.publish(OrderCreatedEvent(order_id="1001"))
```

## 12. 常见坑

1. **在事务外调用 publish_after_commit**：它注册为 after_commit 回调，若无外层事务同步上下文则缺省最近一次提交后触发；无任何提交入口时行为不确定（源码注释标注了运行时可能抛 `RuntimeError` 的边界）。**务必在 `@transactional` / `db.session()` 事务内调用**。
2. **SQLite 用 async 监听器 + publish_after_commit**：同步触发入口对 awaitable 回调跳过并告警，事件不发布。SQLite 场景请保持 `async_mode=False`。
3. **async_mode 与 handler 类型不匹配**：`async_mode=True` 时 `handle` 会 `await` handler 返回值；若 handler 是同步函数，返回非 awaitable 会被原样返回（不报错但语义不符）。按 handler 类型选择 `async_mode`。
4. **同 handler 重复注册不报错**：`EventListenerRegistry.register` 用 `handler is listener.handler` 判重并覆盖，不会重复触发；但不同 handler 同名事件会多次触发（注意 order）。
5. **跨服务误用**：进程内事件不会广播到其他服务实例，跨服务请改用 MQ（见 §10 边界表）。
