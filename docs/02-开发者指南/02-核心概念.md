# 核心概念

> 本文讲清楚框架的**总体设计**，帮助你理解「为什么这么用」。涉及：三层结构、配置驱动装配、配置体系、SPI 模式、能力依赖链、扩展点。
> 建议阅读顺序：先通读本文，再按需翻阅能力篇。

---

## 1. 三层结构

`web_infra` 包按职责分三层（v1.0.0 破坏性整改后）：

```
web_infra/
├── core/          # 内核：应用编排（Application / create_app）+ 扩展点（Capability / Extension）
├── infra/         # 技术底座：所有能力共用的基础（result / error / constants / context /
│                  #   logging / resilience / monitoring / web / config 本地配置 / utils）
└── capabilities/  # 能力层：业务能力（ai / cache / db / mq / storage / registry / security /
                   #   payment / search / state_machine / task / schedule / http / loadbalance / config 配置中心）
```

设计意图：

| 层 | 职责 | 被谁依赖 |
| -- | ---- | -------- |
| core | 把一切「组织起来」：加载配置、校验能力、装配组件、编排生命周期 | 所有能力 |
| infra | 提供「地基工具」：响应、错误码、日志、上下文、韧性、监控 | 所有能力 |
| capabilities | 提供「业务能力」，相互独立、可裁剪 | 业务代码 |

> **导入约定**：顶层导出保持不变——`from web_infra import Result, create_app` 照常使用；子包路径已迁移至三层，如 `web_infra.payment` → `web_infra.capabilities.payment`、`web_infra.result` → `web_infra.infra.result`。

## 2. 配置驱动装配

框架的核心哲学是 **Spring Boot 风格**：业务代码不手动初始化组件，而是**声明配置，框架自动装配**。

```python
from web_infra import create_app

app = create_app()   # 读取配置 → 校验 → 装配组件 → 注册端点 → 返回 FastAPI 实例
```

`create_app` 内部（`Application.build()`）的固定装配顺序：

1. 日志（格式与输出通道）
2. 能力校验与启用（`app.capabilities.enabled`）
3. 组件装配（cache / db / mongo / storage / mq / registry / ai，挂到 `app.state.<name>`）
4. 扩展点装配（`app.extensions.enabled`）
5. Web 层（全局异常处理 + 声明式中间件）
6. 多租户过滤（`app.tenant.enabled`）
7. 诊断端点守卫（/metrics /capacity）
8. 容量评估（`app.capacity.enabled`）
9. 健康检查三端点 + /metrics

组件经 `app.state` 访问：

```python
cache = app.state.cache     # 缓存后端
db = app.state.db           # DatabaseManager
storage = app.state.storage
mq = app.state.mq
registry = app.state.registry
ai = app.state.ai           # ModelGateway（未启用 AI 时为 None）
```

**组件切换只改配置**：`app.cache.type: memory → redis`，业务代码不变。

## 3. 配置体系

### 3.1 加载优先级（从高到低）

| 优先级 | 来源 | 说明 |
| ------ | ---- | ---- |
| 1 | 代码 dict 覆盖层 | `create_app({"app.name": "x"})` 显式传入 |
| 2 | 环境变量 | `app.db.host` → `APP_DB_HOST`（点号转大写+下划线） |
| 3 | 项目根 `.env` | 包导入时自动加载，不覆盖已存在的环境变量 |
| 4 | 项目 `application.yml` | 相对当前工作目录 |
| 5 | 框架默认 `application.default.yml` | 包内自带，全量默认值 |

> `application.default.yml` 是全部默认配置的**权威来源**（禁止在代码里再嵌默认值）；敏感项统一用 `${ENV:default}` 占位符引用环境变量。

### 3.2 读取配置

```python
from web_infra import Settings

Settings.get("app.db.mysql.host")          # 取字符串
Settings.get_int("app.cache.redis.max_connections")
Settings.get_bool("app.tenant.enabled")
Settings.get_required("app.payment.wechat.mchid")  # 缺失抛 ConfigError
```

### 3.3 敏感信息

- 支持 `enc:` 前缀的 Fernet 加密值，密钥来自环境变量 `CONFIG_ENCRYPT_KEY`（生成方法见 [配置管理](../03-运维指南/02-配置管理.md)）；
- 支持 `env:VAR_NAME` 引用（AI 模型 API Key 等），禁止明文落盘。

## 4. SPI 模式：接口 + 默认实现 + 生产实现

框架里**几乎每个能力**都遵循同一套模式：

```
抽象接口（Protocol/ABC）           ← 业务只依赖它
   ├── 默认实现（内存/本地，开箱即用，单机/测试）
   └── 生产实现（Redis/Nacos/RocketMQ/MinIO/ES…，延迟导入）
注册表（*Registry）                ← 按 type 名装配，未注册快速失败
```

```python
# 业务只依赖抽象接口
from web_infra import CacheBackendInterface

def biz(cache: CacheBackendInterface): ...
```

切换实现 = 改一行配置：

```yaml
app:
  cache: { type: redis }   # 原来是 memory
  mq:    { type: rocketmq }
  storage: { type: minio }
  registry: { type: nacos }
```

装配期按注册表按名创建，未注册的 type 抛 `ConfigError`（快速失败，不带到线上）。

### SPI 注册表命名空间与内置默认保护

领域注册表（如 `CacheBackendRegistry`、`DatabaseRegistry`）继承统一 `SpiRegistry` 基类，提供两类命名空间：

- `framework`：框架内置默认实现（如 cache 的 `memory`/`redis`）。**同名覆盖默认拒绝**，需显式 `overwrite=True`，防止业务无感覆盖框架核心实现。
- `user`：业务自定义实现（默认命名空间）。同名注册可在装配时覆盖框架默认（配置 `type` 选择 + `user` 命名空间同名覆盖），但不会破坏 `framework` 命名空间的原始实现。

`get` 解析顺序：`ns:name` 显式限定 > `user` 命名空间 > `framework` 命名空间；同命名空间按 `priority` 取最高者（为后续默认实现优先级排序预留）。

```python
# 业务实现（默认 user 命名空间），同名覆盖装配选择但不破坏框架默认
CacheBackendRegistry.register("memory", lambda settings: MyCacheBackend())
```

### SPI 注册表扩展：实例引用 / 运行时切换 / 策略组合器 / 命名空间粒度

`SpiRegistry` 基类在「注册工厂 + 命名空间 + 优先级」之外，还提供下述扩展能力（源码见 `src/web_infra/core/spi/spi_registry.py`），各级领域注册表（`CacheBackendRegistry` / `DatabaseRegistry` 等）继承即获得。

**实例旁路引用（`register_instance` / `get_instance`）**

- `register_instance(name, instance, *, namespace=None, overwrite=False)`：登记一个**已实例化**对象而非工厂；与 `register` 同享命名空间/同名规则（`'ns:name'` 限定命名空间、同名未 `overwrite` 抛 `ValueError`）。
- `get_instance(name)`：按「显式 `ns:name` > `user` > `framework`」顺序解析实例，未命中抛 `KeyError`。
- 典型用途：**代码共享、实例隔离**——同一 `name` 可在 `framework` 与 `user` 各自注册**不同实例**（如框架默认缓存后端与业务自研缓存客户端同名并存，实例互不干扰）。

```python
# 同一实例名，framework / user 各自注册不同实例（代码共享、实例隔离）
CacheBackendRegistry.register_instance("mycache", MyCacheBackend(), namespace="framework")
CacheBackendRegistry.register_instance("mycache", MyRedisCacheBackend(), namespace="user")
assert CacheBackendRegistry.get_instance("mycache") is not None
```

**`type: ref:<实例名>` 装配（实例引用）**

`create_app` 的 `_resolve_component` / `SpiRegistry.resolve` 对以 `ref:` 开头的 type 直接走 `get_instance` 返回已注册实例（**不再调用工厂**）。由此可在配置里引用任意**已注册实例**（含业务启动期手工构造的），无需工厂二次拼装。

```yaml
app:
  cache:
    type: ref:mycache   # 直接引用已注册实例 mycache（经 register_instance 注册）
```

**运行时动态切换（`activate` / `deactivate`）**

- `activate(name, target)`：把纯名 `name` 的解析**重定向**到 `target`（`target` 可为 `'ns:name'` 或纯名），**不重启**即可更换生效实现。
- `deactivate(name)`：移除切换，恢复默认解析（不存在时静默）。
- 语义要点：`activate` **仅影响纯名解析**；显式 `ns:name` **绕过**切换表（仍可拿到底层实现）；解析顺序中 `user` 命名空间默认胜出。

```python
CacheBackendRegistry.activate("memory", "user:mycache")   # 将 memory 重定向到业务实例
CacheBackendRegistry.deactivate("memory")                 # 恢复默认解析
```

**策略组合器回退（`fallback`）**

- `fallback(primary, fallback)`：返回组合工厂——先按 `primary` 解析并实例化；抛 `Exception` 才按 `fallback` 解析并实例化（主策略失效自动回退）。

```python
CacheBackendRegistry.fallback("redis", "memory")          # 主 redis 失败自动回落 memory
```

#### 附：可运行示例（示例实现 `MyCacheBackend` 由业务定义）

```python
from web_infra.capabilities.cache.cache_backend_registry import CacheBackendRegistry

# 1) 实例旁路注册（默认 user 命名空间），供 ref: 装配引用
my_cache = MyCacheBackend()
CacheBackendRegistry.register_instance("mycache", my_cache)

# 2) ref: 装配：配置 app.cache.type: ref:mycache，_resolve_component/resolve 直接返回原实例（不调用工厂）
assert CacheBackendRegistry.resolve("ref:mycache") is my_cache

# 3) 运行时切换：把 memory 的纯名解析重定向到 user:mycache（不重启更换实现）
CacheBackendRegistry.activate("memory", "user:mycache")
assert CacheBackendRegistry.get_instance("memory") is my_cache   # 纯名按当前切换态解析
CacheBackendRegistry.deactivate("memory")                        # 恢复默认解析

# 4) 策略组合器回退：主 redis 失效自动回落 memory
CacheBackendRegistry.fallback("redis", "memory")
```

> **兼容性**：`register(name, factory)` 旧签名保留（追加 keyword-only `overwrite` / `namespace` / `priority`），对既有调用向后兼容，不引入平行体系。

## 5. 能力依赖链（Capability）

部分能力**没有业务实现就没有意义**，框架用「能力注册表」显式表达依赖：

```
user（用户系统，业务实现）
  └→ authn（认证）
        └→ authz（鉴权）
              └→ pay（支付）
```

- `app.capabilities.enabled: [pay]` → 框架**自动带出** authz → authn → user，并按拓扑序导入对应框架模块；
- 校验：未知能力 / 循环依赖在装配期抛 `ConfigError`；
- 契约能力（如 `user`）没有框架模块，由**业务提供实现**，框架只校验依赖关系。

其余能力（ai / mq / storage / registry / config / db / cache / search）无前置依赖，默认按需启用或关闭。

## 6. 扩展点（Extension）：插拔式集成

能力注册表管理「资源工厂」，扩展注册器管理「插件协议对象」：

```python
from web_infra import ExtensionPoint, ExtensionRegistry

ExtensionRegistry.register(ExtensionPoint(
    name="my_plugin",
    description="示例插件",
    requires=(),                          # 前置扩展点
    build=lambda options, ctx: MyPlugin(),  # 装配期构建（ctx 含 settings/components）
    startup=lambda inst: inst.start(),    # 生命周期钩子（同步/异步均可）
    shutdown=lambda inst: inst.stop(),
))
```

- `app.extensions.enabled: [my_plugin]` 声明即启用；
- 启动时按拓扑序执行 startup，停机时**逆序**执行 shutdown（先于框架组件关闭）；
- 典型用途：新数据源、第三方 SDK 客户端、资源预加载。

## 7. 惰性导入与 extras

框架遵循**最小安装原则**：

| 行为 | 说明 |
| ---- | ---- |
| 可选组件延迟导入 | `import web_infra` 不加载 sqlalchemy/redis/mongo 等（`from web_infra import MySQLConfig` 首次访问才导入） |
| `from web_infra import *` | 按已安装依赖动态扩展 `__all__`（最小安装不触发惰性导入） |
| extras 按需安装 | `[mysql] [redis] [mongo] [nacos] [rocketmq] [storage] [es] [rag] [pdf] [migrate]`，场景包 `[min-monolith] [min-microservice] [all]` |
| 支付为可选能力 | 不随顶层导出，需显式 `from web_infra.capabilities.payment import ...` |

## 8. 生命周期（Lifespan）

| 阶段 | 顺序 |
| ---- | ---- |
| 启动 | 清上下文 → 关闭 uvicorn 原生访问日志（若装配 LoggingMiddleware）→ 同步 AI 模型配置 → 扩展点 startup（拓扑序）→ 容量采样启动 |
| 停机 | 容量采样停止 → 扩展点 shutdown（逆拓扑序）→ 组件 close（优雅停机：等待窗口 `app.graceful_shutdown_wait_seconds`，生产建议 ≥10s） |

## 9. 中间件的声明式启用

```yaml
app:
  web:
    middlewares:
      trace_id: {}                       # 默认引入，必须最后声明
      auth:
        enabled: true
        whitelist: ["/health", "/metrics"]
      idempotency:
        enabled: true
        store_type: redis                # memory | redis
        ttl_seconds: 86400
      rate_limit:
        enabled: true
        qps: 100.0
      security_headers:
        enabled: true
```

顺序约束（Starlette 后声明者先执行）：`trace_id` 最先执行生成链路 ID → `auth` 注入身份 → `idempotency` 最后（身份已就绪、按用户隔离幂等键）。
