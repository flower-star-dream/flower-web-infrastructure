## 1. 能力总览

| 能力 | 入口 | 说明 |
| ---- | ---- | ---- |
| 重试 | `retry` 装饰器 + `RetryConfig` | 同步/异步通用；仅对瞬时错误重试（`_is_transient`）；**仅幂等接口允许重试** |
| 熔断 | `CircuitBreaker` + `CircuitBreakerConfig` | 错误率 50% + 慢调用 80%（超 1s）双维度；CLOSED→OPEN→HALF_OPEN 状态机；fallback 降级 |
| 限流（服务内） | `TokenBucketRateLimiter` | 令牌桶平滑限流，QPS 补充 + burst 突发容量 |
| 限流（统一入口） | `RateLimitMiddleware` | 按路径/用户维度，429 + Retry-After + E1-RATE-000 |
| 分布式锁 | `DistributedLock` | SET NX PX 原子加锁 + Lua 原子释放；带租约与获取超时；`async with` |
| API 幂等 | `IdempotencyMiddleware` + `IdempotencyStoreInterface` | Idempotency-Key 头；占用/摘要比对/重放/409/202；内存与 Redis 双存储 |
| 缓存 Key 模板 | `CacheKeyBuilder` | `web:{module}:v1:{biz}` 统一模板（锁/幂等键等） |

## 2. 重试（retry）

### 2.1 是什么

`retry` 装饰器（`web_infra.infra.resilience.retry`）同时支持同步与异步函数，指数退避重试。

- **默认配置** `RetryConfig(max_retries=2, base_delay=0.5, backoff_factor=2.0)`：最多重试 2 次（共执行 3 次），退避间隔 0.5s → 1s；
- **判定规则**：仅对满足 `retry_on(exc)` 的异常重试，默认 `_is_transient` 判定为 `ConnectionError` / `TimeoutError` / `httpx.TimeoutException` / `httpx.TransportError`（网络错误、连接失败、超时等确定未产生副作用的场景，httpx 延迟导入兼容无 httpx 环境）；
- **红线**（规范 §7.2）：**仅幂等接口允许重试**——非幂等（下单、扣款、转账）调用方应显式评估幂等性后再使用，重试造成重复副作用由调用方负责。

### 2.2 代码示例

```python
import httpx
from web_infra.infra.resilience.retry import retry, RetryConfig

# 同步
@retry()   # 默认最多重试 2 次
def fetch_sync(url: str) -> dict:
    return httpx.get(url, timeout=5).json()

# 异步（装饰器自动识别协程函数）
@retry(RetryConfig(max_retries=3, base_delay=0.2, backoff_factor=2.0))
async def fetch_async(url: str) -> dict:
    async with httpx.AsyncClient(timeout=5) as client:
        resp = await client.get(url)
        resp.raise_for_status()
        return resp.json()

# 自定义重试判定：只对 5xx / 特定状态码重试
def retry_on_5xx(exc: BaseException) -> bool:
    return isinstance(exc, httpx.HTTPStatusError) and exc.response.status_code >= 500

@retry(retry_on=retry_on_5xx)
async def fetch_with_custom_rule(url: str) -> dict:
    ...
```

> 注意：重试不会自动与熔断协同——重试的是"单次远程调用"，熔断保护的是"资源整体"。组合用法见 [第 7 节](#7-组合用法)。

## 3. 熔断（CircuitBreaker）

### 3.1 是什么

`CircuitBreaker`（`web_infra.infra.resilience.circuit_breaker`）按错误率 + 慢调用比例双维度统计，自动熔断与恢复（规范 §7.4）。

**配置项全默认值**（`CircuitBreakerConfig`，`dataclass(frozen=True)`）：

| 配置项 | 默认 | 说明 |
| ---- | ---- | ---- |
| `failure_rate_threshold` | `0.5` | 错误率阈值（50%） |
| `slow_call_rate_threshold` | `0.8` | 慢调用比例阈值（80%） |
| `slow_call_duration_threshold` | `1.0` | 慢调用判定阈值（秒） |
| `wait_duration_in_open_state` | `30.0` | OPEN 状态等待时间（秒） |
| `permitted_calls_in_half_open_state` | `5` | HALF_OPEN 允许试探调用数 |
| `minimum_number_of_calls` | `10` | 评估熔断所需最小样本数 |
| `window_size` | `20` | 滑动窗口容量（deque maxlen） |

**状态机**：`CLOSED`（关闭，正常放行）→ 错误率/慢调用比例超阈值且样本 ≥10 → `OPEN`（拒绝执行）→ 等待 30s 到期 → `HALF_OPEN`（放行 ≤5 个试探请求）→ 试探成功回 `CLOSED`（清空窗口）/ 失败回 `OPEN`（重新计时）。状态枚举 `CircuitBreakerState`（`closed/open/half_open`，含 `get_code()/of()/description`）。

**fallback 降级**：构造时传入 `fallback(*args, **kwargs)`（与受保护调用同参）——熔断开启或调用异常时返回兜底结果；未配置 fallback 时抛 `CircuitOpenError`（OPEN 状态）或保持原始异常（调用异常）。同步调用配同步回调；异步调用可配同步或异步回调。

**调用入口**：`execute(func, ...)`（同步；传入异步函数抛 TypeError，须用 `execute_async`）、`execute_async(func, ...)`。两者内部都做：`can_execute()` 判空 → 执行 → `_record(success, slow)` 评估。

### 3.2 代码示例

```python
from web_infra.infra.resilience.circuit_breaker import CircuitBreaker
from web_infra.infra.resilience.circuit_breaker_config import CircuitBreakerConfig
from web_infra.infra.resilience.circuit_open_error import CircuitOpenError

# 受保护资源：第三方支付下单接口
cb = CircuitBreaker(
    name="pay-gateway",
    config=CircuitBreakerConfig(
        failure_rate_threshold=0.3,
        wait_duration_in_open_state=60.0,
    ),
    fallback=lambda *a, **kw: {"fallback": True},   # 熔断/异常时降级
)

# 同步调用
result = cb.execute(create_payment, order_id="1001")

# 异步调用
async def create_payment_async(order_id: str) -> dict:
    ...

result = await cb.execute_async(create_payment_async, order_id="1001")

# 不配 fallback：熔断开启抛 CircuitOpenError（RuntimeError 子类），调用方自行捕获
cb2 = CircuitBreaker("pay-gateway")
try:
    cb2.execute(create_payment, order_id="1001")
except CircuitOpenError:
    ...  # 快速失败处理
```

> 状态机线程安全（`threading.Lock` 保护，纯内存临界区）；`HALF_OPEN` 下的取消（`asyncio.CancelledError`）也会记录结果回收试探许可，防止半开状态永久泄漏。

## 4. 限流（TokenBucketRateLimiter + RateLimitMiddleware）

### 4.1 TokenBucketRateLimiter（服务内限流）

令牌桶（`web_infra.infra.resilience.token_bucket_rate_limiter`）：`qps` 决定每秒补充速率，`burst` 决定桶容量（允许突发量），请求消耗令牌、令牌不足即拒绝。

- `RateLimitConfig` 默认：`qps=1000.0`、`burst=100.0`；
- `try_acquire(tokens=1.0)`：取令牌（线程安全），不足返回 False；`acquire_or_false()` 单令牌便捷方法；
- `retry_after_seconds(tokens=1.0)`：计算补足指定令牌所需等待秒数（供 429 Retry-After 响应头；当前足够返回 0；qps≤0 返回无穷大）。

```python
from web_infra.infra.resilience.rate_limit_config import RateLimitConfig
from web_infra.infra.resilience.token_bucket_rate_limiter import TokenBucketRateLimiter

limiter = TokenBucketRateLimiter("order-submit", RateLimitConfig(qps=10, burst=20))
if not limiter.try_acquire():
    raise CommonErrorCode.RATE_LIMITED.to_exception(message="请稍后再试")
```

### 4.2 RateLimitMiddleware（统一入口限流）

`RateLimitMiddleware`（`web_infra.infra.web.rate_limit_middleware`）在统一入口按维度令牌桶限流：

- **维度** `key_by`：`"path"`（method:path）或 `"user"`（user_id + method:path；未登录/匿名自动退化为路径维度）；
- **参数缺省**：`qps=100`、`burst=50`、`max_limiters=10000`（user 维度每个用户一个桶，超限按 LRU 淘汰最久未访问的桶，防内存无限增长）；
- **超限响应**：HTTP 429 + `Retry-After` 响应头 + 统一 Result 结构（`E1-RATE-000` "请求过于频繁"）；
- **顺序约束**：用户维度限流需在统一鉴权**之后**执行（依赖 auth 注入的 user_id）——yml 中 `rate_limit` 须声明于 `auth` **之前**（Starlette 后声明者在外层先执行，先声明者在内层后执行）；未启用统一鉴权时读不到用户身份，自动退化为路径维度。

```yaml
app:
  web:
    middlewares:
      rate_limit:            # 默认 yml 未内置 rate_limit 段，需业务显式声明
        enabled: true
        qps: 100
        burst: 50
        key_by: user         # path（默认）| user（需在 auth 之前声明，见上）
      auth:
        enabled: true
        whitelist: ["/health", "/metrics", "/docs"]
      trace_id: {}           # 必须最后声明（最先执行）
```

> `RateLimitConfig` 默认 qps=1000 是**类内默认值**；`RateLimitMiddleware` 构造缺省 qps=100/burst=50（中间件视角更保守）。两者语义不同：前者是组件默认参数，后者是中间件入口缺省。

## 5. 分布式锁（DistributedLock SPI）

分布式锁经 SPI 抽象（`DistributedLockInterface`）+ 注册表（`DistributedLockRegistry`）按 `app.lock.type` 装配，内置 **redis** 与 **redisson** 两种实现：

| 实现 | 特性 | 适用 | 说明 |
| ---- | ---- | ---- | ---- |
| `redisson`（默认） | 看门狗自动续期 + **可重入** | 多实例、临界区可能超过租约 | 自研 Redisson 风格 RLock：后台任务每 lease_time/3 续期（`asyncio.shield` 保护取消安全），同任务可重复 acquire（引用计数），置 `app.lock.type=redisson` |
| `redis` | 静态租约 SET NX PX + Lua 释放 | 临界区远小于租约 | 保留原 `DistributedLock` 语义（`DistributedLock(redis, key, lease_time)`，兼容旧用法） |

### 5.1 配置（默认 redisson）

```yaml
app:
  lock:
    enabled: false        # 默认关闭：不装配锁（不强制 Redis）；需显式 true 并配置 Redis 客户端
    type: redisson        # redisson（默认，看门狗续期+可重入）/ redis（静态租约）
    cache_max_size: 10000  # 锁实例缓存上限（方案甲按 Key 复用实例）：超出按 LRU 淘汰最久未用
    # redis:             # 未启用 cache.type=redis 时，独立 Redis 连接（锁复用 cache 客户端则无需配置）
    #   host: 127.0.0.1
    #   port: 6379
    #   db: 0
```

锁默认关闭（对齐 ai/mongo/capacity 惯例），显式 `enabled: true` 并配置 Redis 客户端后装配；`enabled=true` 但无 `cache.type=redis` 且未配 `app.lock.redis` 时快速失败（`ConfigError`）。锁复用 `cache` 组件 Redis 客户端（`cache.type=redis` 时），否则需独立 `app.lock.redis` 连接段。

### 5.2 用法（统一工厂，经 app.state.distributed_lock）

```python
lock_factory = app.state.distributed_lock     # (key, lease_time=30) -> 锁实例

# 推荐：async with（获取失败抛 TimeoutError）
async with lock_factory("order:1001", lease_time=30):
    ...  # 临界区：处理订单 1001

# 或显式 tryLock：
lock = lock_factory("order:1001", lease_time=30)
if await lock.acquire(wait_timeout=3):
    try:
        ...
    finally:
        await lock.release()
```

> **工厂缓存实例（方案甲）**：`app.state.distributed_lock` 工厂按完整锁 Key 缓存 `RedissonLock` 实例——**同一锁 Key 多个调用方拿到同一锁对象**。这是可重入判定成立的前提（同任务对同一锁 Key 重复 `acquire` 才判重入），也避免"同 Key 多实例"导致的锁语义分裂。锁释放后实例仍驻留，供后续同 Key 复用；若业务锁 Key 无限增长需考虑按释放清理（框架暂不自动做，YAGNI）。

或继承旧用法直连实现：`from web_infra.infra.resilience.redisson_lock import RedissonLock` / `from web_infra.infra.resilience import DistributedLock, RedissonLock`。

### 5.3 基础语义（两种实现共有：SET NX PX + Lua 释放）

`DistributedLock`（`web_infra.infra.resilience.distributed_lock`）与 `RedissonLock` 均基于 Redis 分布式锁（规范 §16.4：必须带租约/超时、tryLock），共同遵循：

- **加锁**：`SET key token NX PX(lease_time_ms)` 原子加锁——`token` 为每次 acquire 随机生成（`secrets.token_urlsafe(16)`），`NX` 保证互斥，`PX` 保证租约到期自动释放；
- **释放**：Lua 脚本原子操作，**仅持有者 token 匹配时删除**（防误删他人新持有的锁）；
- **获取超时**：`acquire(wait_timeout=3.0)` 尝试获取，最多等待 3s（每 50ms 重试一次），超时返回 False；
- **异步上下文管理器**：`async with lock:` 进入时未获取到锁抛 `TimeoutError`；退出自动 `release()`；
- **Key 模板**：`CacheKeyBuilder.DISTRIBUTED_LOCK = "web:common:v1:lock:{key}"`——构造时传入业务 Key（如 `"order:1001"`），完整 Redis Key 为 `web:common:v1:lock:order:1001`。

```python
from web_infra.infra.resilience.distributed_lock import DistributedLock

lock = DistributedLock(redis_client, key="order:1001", lease_time=30)  # 租约 30s

# 推荐：async with（获取失败抛 TimeoutError）
async with lock:
    ...  # 临界区：处理订单 1001

# 或显式 tryLock：
if await lock.acquire(wait_timeout=3):
    try:
        ...
    finally:
        await lock.release()
```

> 典型场景：定时任务防重复执行（`TaskScheduler` 内置分布式锁）、订单处理幂等、库存扣减、本地缓存重建防击穿。业务 Key 语义自解释（如 `"pay:refund:20260818001"`），勿塞无意义随机串。

### 5.4 redisson 实现特性（看门狗自动续期 + 可重入）

`redisson` 实现（`RedissonLock`，对标 Redisson RLock）在基础语义上叠加：

- **可重入**：同任务可重复 `acquire`（引用计数 +1），`release` 需成对递减；归零才真正删锁。可重入判定按 `lock_key` 维度隔离，不同锁互不误判——`_REENTRANT` 三元组 `(lock_key, token, count)` 记录持有者与引用计数，同任务对同一锁 Key 重复获取才判重入。
- **看门狗**：获取锁后启动后台任务每 `lease_time/3` 续期，避免静态租约到期导致临界区未完成被他人取锁；`release` 后取消。续期用 `asyncio.shield` 保护（取消不会中途打断续期）。
- **取消安全**：释放锁时先同步 `cancel` 看门狗 Task，再用 `asyncio.shield` 保护 Lua 删锁（即使当前任务被取消，删锁仍完整执行）；取消级联安全，最多等 `lease_time` 自然过期，**不误删他人锁、不死锁**。

### 5.5 停机清理

应用停机时框架调用 `shutdown_all_watchdogs()` 清理所有残留看门狗任务（`_lifespan` 停机段），避免孤儿续期导致死锁窗口永久化与 `Task was destroyed` 警告。

## 6. API 幂等（IdempotencyMiddleware）

### 6.1 是什么

`IdempotencyMiddleware`（`web_infra.infra.web.idempotency_middleware`）实现规范 §12.6 API 幂等键：

- **触发条件**：写方法 `POST/PATCH/PUT/DELETE` 且请求头携带 `Idempotency-Key`（header 名可自定义，默认 `Idempotency-Key`）；其余请求直接放行；
- **唯一约束**：`用户 + 幂等键`（`key = "idem:{user_id}:{idem_key}"`，按用户隔离，规范 §12.6 userId + Idempotency-Key 联合唯一）；
- **原子占用**：`store.try_occupy(key, ttl)` 首次返回 True（SETNX 语义），重复占用返回 False；
- **请求摘要**：`method + path + query + 请求体` 的 SHA-256（规范 §5.6 摘要算法，禁 MD5）；
- **重复请求三态**：
  - 已缓存结果且摘要一致 → 重放首次结果（HTTP 状态码 + 原业务 code 原样返回）；
  - 已缓存结果但摘要不一致 → HTTP 409（`E4-COMMON-001`，提示更换幂等键）；
  - 占用中（首个请求尚未处理完）→ HTTP 202（"幂等请求处理中，请稍后重试"）；
- **业务异常释放**：首个请求处理抛异常时 `store.release(key)` 释放占用，允许客户端用同键重试；
- **TTL**：结果保留时长默认 86400s（24h，覆盖重试窗口）；
- **存储 SPI**：`IdempotencyStoreInterface`（`try_occupy` / `set_result` / `get_result` / `release`；`IdempotencyResult(status_code, content_type, body, request_hash)`），内存与 Redis 双实现。

### 6.2 存储双实现

| 实现 | 场景 | 说明 |
| ---- | ---- | ---- |
| `InMemoryIdempotencyStore` | 单实例（默认） | `asyncio.Lock` + 内存字典，带过期清理；**仅限单事件循环** |
| `RedisIdempotencyStore` | 多实例 | `SET NX` 原子占用保证跨实例唯一；Key 经 `CacheKeyBuilder`：`web:idem:v1:occupy:{key}` / `web:idem:v1:result:{key}`（{key} 为"用户+幂等键"联合业务键） |

### 6.3 启用与示例

```yaml
app:
  web:
    middlewares:
      idempotency:                 # 幂等键按用户隔离：声明于 auth 之前（后声明者外层先执行），
        enabled: true              # 保证 auth 注入身份后幂等键按真实用户隔离（最内层最后执行）
        store_type: redis          # memory（默认，单实例）/ redis（跨实例原子，复用 cache 组件 Redis 客户端，需 app.cache.type=redis）
        ttl_seconds: 86400
      auth:
        enabled: true
      trace_id: {}                 # 必须最后声明（最先执行）
```

> `store_type=redis` 但缓存组件非 Redis 时启动快速失败（`ConfigError`，提示需 `app.cache.type=redis`）。

客户端调用示例（curl）：

```bash
# 首次请求：携带幂等键
curl -X POST http://localhost:8000/v1/orders \
  -H "Authorization: Bearer <token>" \
  -H "Idempotency-Key: 8f14e45f-8f4e-4b0e-9f0a-123456789abc" \
  -d '{"amount": "19.90"}'
# 200 + 业务 code S0000

# 重放（同一用户、同一幂等键、相同请求体）：直接返回首次结果
# 请求体变更：409 E4-COMMON-001 "幂等键已使用且请求内容不一致，请更换幂等键"
# 首请求处理中：202 "幂等请求处理中，请稍后重试"
```

业务代码无需感知幂等逻辑；幂等结果缓存发生在响应完成后（`dispatch` 内读取 body 并 `set_result`）。

## 7. 组合用法

重试 + 熔断 + 限流 + 幂等的典型组合（顺序：入口限流 → 业务幂等 → 受保护调用重试 → 熔断兜底）：

```python
from web_infra.infra.resilience.circuit_breaker import CircuitBreaker
from web_infra.infra.resilience.circuit_breaker_config import CircuitBreakerConfig
from web_infra.infra.resilience.retry import RetryConfig, retry
from web_infra.infra.resilience.circuit_open_error import CircuitOpenError

# 1. 熔断保护下游资源（fallback 降级）
circuit = CircuitBreaker(
    "payment-channel",
    CircuitBreakerConfig(failure_rate_threshold=0.3, wait_duration_in_open_state=60),
    fallback=lambda *a, **kw: {"status": "degraded"},   # 熔断时降级结果
)

# 2. 重试包裹远程调用（仅瞬时错误，指数退避）
@retry(RetryConfig(max_retries=2, base_delay=0.5))
async def call_payment(channel: str, payload: dict) -> dict:
    async with httpx.AsyncClient(timeout=5) as client:
        resp = await client.post(f"https://pay.{channel}", json=payload)
        resp.raise_for_status()
        return resp.json()

# 3. 组合调用：重试是单次调用的策略，熔断是整体资源的策略
async def place_order(order_id: str):
    try:
        result = await circuit.execute_async(call_payment, "wechat", {"order_id": order_id})
        return result
    except CircuitOpenError:
        return {"status": "degraded"}   # 未配 fallback 时调用方兜底
```

层次关系说明：

- **限流**（`RateLimitMiddleware` / `TokenBucketRateLimiter`）：挡在入口，防流量洪峰打穿服务——超限直接 429，不消耗下游；
- **幂等**（`IdempotencyMiddleware`）：挡在写接口，防重试/重放造成重复副作用——同一幂等键只执行一次；
- **重试**：在**幂等接口**上对瞬时错误补一次机会（配合退避），但重试次数要能塞进幂等 TTL 窗口；
- **熔断**：当下游持续故障时快速失败/降级，避免重试风暴放大故障——熔断开启时重试层应感知 `CircuitOpenError` 直接走降级。

## 8. 常见坑

- **非幂等接口重试**（规范 §7.2 红线）：下单/扣款/转账等禁止盲目 `@retry`；确需重试必须先保证接口幂等（如携带幂等键、业务幂等键、唯一索引）。
- **重试与熔断脱节**：重试 2 次 × 熔断窗口未开 → 故障放大；熔断开启后重试层仍在打 → 半开状态被重试流量消耗。组合场景应把重试放在熔断的 `execute_async` 之内、并捕获 `CircuitOpenError` 走降级。
- **分布式锁忘记释放**：进程崩溃时靠租约（lease_time）兜底，但业务持有锁过久（>lease_time）会被其他请求获取——临界区时长应显著小于租约；用 `async with` 防手写 finally 遗漏。
- **锁误删他人锁**：释放必须走持有者 token 校验（框架 Lua 已实现），不要手写 `del key`。
- **幂等键滥用**：同一个幂等键换了请求体 → 409 拒绝重放（这是刻意的一致性校验）；幂等键要保证用户维度唯一（框架已按 user_id 隔离），不要用全局可预测序列。
- **内存实现的多实例语义**：`InMemoryJwtTokenStore` / `InMemoryCaptchaStore` / `InMemoryIdempotencyStore` 均标注 `@Stateful`——多实例部署必须换 Redis 实现（Token 状态/验证码/幂等占用），否则登出撤销、一次性消费、幂等占用都只在单进程内成立。
- **限流 key_by=user 的顺序**：yml 中 `rate_limit` 声明于 `auth` 之前才读得到用户身份（后声明者外层先执行），否则匿名退化路径维度。
