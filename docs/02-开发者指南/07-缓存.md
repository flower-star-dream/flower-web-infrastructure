## 1. 是什么

`web_infra.capabilities.cache`（源码见 `src/web_infra/capabilities/cache/`，Redis 实现 `RedisCacheBackend` 位于 `db/` 子包）围绕规范 §8（缓存全生命周期）提供：

| 组件 | 职责 |
| ---- | ---- |
| `CacheBackendInterface` | 异步缓存抽象：`get` / `set` / `delete` / `exists` / `set_empty` / `is_empty` |
| `MemoryCacheBackend` | 进程内缓存（容量上限 + TTL 淘汰），单实例/测试场景 |
| `RedisCacheBackend` | Redis 分布式缓存（连接管理委托 `RedisConfig`），多实例场景 |
| `CacheConfig` | 容量 / TTL / 抖动 / 本地 TTL 钳制参数 |
| `CacheBackendRegistry` | 按 `app.cache.type` 装配（内置 `memory` / `redis`，自定义经 `register` 接入） |
| `KeyBuilder` / `TenantKeyBuilder` | Key 统一生成（占位符模板 / 租户维度注入） |

**何时用**：需要进程内或分布式缓存的任何场景；与 Redis 相关组件（JWT 状态存储、API 幂等存储、消息消费幂等）复用同一 Redis 连接时；多租户系统的租户数据缓存（必须经 `TenantKeyBuilder` 生成 Key）。

> 安装：Redis 实现需 `pip install "flower-web-infrastructure[redis]"`（延迟导入）；内存实现在核心依赖内开箱即用。

## 2. CacheBackendInterface 接口

```python
from web_infra.capabilities.cache import CacheBackendInterface

# 方法契约（全部异步）
async def get(self, key: str) -> Any | None: ...           # 读取，未命中返回 None
async def set(self, key, value, ttl=None, ttl_jitter_seconds=None) -> None: ...  # 写入
async def delete(self, key: str) -> None: ...              # 删除
async def exists(self, key: str) -> bool: ...              # 存在性判断
async def set_empty(self, key: str, ttl: int = 60) -> None: ...  # 空值占位（防穿透）
async def is_empty(self, key: str) -> bool: ...            # 是否处于空值占位
```

要点：

- `ttl` 为过期秒数（`None` 使用后端默认 TTL：内存 300s；Redis 为不过期，见 §3 差异说明）。
- `ttl_jitter_seconds`：TTL 生效时叠加 `[0, jitter)` 秒随机抖动（`None` 使用后端默认抖动，`0` 关闭），用于防缓存雪崩（规范 §8.3）。
- `EMPTY_TTL_LIMIT_SECONDS = 120`：空值占位 TTL 硬上限，超过自动钳制。
- 存储值为字符串/字节等基础类型，复杂对象需**调用方自行序列化**后存储（如 `json.dumps`）。

一个最小使用示例：

```python
cache = app.state.cache                     # 装配后的后端实例

await cache.set("k", "v", ttl=60)           # 60 秒过期
value = await cache.get("k")                # "v" / None
await cache.delete("k")
```

## 3. 内存与 Redis 实现差异

| 维度 | `MemoryCacheBackend` | `RedisCacheBackend` |
| ---- | ---- | ---- |
| 存储 | 进程内 `OrderedDict`（`asyncio.Lock` 保护） | Redis（连接池由 `RedisConfig` 管理） |
| 适用 | 单实例 / 测试 / 本地开发 | 多实例 / 生产 |
| TTL 默认 | `CacheConfig.default_ttl`（300s） | `ttl=None` 表示不过期（Redis `SET` 不带 `ex`） |
| 容量 | `max_size` 超限淘汰最旧项 | 无（Redis 侧内存管理） |
| 本地 TTL 钳制 | 有（见 §5） | 无（本身就是分布式） |
| 空值占位 | 同 Key 存 `_EMPTY` 标记，`get` 返回 `None` | 独立 `#empty` 后缀 Key 隔离存储 |
| 删除 | 删单个 Key | **同时删真实 Key 与 `#empty` 占位 Key**（防残留空值标记） |
| 线程模型 | 仅限单事件循环（`asyncio.Lock` 不跨线程互斥） | 跨实例安全 |

> `RedisCacheBackend` 的 Key 前缀默认 `"web:"`（构造参数 `key_prefix`）；真实 Key 形如 `web:auth:v1:token:1001:xxxx`，空值占位 Key 形如 `web:auth:v1:token:1001:xxxx#empty`。

## 4. 空值缓存防穿透（set_empty / is_empty）

缓存穿透：查询一个**必然不存在**的数据（如恶意高频请求不存在的订单号），每次都会直打 DB。规范 §8.2 的做法是**把"数据不存在"也缓存起来**，TTL 上限 120s：

```python
async def get_order_detail(order_id: str):
    key = f"web:order:v1:detail:{order_id}"

    # 1) 先查空值占位：命中说明最近确认不存在，直接短路（避免再次打 DB）
    if await cache.is_empty(key):
        return None

    # 2) 查真实缓存
    cached = await cache.get(key)
    if cached is not None:
        return json.loads(cached)

    # 3) 缓存未命中 → 查库
    row = await order_repo.get(order_id)
    if row is None:
        await cache.set_empty(key, ttl=60)     # 空值占位（默认 60s，上限 120s 自动钳制）
        return None
    await cache.set(key, json.dumps(row), ttl=300)
    return row
```

要点：

- `set_empty` 的 `ttl` 会被钳制到 `[1, 120]` 秒——空值缓存 **TTL ≤ 120s**，避免"不存在"状态长期驻留掩盖数据已新增。
- 对调用方，空值占位表现为 `get` 返回 `None`（内存实现 `_EMPTY` 标记、Redis 实现独立 `#empty` Key），用 `is_empty` 区分"缓存未命中"与"确认不存在"。
- Redis 实现 `delete` 会**连带删除** `#empty` 占位 Key：业务更新数据后执行一次 `delete(key)`，即可让新数据立即可见，无需额外清理。

## 5. TTL 抖动防雪崩与本地 TTL 钳制

**防雪崩（规范 §8.3）**：同一热点 Key 若 TTL 完全一致，会同时过期、同时回源打爆 DB。`set` 时叠加随机抖动让过期时间错峰：

```python
# 方式一：使用后端默认抖动（CacheConfig.default_ttl_jitter_seconds，默认 5s）
await cache.set(key, value, ttl=300)

# 方式二：按调用场景显式指定抖动上限
await cache.set(key, value, ttl=300, ttl_jitter_seconds=30)
```

抖动实现（源码事实）：`ttl` 非空且抖动 > 0 时，实际过期时间 = `ttl + random.uniform(0, jitter)` 后取整（Redis 实现取整为 `int`，内存实现保持浮点）。

**本地缓存 TTL 钳制**：`MemoryCacheBackend` 在叠加抖动**之前**校验 `ttl ≤ remote_default_ttl × local_ttl_ratio_limit`（默认 `300 × 1/3 = 100s`），超限自动钳制并记 warning——本地缓存 TTL 不得超过分布式 TTL 的 1/3，防止"本地缓存拖长分布式 TTL 语义"（即本地多缓存了一段时间导致数据新鲜度劣化）：

```python
from web_infra.capabilities.cache import CacheConfig, MemoryCacheBackend

# 分布式 TTL 300s → 本地 TTL 上限 100s
backend = MemoryCacheBackend(CacheConfig(remote_default_ttl=300, local_ttl_ratio_limit=1/3))
await backend.set("k", "v", ttl=300)   # 实际生效 TTL 被钳制为 100s（日志 warning）
```

`CacheConfig` 全量参数：

| 参数 | 默认值 | 说明 |
| ---- | ---- | ---- |
| `max_size` | `10000` | 缓存容量上限（防内存无界增长） |
| `default_ttl` | `300` | 默认过期时间（秒） |
| `default_ttl_jitter_seconds` | `5.0` | 默认 TTL 抖动上限（秒；0 关闭） |
| `remote_default_ttl` | `300` | 分布式缓存参考 TTL（钳制基准） |
| `local_ttl_ratio_limit` | `1/3` | 本地 TTL 不得超过分布式 TTL 的比例上限 |

## 6. Key 规范：KeyBuilder

Key 模板统一按规范 §5.7 组织：**`web:{module}:v1:{biz}`**（含版本号 `v1`，动态段运行时注入）。框架内置模板见 `CacheKeyBuilder`（`web_infra.infra.constants.cache_key`）：`web:auth:v1:token:{user_id}:{jti}`、`web:common:v1:lock:{key}`、`web:mq:v1:msg_idem:{key}` 等。

业务自定义 Key 用 `KeyBuilder.build(template, *args)`（占位符 `{xxx}` 按位置注入）：

```python
from web_infra.capabilities.cache import KeyBuilder

key = KeyBuilder.build("web:order:v1:detail:{order_id}", order_id)  # web:order:v1:detail:1001
# 也可结合常量模板：KeyBuilder.build(CacheKeyBuilder.LOGIN_LOCK, username)
```

规则（源码事实）：动态段为空或含空白/冒号（`[\s:]+`）抛参数异常；模板占位符与实参数量不匹配同样抛异常——从源头防止手写拼接产生非法 Key。**业务禁止手写 `前缀+key` 拼接**（整改 S5-4）。

## 7. 租户隔离：TenantKeyBuilder

多租户规范 §3 / T-3：**租户相关数据的缓存 Key 必须含租户维度**，禁止用裸 `KeyBuilder` 存储租户数据。`TenantKeyBuilder` 自动从 `RequestContext` 取当前租户注入 `{tenant_id}` 占位符：

```python
from web_infra.capabilities.cache import TenantKeyBuilder

# 方式一：模板含 {tenant_id} 占位（tenant_id 缺省从请求上下文读取）
key = TenantKeyBuilder.build(
    "web:common:v1:order:{tenant_id}:detail:{order_id}",
    tenant_id=current_tenant,               # 可显式指定；缺省读 RequestContext
    require_tenant=True,                    # 强隔离：无租户上下文抛参数异常
)

# 方式二：三段式便捷方法 {prefix}:{tenant_id}:{biz_key}
key = TenantKeyBuilder.build_with_tenant(
    prefix="web:common:v1:order",
    tenant_id=None,                          # None → 自动取上下文租户
    biz_key="detail:1001",
)
```

要点：

- 模板**必须**包含 `{tenant_id}` 占位符，否则抛参数异常（防漏租户维度）。
- `require_tenant=True` 时无租户上下文抛异常（多租户强隔离场景）；默认回落 `no-tenant` 占位（单租户/非租户场景，避免跨租户串扰）。

## 8. CacheBackendRegistry 装配

`create_app` 按 `app.cache.type` 经 `CacheBackendRegistry` 按名装配，结果挂 `app.state.cache`（源码：`application.py::_build_cache`）：

```yaml
app:
  cache:
    type: redis            # memory（默认，单实例）/ redis（分布式）
    max_size: 10000        # 仅 memory 生效（容量上限）
    redis:                 # type=redis 时生效（缺省用 RedisConfig 默认值）
      host: localhost
      port: 6379
      db: 0
      password: ${APP_CACHE_REDIS_PASSWORD:}
      username: ${APP_CACHE_REDIS_USERNAME:}
      max_connections: 50
      decode_responses: true
      socket_connect_timeout: 5
      socket_timeout: 5
      socket_keepalive: true
      health_check_interval: 30
      retry_on_timeout: true
```

业务侧使用：

```python
app = create_app()          # 读取 application.yml
cache = app.state.cache     # MemoryCacheBackend 或 RedisCacheBackend（均为 CacheBackendInterface）

await cache.set("web:common:v1:model_config:demo", "{}", ttl=300)
config_str = await cache.get("web:common:v1:model_config:demo")
```

自定义缓存后端（第三方/自研）经注册表接入，未注册的 `app.cache.type` 装配期抛 `ConfigError`：

```python
from web_infra.capabilities.cache import CacheBackendRegistry

def my_factory(settings):
    """工厂入参为装配配置 Settings（读取 app.cache.<type> 段）"""
    return MyCacheBackend(settings.get("app.cache.my", {}))

CacheBackendRegistry.register("my", my_factory)
# application.yml: app.cache.type: my
```

## 9. 监控指标：缓存命中率（/metrics）

缓存组件内置指标采集（`web_infra.infra.monitoring.cache_metrics` 的 `CacheMetrics`），随 `/metrics` 暴露，**懒注册**——组件实际被调用（首次 `get`/`set` 等）时才注册，未启用的缓存组件不产生指标：

| 指标 | 标签 | 说明 |
| ---- | ---- | ---- |
| `cache_operations_total` | `cache`（memory/redis）、`operation`（get/set/delete/exists） | 缓存操作次数 |
| `cache_hits_total` | `cache` | 缓存命中次数（`get`/`exists` 命中时递增） |
| `cache_misses_total` | `cache` | 缓存未命中次数（`get`/`exists` 未命中时递增） |

命中率 = `cache_hits_total / (cache_hits_total + cache_misses_total)`。框架在两个实现内部统一调用 `CacheMetrics.record_operation(cache, operation, hit=...)` 埋点（源码事实：`memory_cache_backend.py` / `redis_cache_backend.py` 的 `get`/`set`/`delete`/`exists`/`set_empty`/`is_empty`），业务代码无需额外埋点。组件关闭时框架调用 `unregister_metrics()` 卸载指标（规范 §16.5：扩展点注册与生命周期绑定）。

> 排查建议：命中率长期偏低说明缓存未生效（Key 拼错 / TTL 过短 / 空值未缓存），可结合 `cache_operations_total{operation="get"}` 与 DB 慢查询一起定位；命中率突降通常伴随上线或数据变更，优先检查 Key 规范与租户维度（§6/§7）。

## 10. 缓存与数据一致性（实践建议）

> 以下为**业务侧实践建议**（框架不提供自动失效封装）：缓存是提升读性能的旁路，一致性由业务更新链路保证。

**更新顺序（Cache-Aside，推荐）**：先写库、后删缓存——避免"先删缓存后写库"在写库失败时留下过期缓存、以及并发读写下的脏窗口：

```python
async def update_order(order_id: str, new_status: int) -> None:
    key = KeyBuilder.build("web:order:v1:detail:{order_id}", order_id)
    async with db.orm_session() as session:        # 业务事务
        order = (await session.execute(select(Order).where(Order.id == order_id))).scalar_one()
        order.status = new_status
    await cache.delete(key)                        # 事务提交后删缓存（下次读取重建）
```

**组合空值占位**：查询为 None 时 `set_empty`（TTL≤120s），删除时 `delete` 会连带清理 `#empty` 占位（Redis 实现），保证"新增数据后立即可见"（见 §4）。

**要点**：

- 删缓存（而非更新缓存）：重建成本低、避免"更新值与写库值不一致"的编码缺陷；写库失败时删缓存只是多一次未命中，无害。
- 事务**提交后**再删缓存：事务未提交就删，会有并发读把旧值写回缓存的窗口；提交后再删是安全的最终一致性。
- 缓存与 DB 强一致（如金额类）超出本能力范围：应结合分布式锁/版本号或直接读库，缓存仅用于可容忍秒级延迟的场景。

## 11. 与 JWT 状态存储共用 Redis 连接

`app.cache.type: redis` 装配时（源码：`cache_backend_registry.py::_redis_cache_factory`）除创建 `RedisCacheBackend` 外，还会执行 `JWTUtil.set_redis_config(config)`——**JWT 登出黑名单 / Token 状态存储默认跟随使用同一个 Redis 连接实例**（同一 `RedisConfig`），不重复建连。需要 Redis 的其它组件（API 幂等存储、消息消费幂等存储）也按此模式复用：

```python
from web_infra.capabilities.cache import CacheBackendRegistry

# redis 工厂内部（框架源码事实）：
#   config = RedisConfig(**{app.cache.redis.* 字段})
#   JWTUtil.set_redis_config(config)        # JWT 状态存储共用同一连接
#   return RedisCacheBackend(config=config)

# 业务侧：经 cache.config 拿到共享的 RedisConfig，再构造需要 Redis 的组件
redis_config = cache.config                # RedisCacheBackend.config 属性
client = await redis_config.connect()      # 与缓存/JWT 共用同一连接池
```

> 一致性前提：JWT 状态存储、缓存、幂等存储必须都走**同一个** `RedisConfig` 实例（经 `app.cache.redis` 装配），否则各建各的连接池，语义上等价但浪费连接资源。

## 12. 常见坑

1. **复杂对象未序列化**：缓存值限基础类型（字符串/字节），`dict` / Pydantic 模型需自行 `json.dumps`，读取时反序列化。
2. **空值占位与真实缓存混淆**：`get` 对空值占位返回 `None`，先 `is_empty` 再 `get` 才是完整读路径（见 §4 顺序）。
3. **内存缓存 TTL 被钳制到 100s 一脸懵**：这是规范 §8.3 的本地 TTL 钳制（分布式 300s 的 1/3），日志有 `本地缓存 TTL 超限被钳制` warning；要延长本地缓存请在 `CacheConfig` 调大 `remote_default_ttl` 或调小比例系数。
4. **Redis `ttl=None` 永不过期**：内存实现 `ttl=None` 用默认 300s，Redis 实现 `ttl=None` 是永不过期——写跨环境通用代码时务必显式传 `ttl`。
5. **多实例部署仍用 memory**：`MemoryCacheBackend` 是进程内状态（@Stateful），多实例需 `app.cache.type: redis`（规范 S1-1）。
6. **租户数据缓存 Key 没租户维度**：多租户系统禁止裸 `KeyBuilder` 存租户数据（规范 T-3），否则租户间数据串扰；统一走 `TenantKeyBuilder`。
7. **Key 手写拼接**：动态段含冒号/空白会导致 Key 结构错乱甚至命中错误数据；统一走 `KeyBuilder` / `TenantKeyBuilder` 校验。
