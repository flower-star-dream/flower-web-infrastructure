# 价值与业务场景（写给业务、产品与决策者）

> 本文从**真实业务场景**出发，说明框架如何组合能力解决问题。
> 每节：业务痛点 → 框架怎么解决 → 需要什么（团队/外部服务）→ 落地效果。
> 不涉及代码，产品经理可把它当作与研发沟通的「能力对齐清单」。

---

## 场景 1：商城 / 电商系统

### 痛点
- 用户登录、下单、支付、退款、消息通知、商品搜索、订单报表……
- 最怕：**重复下单、重复扣款**；**支付回调丢消息**导致订单状态错乱。

### 框架组合
| 业务环节 | 使用的能力 |
| -------- | ---------- |
| 用户体系 | 认证登录、JWT、验证码、登录防爆破、社交登录（微信） |
| 下单 | API 幂等（防重复提交）、通用状态机（订单状态流转） |
| 支付 | 支付 SPI（微信 APIv3：下单/回调/退款/查单/关单） |
| 关键事件不丢 | Outbox 可靠投递（订单创建成功消息必达） |
| 异步处理 | 消息队列（订单 → 库存/通知/积分解耦） |
| 商品搜索 | 全文搜索引擎（Elasticsearch） |
| 对账 | 支付对账（T+1 账单差异自动核对） |
| 安全 | 权限控制（管理员/普通用户）、隐私脱敏 |

### 落地效果
- 重复支付/重复回调被框架幂等机制拦截，资金安全有保障；
- 关键消息走 Outbox 本地事务表，数据库写入成功即不丢；
- 微信支付从零对接变成「填配置 + 写一个回调处理器」。

## 场景 2：SaaS 多租户平台（一套系统服务多家客户）

### 痛点
- 多家客户的数据必须**严格隔离**，不能串数据（A 公司员工看到 B 公司订单 = 事故）。
- 每家客户配置不同（数据库独立 or 共享库按租户过滤）。

### 框架组合
| 需求 | 使用的能力 |
| ---- | ---------- |
| 租户隔离 | 多租户能力：请求上下文带租户 ID、SQL 自动追加租户条件、缓存 Key 按租户隔离 |
| 按租户分库 | 多数据源路由（租户 → 独立数据库），支持租户注销动态回收 |
| 高并发缓存 | 缓存按租户维度构建 Key，防串扰 |
| 资源管控 | AI 配额按租户/用户/场景三维管控（如有 AI 能力） |

### 落地效果
- 开发时**几乎无感**：框架自动在 SQL 和缓存 Key 上注入租户条件，业务代码不用每个查询都写 `WHERE tenant_id = ?`；
- 从「共享库」到「独立库」只改配置，业务代码不变。

## 场景 3：AI 应用（智能客服 / 知识库问答 / AI 助手）

### 痛点
- 多家大模型（OpenAI、通义、DeepSeek……）协议不同，换模型要改代码；
- 模型不稳定：超时、限流、临时故障——不能影响主业务；
- 成本失控：谁在调、调了多少、花了多少钱说不清；
- 私域知识库问答：让模型基于**自家文档**回答，不胡说。

### 框架组合
| 需求 | 使用的能力 |
| ---- | ---------- |
| 多模型统一接入 | AI 模型网关（场景路由 + 主备降级 + 自动重试） |
| 故障切换 | 主模型挂了自动切备用模型 |
| 成本控制 | 配额管控（次数/Token/金额三维）+ 用量计费记录 |
| 基于知识库问答 | RAG 检索：文档切片 → 向量化 → 检索 → 模型回答 |
| 提示词管理 | Prompt 模板（版本化、参数化、防注入） |
| 内容安全 | 输入/输出审核（政治敏感、暴力等内容拦截） |
| 性能 | AI 缓存（相同问题直接命中缓存）、流式输出（SSE） |
| 监控 | AI 调用指标（成功率/延迟/TTFT/Token/成本） |

### 落地效果
- 换模型供应商只改配置，不动业务代码；
- 成本、配额、调用量全部可查可管控；
- 知识库问答开箱即用（默认内存向量库可先跑通，生产换 Elasticsearch）。

## 场景 4：微服务改造 / 中台化

### 痛点
- 服务拆了，但互相怎么找？怎么调？挂了怎么办？
- 配置散落各处，改一个参数要登好几台机器。
- 消息、存储、注册中心各自为政，团队认知成本高。

### 框架组合
| 需求 | 使用的能力 |
| ---- | ---------- |
| 服务发现 | 注册中心（Nacos）：服务自动注册/注销、健康检查 |
| 服务间调用 | Feign 客户端：负载均衡 + 指数退避重试 + 按服务熔断 + 统一 503 降级 |
| 统一入口 | 网关：路由表转发、鉴权前置 |
| 配置中心 | Nacos 配置中心：远程配置热更新，覆盖本地配置 |
| 可靠消息 | Outbox + 幂等消费（跨服务事件不丢不重） |
| 容错 | 熔断降级、限流、分布式锁 |

### 落地效果
- 服务间调用「声明式」：像调本地方法一样调别的服务；
- 一个服务挂了，熔断器快速失败并降级，**不让故障雪崩**；
- 脚手架提供参考实现（gateway + user-service + order-service），从零到跑通有模板可抄。

## 场景 5：报表 / 导出 / 后台任务

### 痛点
- 大数据量导出 Excel/PDF，接口同步等太久，前端超时；
- 需要定时跑：每日对账、每日报表、定期清理。

### 框架组合
| 需求 | 使用的能力 |
| ---- | ---------- |
| 后台任务 | 异步任务框架：提交任务、后台执行、可查进度/结果 |
| PDF 导出 | PDF 渲染工具（网页/HTML → PDF，支持登录态注入） |
| 定时执行 | 定时任务调度（间隔/超时/连续失败暂停/执行记录） |
| 多实例防重 | 分布式锁（多台机器只允许一台执行） |

### 落地效果
- 导出类操作全部异步化，前端轮询状态即可；
- 定时任务自带「连续失败自动暂停 + 告警」，不会无限重试打爆系统。

## 场景 6：业务规则复杂（订单/审批/工单状态流转）

### 痛点
- 状态机逻辑散落在代码里：`if 状态==A and 事件==X` 满天飞；
- 非法流转（已退款又支付成功）难拦截、难审计。

### 框架组合
通用状态机引擎：状态/事件枚举 → 合法流转表 → 事件处理器，**非法流转直接报错**，流转路径一目了然。

### 落地效果
- 状态流转集中管理，代码评审看得懂、改得动；
- 非法状态流转在框架层拦截，业务不会出现「灵异状态」。

## 决策清单（评审项目时对照用）

| 问自己 | 若答案是「是」 | 需要准备 |
| ------ | ------------- | -------- |
| 要用户登录注册？ | 认证 + 验证码 + 防爆破 | 无 |
| 有交易/资金？ | 支付 + 幂等 + 状态机 + 审计 | 微信商户号 |
| 关键事件不能丢？ | Outbox | 数据库 |
| 多家客户数据隔离？ | 多租户 | 数据库规划 |
| 要接大模型？ | AI 网关 + RAG + 配额计费 | 模型 Key |
| 要站内搜索？ | 全文搜索 | Elasticsearch |
| 要拆微服务？ | 注册中心 + Feign + 网关 | Nacos + MQ |
| 要监控线上？ | 监控 + 容量评估 | Prometheus + Grafana |
