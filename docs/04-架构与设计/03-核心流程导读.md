## 1. create_app 装配全流程

**参与者**：`create_app` → `Application`（构造 + `build`）→ 各 `_setup_*` 步骤 → `_lifespan`（启动钩子）。

```ascii
create_app(settings, **kwargs)
  │  Application(settings, **kwargs).build()
  ▼
Application.__init__
  ├─ _resolve_settings(settings)          # Settings 实例直用 / None 用全局实例 / dict 叠加默认源
  ├─ FastAPI(title, version, lifespan=_lifespan)
  ▼
Application.build()                       # 固定装配顺序（顺序即依赖约束）
  ├─ _setup_logging()                     # ① 日志：configure_logging（格式/通道/脱敏/自定义 sinks）
  ├─ _setup_capabilities()                # ② 能力：app.capabilities.enabled 校验（未知/循环→ConfigError）+ 拓扑序 enable
  ├─ _setup_components()                  # ③ 组件：cache/db/storage/mq/registry/ai[/mongo]
  │     └─ 各 _build_* 经注册表按 type 装配（_resolve_registry 未注册→ConfigError 快速失败）
  │     └─ 挂载 app.state.components / app.state.<name> / app.state.settings
  ├─ _setup_extensions()                  # ④ 扩展点：app.extensions.enabled 校验 + 拓扑序 build → app.state.extensions
  ├─ _setup_web()                         # ⑤ Web：register_global_exception_handlers + 配置声明中间件（_MIDDLEWARE_REGISTRY）
  ├─ _setup_tenant()                      # ⑥ 多租户（enabled=true）：TenantQueryFilter 挂载数据库会话（install_tenant_filter）
  ├─ _setup_diagnostic_guard()            # ⑦ DiagnosticAccessGuard（/capacity 与 /metrics 共用，生产 IP 白名单）
  ├─ _setup_capacity()                    # ⑧ 容量评估（enabled=true，延迟导入 capacity 包）
  └─ _setup_health()                      # ⑨ register_health_endpoints：/health/live /health/ready /health /metrics
  ▼
（uvicorn 启动应用时触发）
_lifespan 启动序
  ├─ RequestContext.clear()               # 启动前清理上下文
  ├─ setup_uvicorn_access_log(app)        # 关闭 uvicorn 原生 access log（中间件输出唯一访问日志）
  ├─ _register_ai_models_from_store()     # ai store.type=db/自定义：全量加载自动注册供应商（失败不阻断启动）
  ├─ _run_extension_startups()            # 扩展点 startup 钩子（拓扑序，前置先启动）
  └─ _start_capacity_sampler()            # 容量采样任务启动（未启用跳过）
```

**关键点**：

- 装配顺序 `日志→能力→组件→扩展点→Web→租户→守卫→容量→健康`：组件先于中间件（中间件可复用组件），扩展点在组件之后、中间件之前（插件 build 可复用组件、产物可被中间件复用）。
- `_resolve_settings`：dict 入参包装为 `Settings(CompositeConfigSource(DictConfigSource(settings), Settings.default_source()))`，dict 优先级最高。
- 组件注册表按名装配，`_resolve_registry` 将未注册 `KeyError` 转为 `ConfigError`（内置清单提示），杜绝拼写错误静默回落默认实现。
- 能力校验在组件装配之前，能力不通过则整个应用装配失败。
- 组装完成的组件全部暴露在 `app.state`，业务经 `app.state.<name>` 访问。

## 2. 一次 HTTP 请求的完整旅程

**参与者**：`TraceIdMiddleware`（=`RequestContextMiddleware`）→ `SecurityHeadersMiddleware` → `AuthMiddleware` → `RateLimitMiddleware` → `IdempotencyMiddleware` → 路由/控制器 → Service → DB → 响应 → 全局异常 → 日志 → 指标。

**中间件执行顺序约定**（`core/application.py` + `application.default.yml`）：Starlette 中**后声明者在外层先执行**；`application.default.yml` 声明顺序为 `idempotency → auth → security_headers → trace_id`，因此执行顺序为 `trace_id → security_headers → auth → idempotency`——TraceId 最先生成、身份在幂等层之前注入（幂等键按用户维度隔离需要身份）。`rate_limit` 由业务按需声明。

```ascii
请求进入（外层 → 内层）
┌─────────────────────────────────────────────────────────────┐
│ TraceIdMiddleware（最外层，最先执行）                            │
│   ├─ 透传 X-Trace-Id 或 generate_trace_id() 生成               │
│   ├─ 注入 X-User-Id/X-Scope/X-Client-Id/X-Service-Id/X-Tenant-Id
│   │     （仅请求头存在时注入，避免空值覆盖身份）                  │
│   └─ 响应头回写 X-Trace-Id；finally RequestContext.clear()      │
│  ┌─────────────────────────────────────────────────────────┐  │
│  │ SecurityHeadersMiddleware（安全响应头，enabled 时）         │  │
│  │  ┌───────────────────────────────────────────────────┐  │  │
│  │  │ AuthMiddleware（enabled 时，白名单/OPTIONS 放行）      │  │  │
│  │  │   ├─ Bearer 凭证 → _verify（默认 JWTUtil.verify_token）│  │  │
│  │  │   ├─ 失败 → 401（E2-AUTH-*）不入业务模块               │  │  │
│  │  │   └─ 成功 → RequestContext.set_user_id/scope/client_id│  │  │
│  │  │  ┌───────────────────────────────────────────────┐ │  │  │
│  │  │  │ IdempotencyMiddleware（enabled 时，最内层）       │ │  │  │
│  │  │  │  写方法+幂等键 → try_occupy → 摘要比对 → 重放 │ │  │  │
│  │  │  │  ┌─────────────────────────────────────┐ │ │  │  │
│  │  │  │  │ 路由 → Controller → Service           │ │ │  │  │
│  │  │  │  │ → db.session()/orm_session()（自动   │ │ │  │  │
│  │  │  │  │   提交/回滚/关闭）→ Result 响应        │ │ │  │  │
│  │  │  │  └─────────────────────────────────────┘ │ │  │  │
│  │  │  │  成功缓存结果；业务异常 release 占用          │ │  │  │
│  │  │  └───────────────────────────────────────────┘ │  │  │
│  │  └───────────────────────────────────────────────────┘  │  │
│  └─────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘

注：RateLimitMiddleware 未在默认配置中；业务在 yml 中声明时按声明位置插入栈——
声明在 auth 之后则位于 auth 外层（先于 auth 执行），声明在 idempotency 之前则位于其外层。

异常路径：WebInfraException/RequestValidationError/StarletteHTTPException/Exception
  └─ register_global_exception_handlers 全局处理器
       └─ 日志记完整错误码（服务端）→ 出网响应边界收敛（E3/E5 → 大类前缀码，见 04-设计决策.md）
```

**关键点**：

- 认证成功仅注入上下文，**业务禁止自行解析凭证**（规范 §6.4），从 `RequestContext` 取身份；粗粒度授权由 `PermissionGuard` 声明式控制。
- 幂等中间件：`用户 + 幂等键` 唯一（`_build_key`），请求摘要 = `method:path:query + body SHA-256`（`_build_request_hash`）；摘要一致重放首次结果（HTTP 200 + 原业务 code）、不一致 409、处理中 202；业务异常 `release` 占用允许重试。
- 访问日志由 `LoggingMiddleware`（`setup_logging_middleware`）输出唯一访问日志（真实客户端 IP + trace_id/耗时/阶段）；耗时阶段由 `PhaseTimer` 标记（`PhaseTimer.mark("auth")` 等）。
- 响应统一 `Result` 结构（`S0000`/错误码），`BigIntJSONResponse` 防大整数精度丢失；全局异常处理器按大类定日志级别（E1/E2 INFO、E3 ERROR、E4 WARN）。

## 3. 数据库 session 生命周期

**参与者**：`DatabaseManager.session` / `MySQLDatabase.orm_session` / `SessionScopeMixin.session` / `DatabaseSessionInterface`。

提交/回滚/关闭决策路径由框架上下文管理器统一处理（`SessionScopeMixin.session`，MySQLDatabase 的 `orm_session` 同构），**业务无需 try/finally**：

```ascii
async with db.session() as session:        # 或 db.orm_session()
  │
  ├─ 进入：create_session()
  │   ├─ 多租户 strict 模式先 require_context()（无租户上下文拒绝执行）
  │   └─ 建会话（SQLite 同步 / SQLAlchemy AsyncSession / 通用 DatabaseSessionInterface 包装）
  │
  ├─ 业务体：await session.query_all(...) / select(Model) ...
  │
  ├─ 正常退出 → session.commit()
  │     └─ orm_session 另统计事务耗时：≥ long_transaction_threshold_seconds(默认 5.0s)
  │        记 warning 审计日志（含 datasource 与耗时）+ db_long_transaction_total 计数（仅告警不阻断）
  │
  ├─ 异常退出 → session.rollback() → raise（异常向上传播）
  │
  └─ finally → session.close()（归还连接/关闭会话）
```

**关键点**：

- 决策路径是**单个 try/except/finally**：`yield` 成功 → commit；`yield` 抛异常 → rollback + 原样上抛；无论如何 finally 关闭。
- 读写分离（S10-2）：`orm_session(read_replica=True)` 且有从库（`replica_urls`）时经 `ReadWriteRouter.next_replica()` 轮询路由从库；未配置/无可用从库回退主库并 warning。
- 多租户：`TenantQueryFilter` 经 `install_tenant_filter` 挂载到会话工厂，SQL 自动注入租户条件；数据源切换（`DatabaseManager.route`）须经 T-1 租户权限校验（当前上下文租户与目标租户一致，否则 `PermException`）。
- `DatabaseManager.session(name)` / `orm_session(name)` 按名代理到具体数据源（`app.db.instances` 多源场景）。

## 4. Outbox 可靠投递时序

**参与者**：业务代码 → `OutboxStoreInterface.append` → `OutboxPublisher.publish_pending` → `MessagePublisherInterface.publish` → `OutboxCleaner.cleanup`。

```ascii
业务事务（本地数据库事务内）
  ├─ 写业务数据（订单等）
  └─ store.append(OutboxRecord)          # 同一事务提交：业务数据 + 消息同生共死
       │
       ▼
定时任务（register_outbox_tasks 注册，默认不启用；多实例配分布式锁防重复）
OutboxPublisher.publish_pending()        # 每 publish_interval_seconds（默认 5s）轮询
  ├─ store.next_pending(batch_size=100)  # 按创建时间升序取待发送
  ├─ 逐条构造 Message(msg_id, topic, tag, body=payload)
  ├─ publisher.publish(message)          # 依赖 Broker 确认（confirm/ack），未确认视为失败
  │   ├─ 成功 → store.mark_sent(msg_id)  # 状态 → SENT
  │   └─ 失败 → _handle_failure(record, exc)
  │        ├─ retry_count+1 < max_retry → mark_failed(retry_delay_seconds=base*2^retry_count)
  │        │     # 指数退避（首次失败 retry_count=0 → base 秒），next_retry_at 调度下次轮询
  │        └─ 重试超限 → mark_failed(收敛) → _send_to_dlq(死信主题 web-dlq-topic，
  │              包裹 original_msg_id/original_topic/biz_id/retry_count/error/payload)
  │              → mark_dlq(msg_id)      # 状态 → DLQ（死信投递失败不阻塞状态流转）
  │
  ▼
OutboxCleaner.cleanup()                  # 每 cleanup_interval_seconds（默认 1h）
  └─ store.cleanup_sent(before=now - retain_days(默认7天))   # 清理已发送超保留期记录
```

状态机：`OutboxStatus.PENDING(0) → SENT(1)`；失败重试中保持待发送语义（`mark_failed` 递增重试次数并调度），重试超限 → `FAILED(2)` / `DLQ(3)`。

**关键点**：

- **不丢消息**：消息与业务数据同本地事务写入（Outbox 本地事务表），投递是"事后轮询"，业务事务提交即不丢（见 [04-设计决策.md](./04-设计决策.md) 决策 14）。
- 失败治理：指数退避（S9-4）+ 重试超限进死信主题（P0-3/S9-7）；`MqConfig.max_retry / retry_backoff_seconds / dead_letter_topic` 生效。
- 消费侧幂等：`IdempotentConsumer`（bizId + msgId 联合幂等键，保留 7 天，`try_consume`/`release`）；`RetryableConsumer` 区分可重试/不可重试异常。
- 清理仅针对 `SENT` 且超过保留期的记录（`created_at` 判断），`FAILED`/`DLQ` 需人工介入。

## 5. 支付回调时序

**参与者**：渠道（微信）→ 回调入口 → `PaymentChannelTemplate.handle_callback`（final）→ `_parse_callback`（渠道层验签解密）→ `_verify_and_check`（业务校验）→ `_persist_flow`（流水落库）→ `PaymentCallbackDispatcher.dispatch`（业务处理器）。

```ascii
微信服务器 ──POST 回调(headers + body)──▶ 回调入口
  │
  ▼
PaymentChannelTemplate.handle_callback()        # final 骨架，不可覆写
  ├─ _parse_callback(headers, body)             # 渠道层（WeChatCallbackVerifier.parse）
  │    ├─ 签名头齐全检查（wechatpay-timestamp/nonce/signature/serial）
  │    ├─ 时间戳容差校验（CALLBACK_SIGN_EXPIRE_SECONDS 内，防重放）
  │    ├─ 平台证书验签（未知序列号 + cert_auto_download → 自动下载平台证书再验）
  │    │      └─ 验签失败返回 None
  │    ├─ AES-256-GCM 解密 resource 明文
  │    └─ 映射统一 PaymentCallback（金额分→元，区分支付/退款事件）
  │         └─ None → 抛 E3-PAY-001（回调入口回 401，渠道自动重试）
  ├─ _verify_and_check(callback)                # 通用层业务校验（§4.3）
  │    ├─ 本地订单存在性（order_store，缺失 → E4-PAY-*）
  │    ├─ 金额强校验：回调金额 == 本地订单金额（不符 → E4-PAY-002）
  │    ├─ attach 关联校验（本地未设 attach 不强制）
  │    └─ 状态机幂等流转：PaymentStateMachine.target(当前状态, 事件) → update_status
  ├─ _persist_flow(PaymentFlowContext)          # 流水落库（§5.2 本地事务表）
  │    └─ 三态收敛 → PaymentFlowRecord（幂等：唯一索引兜底）
  └─ 审计埋点（audit_store 注入时）：成功/失败均留痕，raw 仅落审计
  │
  ▼
PaymentCallbackDispatcher.dispatch(callback)    # 分发业务处理器
  └─ 顺序调用全部已注册 PaymentCallbackHandler.handle(callback)
       ├─ 业务处理器实现入账/发货等（回调幂等由业务保证）
       └─ 无处理器时静默兜底（日志告警，回调入口不抛错）
```

**关键点**：

- 职责分离：**渠道层**负责验签解密（`_parse_callback`）与时间戳容差（防重放）；**通用层**负责金额/attach/状态机业务校验（`_verify_and_check`）；**分发层**只做顺序分发。
- 验签失败回 401（渠道自动重试），业务校验失败（金额不符/状态冲突）回 4xx/5xx（`E4-PAY-*`）。
- 回调幂等双保险：状态机幂等流转（`E4-PAY-003` 冲突拦截）+ 流水唯一索引兜底；业务处理器的回调幂等由业务保证。
- 支付与退款回调统一入口：`event_type` 映射 `PaymentFlowEvent.PAY / REFUND`（`TRANSACTION.SUCCESS`/`PAY.SUCCESS` → PAY，`REFUND.SUCCESS` → REFUND）。

## 6. 微信支付下单时序

**参与者**：业务 → `PaymentGatewayRegistry` 渠道（`WeChatPayProvider`）→ `PaymentChannelTemplate.prepay`（final）→ `_do_prepay`（渠道特有）→ `WeChatPayClient.request`（APIv3 签名 + HTTP）→ 二次签名调起参数。

```ascii
业务调用 gateway.prepay(PaymentPrepayRequest)
  ▼
PaymentChannelTemplate.prepay()（final 骨架）
  ├─ _check_idempotency(out_trade_no)           # §4.2 本地幂等：SUCCESS/USERPAYING/EXCEPTION 拒绝下单
  ├─ _do_prepay(request)                        # 渠道特有（WeChatPayProvider）
  │    ├─ 场景映射 SCENE_PATH：JSAPI/NATIVE/H5/APP → /v3/pay/transactions/<scene>
  │    ├─ 入参校验：JSAPI 缺 openid、H5 缺 client_ip → E4-PAY-*（E4 场景码）
  │    ├─ 组装 payload：appid/mchid/description/out_trade_no/notify_url/
  │    │                 amount.total(元→分)/time_expire/attach/payer(openid)/scene_info
  │    └─ client.request("POST", path, payload, retryable=False)   # 下单禁盲目重试（§7.2 红线）
  │         │
  │         ├─ WeChatSigner.request_signature(method, path, body, 商户私钥)
  │         │     # 签名串：method\nurl\ntimestamp\nnonce\nbody\n
  │         ├─ Authorization 头：WECHATPAY2-SHA256-RSA2048 mchid=..,nonce_str=..,signature=..
  │         ├─ httpx 调用 api.mch.weixin.qq.com（超时 read_timeout/connect_timeout）
  │         ├─ 应答验签（Wechatpay-Serial 查平台证书，未知序列号+自动下载 → 下载后重验）
  │         └─ 错误分类：网络/5xx/429 → E3-PAY-000(retryable=True，但下单 retryable=False 不重试)
  │              4xx 业务错误 → E3-PAY-000(retryable=False)；404 not_found_ok 语义
  │
  ├─ 成功：record_prepay(channel, True) + 审计
  ├─ order_store 注入时写本地支付订单 PaymentLocalOrder(status=NOTPAY, attach, expire_at)
  └─ 返回 PaymentPrepayResponse
       ├─ NATIVE → code_url（扫码）
       ├─ H5 → h5_url
       ├─ APP → prepay_id + pay_params（_app_pay_params 二次签名）
       └─ JSAPI → prepay_id + pay_params（_jsapi_pay_params 二次签名）
             └─ 签名串 appId\nts\nnonce\npackage(prepay_id=xxx)\nRSA → paySign
```

**关键点**：

- **下单不盲目重试**（规范 §7.2 红线）：`WeChatPayClient.request(..., retryable=False)`——下单为资金操作，防重复下单/重复扣款；网络失败抛 `E3-PAY-000` 由业务**先查单确认**再决策。
- 幂等接口（查单/关单/退款，`out_trade_no`/`out_refund_no` 天然幂等）允许自动重试（默认 `retries=2`，指数退避 + 抖动防重试风暴，`WechatPayConfig.retries=0` 关闭）。
- 金额全程 `Decimal` 元，出网转分（`_to_fen`：×100 整数化），避免浮点精度。
- 二次签名调起参数：JSAPI `signType: RSA`（签名串含 `package=prepay_id=...`），APP `package: "Sign=WXPay"`（签名串含 `prepayid=...`）——与下单时的 APIv3 请求签名是两套签名体系。
- 商户私钥 PEM 按 mtime 进程内缓存（P1 优化），密钥轮换后自动重读。

## 7. ModelGateway 调用时序

**参与者**：业务 → `ModelGateway.chat` → `ModelRouter.route` → `ModelAccessPolicy` → `QuotaManager` → `ContentGuardInterface` → `AICache` → 候选模型（主/备）→ `ConcurrencyGuard` → `ModelProviderInterface` → `UsageAccounting`。

```ascii
gateway.chat(request, scene, tenant_id, user_id)
  │
  ├─ ① 路由：ModelRouter.route(scene) → RouteEntry(primary, backups)
  ├─ ② 权限（AI-8）：_check_access(primary, ...) → ModelAccessPolicy.require_access
  │     无权限抛 E2-PERM-*（默认 AllowAllModelAccessPolicy 放行）
  ├─ ③ 配额（AI-2）：_check_quota(tenant, user, scene)
  │     QuotaManager.check_and_consume（tenant 必查[no-tenant 占位]，user/scene 有值才查）
  │     超限 → E1-RATE-000（调用/Token）或 E4-AI-005（成本预算耗尽）
  ├─ ④ 输入审核（AI 规范 §7.2）：_check_input → ContentGuard.check_input（BLOCK → E4-AI-002）
  ├─ ⑤ 缓存（AI-4）：_try_cache_hit（仅非流式；命中 → cache_hit 埋点直接返回；
  │     未命中 → cache_miss 埋点）——缓存内容写入前已通过输出审核，命中不重复审核
  ├─ ⑥ 候选模型循环：for model_name in [primary] + backups
  │     ├─ 备用模型切换时同样 _check_access（AI-8）
  │     ├─ _attach_pool_clients（连接池注入供应商，asyncio.Lock 防重复注入）
  │     └─ for attempt in range(max_retries + 1)     # 默认 max_retries=2
  │          ├─ async with _get_guard(model_name):   # ConcurrencyGuard 并发上限（默认 8）
  │          │     response = await provider.chat(effective_request)
  │          ├─ 异常分类：
  │          │   ├─ 内容审核拒绝 → 直接抛（不重试不降级）
  │          │   ├─ retryable（E3-THIRD-* 标记）且未达上限 → asyncio.sleep(base*2^attempt) 重试
  │          │   └─ 否则 break → 降级下一候选
  │          ├─ ⑦ 输出审核：_check_output（BLOCK → E4-AI-002）
  │          ├─ ⑧ 指标/计费：_record_success → record_ai_call/duration/tokens
  │          │     + _record_cost（透传 provider/tenant_id/scene 聚合维度）
  │          ├─ ⑨ Token 配额累计（AI-2）：_consume_usage（按实际用量，不重复计调用次数）
  │          └─ ⑩ 缓存写入（AI-4）：仅主模型成功响应落缓存（降级响应不落缓存）
  └─ 主备全部失败 → 抛 E3-THIRD-001（第三方不可用）
```

**关键点**：

- 流式 `stream_chat`：TTFT 计时（`record_ai_ttft` 首个分片产出时记录）；**未产出前**允许重试与降级，**已产出后**异常走统一流内错误分片终止（`finish_reason=ERROR`，AI-5），不再整体重试。
- 幂等键兜底（AI 规范 §4.2）：请求未携带时 `_ensure_idempotency_key` 生成一次，重试复用同一键。
- 并发守卫按模型懒创建（双重检查锁定，M2 修复防超卖）；连接池客户端注入加锁防竞态（H2 修复）。
- 计费与配额分离：`UsageAccounting` 记成本（网关不持有单价时成本为 0，由业务按模型配置核算），`QuotaManager` 只做窗口计数。

## 8. RAG 检索时序

**参与者**：`MarkdownChunker` → `EmbeddingProviderInterface` → `VectorStoreInterface` → `Retriever` → `RerankerInterface`。

```ascii
① 切片（入库阶段）
   document → MarkdownChunker.chunk() → 有序切片列表（携带标题上下文，原子块不拆分）
     ▼
② 向量化（入库阶段）
   embedding_provider.embed(text) → query_vector（默认 HashEmbeddingProvider 稳定哈希 256 维，
     生产注入 bge-m3/OpenAI 等真实嵌入模型）
     ▼
③ 入库（写入阶段）
   vector_store.add(tenant_id, ids, vectors)     # 仅写入指定租户命名空间
     ▼
④ 检索（查询阶段）
Retriever.search(query, top_k)
  ├─ tenant_id = RequestContext.get_tenant_id()   # 从请求上下文读租户（无租户由实现回落 no-tenant 占位）
  ├─ query_vector = embedding_provider.embed(query)
  ├─ hits = vector_store.search(tenant_id, query_vector, top_k)   # 向量召回（余弦相似度，得分越大越相似）
  ├─ ⑤ 邻居扩展（neighbor_window > 0 时）：
  │     _expand_neighbors：vector_store.ids_in_order(tenant_id) 取写入顺序，
  │     命中块前后各扩展 neighbor_window 个相邻块（去重保序）
  ├─ ⑥ 文本化 + 重排：documents = document_texts.get(vid, vid)
  │     scores = reranker.rerank(query, documents)   # 默认 IdentityReranker 不重排
  ├─ ⑦ 阈值过滤：score < min_score（默认 0.75，AI-6 建议余弦 ≥0.75）的命中剔除
  │     全部低于阈值 → warning「低相关降级为纯生成」并返回空列表（不阻断主流程）
  ├─ ⑧ 按重排得分降序，截断 top_k → list[RetrievalResult]
  └─ ⑨ 异常降级：任意异常 → warning + 返回空列表（检索失败不阻断主流程）
```

**关键点**：

- **降级为默认行为**：检索失败/低相关均返回空列表（主流程退化为纯生成），绝不抛错阻断。
- 租户隔离（多租户规范 §2）：`Retriever` 从请求上下文取租户传给向量存储，禁止跨租户命中；tenant_id 可选（无租户由实现回落 `no-tenant` 占位）。
- 邻居扩展依赖向量存储的写入顺序（`ids_in_order`）；ES 生产实现不保证写入顺序，`ElasticsearchVectorStore.ids_in_order` 按 `_id` 升序返回，业务可用时间序雪花 ID 编码保证顺序。
- 生产向量库经 `VectorStoreInterface` 接入（`InMemoryVectorStore` 单实例 / `ElasticsearchVectorStore` dense_vector + kNN，es extra，不改动 `retriever.py`）。

## 9. 熔断器状态机

**参与者**：`CircuitBreaker`（`infra/resilience/circuit_breaker.py`）+ `CircuitBreakerConfig` + `CircuitBreakerState`。

状态机：`CLOSED → OPEN → HALF_OPEN → CLOSED/OPEN`（双维度：错误率 + 慢调用比例）。

```ascii
                          ┌────────────────────────────────────────────┐
                          │                                            │
  样本不足/达标             ▼                                            │
┌────────────┐   错误率≥50% 或 慢调用比例≥80%（样本≥minimum_number_of_calls=10）
│   CLOSED   │────────────────────────────────────▶     OPEN
│ 正常放行    │                                            │
└─────┬──────┘◀───────────────────────────────────────────┘
      │              time.monotonic() ≥ _open_until
      │              （wait_duration_in_open_state=30s 后首次请求触发）
      │                      can_execute()
      │                      ┌───────────────────────────────┐
      │                      ▼                               │
      │              HALF_OPEN（半开试探）                      │
      │              ├─ 限流：permitted_calls_in_half_open_state=5
      │              │     并发占满 → 其余拒绝
      │              └─ _record(success=True)  → 复位 CLOSED + 清空统计窗口
      │                     _record(success=False) → 重新 OPEN（重置 _open_until）
      │                     统计窗口（deque maxlen=window_size=20）
      │
      └── 每次调用 _record(成功?, 慢?)：
            - CLOSED 且样本 ≥10：failure_rate 或 slow_rate 达阈值 → OPEN
            - OPEN 期间不统计（_record 直接返回）
```

**关键点**：

- **双维度判定**：`failure_rate_threshold=0.5`（错误率 50%）或 `slow_call_rate_threshold=0.8`（慢调用比例 80%，响应 > `slow_call_duration_threshold=1.0s` 记为慢调用）任一达标即熔断；窗口容量 20（`deque(maxlen)` 滑动窗口）。
- **最小样本保护**：`minimum_number_of_calls=10`，样本不足不评估（避免抖动误熔断）。
- **半开恢复**：`can_execute()` 在 OPEN 且等待期满后进入 HALF_OPEN；半开限流 `permitted_calls_in_half_open_state=5` 并发试探（`_half_open_inflight` 计数回收）；探测成功 → 清空窗口复位 CLOSED，失败 → 重新 OPEN。
- **降级**：配置 `fallback` 后，熔断开启或调用异常时返回兜底结果；未配置保持抛 `CircuitOpenError` / 原始异常。异步执行 `execute_async`（同步/异步 fallback 均可），同步 `execute` 仅同步 fallback。
- **边界处理**：`asyncio.CancelledError` / `BaseException` 也记录结果并回收半开许可（防 `_half_open_inflight` 泄漏）；临界区为纯内存操作用 `threading.Lock`（S16-2 豁免）。
- 熔断按资源/服务维度隔离：`FeignClient` 按 `service_name` 懒创建熔断器（M1 修复防计数分裂），未传 fallback 时默认 `default_service_fallback`（HTTP 503 + `E5-SYS-002`）。

## 10. 优雅停机时序

**参与者**：部署层（K8s preStop / 注册中心下线）→ FastAPI lifespan → `Application._shutdown` → 扩展点 shutdown 钩子 → 框架组件 close/stop。

```ascii
部署层触发停机（SIGTERM / preStop / 注册中心下线）
  │
  ├─ ① 摘流量：由部署层完成（K8s preStop / 注册中心下线），新流量不再进入
  │    /health/ready 随组件关闭自然返回 DOWN（health 模块无独立就绪开关，框架不做额外状态翻转）
  │
  ▼
FastAPI lifespan 停机序（uvicorn 触发）
  ├─ _stop_capacity_sampler()              # 容量采样任务停止（幂等，未启用跳过）
  ├─ _run_extension_shutdowns()            # 扩展点 shutdown 钩子：逆拓扑序（后启先停）
  │                                         # 先于框架组件 close（插件先用完再关底层）
  └─ _shutdown()
       ├─ ② 等待窗口：await asyncio.sleep(app.graceful_shutdown_wait_seconds)
       │     默认 0（保持旧行为与测试兼容）；生产建议 ≥10s——存量请求在窗口内继续排空
       └─ ③ 连接排空与资源释放：for component in components.values()
             method = getattr(component, "close", None) or getattr(component, "stop", None)
             （同步/异步皆可，isawaitable 自动 await）
             ├─ db（MySQLDatabase.close → 连接池 dispose / DatabaseManager.close 逐源关闭）
             ├─ mongo / cache(Redis) / mq / storage / registry / ai（ModelGateway.close → 连接池）
             └─ 按装配顺序依次释放
```

**关键点**：

- **顺序约定**：摘流量（部署层）→ 等待窗口（排空存量请求）→ 扩展点 shutdown（逆拓扑序）→ 框架组件 close（`close` 优先、`stop` 兜底）。
- 等待窗口配置 `app.graceful_shutdown_wait_seconds` 默认 0（详见 [04-设计决策.md](./04-设计决策.md) 决策 12）。
- 组件关闭幂等性由各组件实现保证（如容量采样器 `stop` 幂等）。
- 停机期间的异常由组件自身处理，不阻塞后续组件关闭。
