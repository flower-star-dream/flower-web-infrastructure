## 1. 配置驱动装配（Spring Boot 风格）

**决定人**：花海 ｜ **日期**：2026-08-14 ｜ **影响范围**：`core/application.py`、`infra/config`、全部能力装配

**背景**：框架需要服务大量业务项目（单体/微服务），若每个组件都在代码里显式初始化，业务项目需写大量样板代码，且默认值散落在各处难以统一治理。

**方案**：参考 Spring Boot 自动装配——`Application.build()` 按固定顺序装配，全部组件的「选型（type）与参数」由配置声明：

- 默认值统一收敛于包内 `application.default.yml`，业务用 `application.yml` 覆盖，环境变量（`APP_*`）最高优先；`application.py` 禁止内嵌默认值；
- 组件按 `app.<x>.type` 经注册表按名装配；中间件按 `app.web.middlewares` 声明式引入（`enabled: false` 关闭）；
- 特殊能力（多租户/AI/Mongo/搜索引擎/容量评估）默认关闭，由配置显式开启。

**取舍**：换来「开箱即用 + 默认值单一权威来源 + 能力可裁剪」，代价是装配过程依赖配置文件、排错需要查配置；配置错误在启动期快速失败（`ConfigError`）而非运行期暴露。

**后果**：业务项目只需一份 `application.yml` 即可启动完整应用；配置体系的默认值、占位符、`.env` 注入等机制随之成型（见 [01-系统架构.md §2](./01-系统架构.md#2-配置体系架构)）。

## 2. SPI + 注册表模式统一所有能力

**决定人**：花海 ｜ **日期**：2026-08-14 ｜ **影响范围**：全部能力域的 `<职责>_interface.py` 与 `*Registry`

**背景**：数据库/缓存/MQ/存储/注册中心等组件在单体与微服务两种形态下实现完全不同，且业务有替换为自研实现的需求；若用 if-else 硬编码分支扩展，代码将散落且无法裁剪。

**方案**：每个可替换点定义扩展接口（SPI，`Protocol` 或 `ABC`），配套类级注册表，遵循「接口 + 默认实现 + 生产实现 + 按 type 装配快速失败」四要素：

- 每个扩展点必须有默认实现（内存/本地，开箱即用），核心功能不因扩展缺失而失效；
- 注册表 `register(name, factory)` 模块导入即注册（幂等），`Application._build_*` 经 `_resolve_registry` 按 type 按名装配；
- **未注册的 type 装配期 `ConfigError` 快速失败**，避免拼写错误/未注册类型静默回落默认实现（防止"我以为在用 Redis 实际在跑内存"）。

**取舍**：统一模式带来学习成本低、替换路径清晰；代价是每个能力多一层注册表间接层，且需要维护接口/实现/注册表的文档契约（[SPI-Extensions.md](../SPI-Extensions.md)）。

**后果**：技术栈不锁定——内置内存实现保证单机/测试可用，Redis/MySQL/RocketMQ/MinIO/Nacos/ES 作为生产实现经 extras 接入，业务自定义实现经 `register` 接入无需改框架代码。

## 3. 能力依赖链显式化（user → authn → authz → pay）

**决定人**：花海 ｜ **日期**：2026-08-17 ｜ **影响范围**：`core/capability/`（CapabilityRegistry）、`app.capabilities.enabled` 配置、`app.extensions` 扩展注册器

**背景**：支付的前置是鉴权、鉴权的前置是认证、认证的前置是用户系统——否则这些能力没有意义。此前这些依赖隐含在文档与人的约定里，配置遗漏前置时运行期才报错，且无法表达"启用支付自动带出鉴权→认证→用户"的包含关系。

**方案**：新增能力注册表（`Capability` 契约 + `CapabilityRegistry`）：

- 能力契约声明 `name/description/modules/requires/contract`；依赖包含规则由框架维护，**缺前置不视为失败**——按包含关系自动补足（`validate` 返回闭包 `closure` 与拓扑序 `chain`）；
- `resolve`（拓扑解析）/ `validate`（装配校验，未知/循环快速失败）/ `enable`（拓扑序自动导入框架模块）三语义分离；
- `create_app` 装配钩子校验 `app.capabilities.enabled`，失败即 `ConfigError`；业务可注册自定义能力（如订单依赖支付）；
- 同一套「契约 + 依赖展开 + 生命周期编排」机制复用于统一扩展注册器（`ExtensionRegistry`，2026-08-18）。

**取舍**：换来依赖关系显式可校验、能力启用自动化；代价是引入「能力」这一抽象层，业务需理解契约与实现分离（框架只校验契约，用户系统等业务实现由业务层提供）。

**后果**：`app.capabilities.enabled: [pay]` 一条配置即可声明完整业务能力链；未知能力/循环依赖在启动期即被拦截。

## 4. 三层结构重构（v1.0.0 破坏性整改）

**决定人**：花海 ｜ **日期**：2026-08-18 ｜ **影响范围**：整个 `web_infra` 包路径（子包迁移），顶层导出保持不变

**背景**：早期 `web_infra` 包为扁平结构（`web_infra.payment`、`web_infra.db`、`web_infra.result` 等平铺），职责边界不清晰：技术底座（result/error/context/logging）与业务能力（payment/ai）混在一起，新增能力时难以判断归属，也不利于按需裁剪与依赖治理。

**方案**：按职责分三层重组（v1.0.0 破坏性整改）：

- `web_infra.core`：内核（`Application/create_app` 应用编排 + `Capability`/`Extension` 扩展点契约）；
- `web_infra.infra`：技术底座（`result/error/constants/context/logging/resilience/monitoring/web/config` 本地配置），被所有能力共用；
- `web_infra.capabilities`：能力层（`ai/cache/db/mq/storage/registry/security/payment/search/state_machine/task/schedule/http/loadbalance/config` Nacos 接入）。
- **顶层导出不变**：`from web_infra import Result, create_app` 等照常使用；子包路径迁移（如 `web_infra.payment` → `web_infra.capabilities.payment`、`web_infra.application` → `web_infra.core.application`），升级需同步更新业务代码中的子包导入。

**取舍**：换来清晰的三层依赖方向（core 组织、infra 被共用、capabilities 独立可裁剪）与长期可维护性；代价是 v1.0.0 为破坏性变更（业务需改子包导入路径），且顶层 `__init__.py` 需要维护大量兼容导出。

**后果**：后续新增能力（搜索、容量评估等）均落入 capabilities 层对应目录；文档体系同步以三层结构描述（见 [01-系统架构.md §1](./01-系统架构.md#1-三层总体结构) 与 [使用说明.md](../使用说明.md) 顶部迁移说明）。

## 5. 支付为可选能力，不随顶层导出

**决定人**：花海 ｜ **日期**：2026-08-17 ｜ **影响范围**：`web_infra/__init__.py` 顶层导出、`capabilities/payment/`

**背景**：支付是资金敏感能力，并非所有系统都需要（如纯内部工具系统）；若随顶层导出，`import web_infra` 会无条件加载支付模块并注册支付错误码，为不需要支付的系统带来无谓开销与安全面。

**方案**：支付不随 `web_infra` 顶层导出：

- `import web_infra` 不加载支付模块、不注册支付错误码；
- 需要支付的系统显式 `from web_infra.capabilities.payment import ...` 主动引入（零负担默认）；
- 配套 extras 能力声明（`[pay]` 为空 extra，仅作能力声明），依赖包含规则由 `CapabilityRegistry` 维护（启用支付自动带出 鉴权→认证→用户）。

**取舍**：换来默认零负担、安全面收敛；代价是需要支付的系统多一步显式引入（文档与示例均给出）。

**后果**：支付成为「显式引入 + 能力声明」双保险的可选能力；容量评估（`app.capacity`）随后沿用同一模式（不随顶层导出，yml 开关装配，2026-08-18）。

## 6. 微信支付自研 APIv3 客户端

**决定人**：花海 ｜ **日期**：2026-08-16 ｜ **影响范围**：`capabilities/payment/provider/wechat/`

**背景**：微信支付官方无 Python SDK（官方 SDK 以 Java/PHP/Go 等为主），接入微信支付 APIv3 需要自行实现请求签名、应答验签、回调解密、平台证书管理；同时框架要求零新依赖。

**方案**：自研 APIv3 客户端（`WeChatPayClient`），基于框架既有依赖 `httpx` + `cryptography`（零新依赖）：

- 请求签名（`WeChatSigner`：RSA-SHA256 签名串 + Authorization 头）、应答验签、错误码映射（网络/5xx/429 → `E3-PAY-000` 可重试标记，4xx 业务错误不重试）；
- 幂等接口（查单/关单/退款）自动重试（指数退避 + 抖动防重试风暴，默认 `retries=2` 可关）；**下单禁盲目重试**（`retryable=False`，资金操作红线，失败先查单确认）；
- 回调验签解密（`WeChatCallbackVerifier`：`platform_cert` / `public_key` 两种验签模式 + AES-256-GCM 报文解密 + 时间戳容差防重放）；
- 平台证书自动下载**默认关闭**（`cert_auto_download: false`），开启后验签遇未知序列号自动调 `/v3/certificates` 下载并缓存（并发加锁防重复下载）；证书落盘「临时文件 + `os.replace`」原子写，商户私钥按 mtime 进程内缓存；
- 可注入 `httpx.MockTransport` 供测试。

**取舍**：自研换取「零依赖 + 完全掌控签名/重试/证书细节」；代价是需要紧跟微信 APIv3 文档维护（路径、字段变更），且签名/加密实现必须经过严格测试（配套 `PaymentChannelContract` 契约测试与 `PaymentCallbackSimulator` 回调模拟器）。

**后果**：微信渠道 `WeChatPayProvider` 覆盖 JSAPI/NATIVE/H5/APP 四场景下单、查单、关单、退款、查退款、回调解析；后续新渠道（支付宝等）按同一骨架（`PaymentChannelTemplate`）接入。

## 7. 惰性导入与最小安装原则

**决定人**：花海 ｜ **日期**：2026-08-15（依赖解耦；`_extend_all_with_installed` 动态扩展 `__all__` 具体日期待确认） ｜ **影响范围**：`web_infra/__init__.py`、extras 体系

**背景**：核心安装（`pip install flower-web-infrastructure`）不应强制携带 sqlalchemy/redis/pymongo/beanie 等重型 SDK；同时非最小安装下 `from web_infra import *` 应能导出全部能力。此前 db 相关实现直接顶层导入，最小安装会 `ImportError`。

**方案**：

- **惰性导出**：`_LAZY_DB_EXPORTS` 声明依赖可选包的实现名（`Base/MySQLConfig/MySQLDatabase/MongoDBConfig/RedisConfig/...`），模块级 `__getattr__` 首次访问时从 `web_infra.capabilities.db` 延迟导入并缓存，未安装对应依赖抛 `ImportError`；
- **`__all__` 动态扩展**：`_extend_all_with_installed()` 用 `importlib.util.find_spec`（不实际导入）探测 `_LAZY_ALL_REQUIRES` 声明的依赖包是否已安装，已安装则把惰性名追加进 `__all__`——最小安装 `import *` 不触发惰性加载，非最小安装 `import *` 全量导出；
- **extras 按需**：`[mysql]/[redis]/[mongo]/[storage]/[nacos]/[rocketmq]/[rag]/[pdf]/[es]` 等按能力安装；`[min-monolith]`/`[min-microservice]` 为开箱即用组合；`[all]` 全量。

**取舍**：换来「最小安装零重型依赖、导入零负担、能力按需裁剪」；代价是顶层导出逻辑复杂（`__getattr__` + 动态 `__all__`），且最小安装下访问未装能力时错误信息依赖 `ImportError` 提示（配合 extras 文档引导）。

**后果**：`import web_infra` 与 `create_app()` 在纯核心依赖下开箱即用；数据访问类组件需先装 extras 再显式导入（`from web_infra import MySQLConfig`）。

## 8. 边界收敛：E3/E5 出网收敛为大类码

**决定人**：花海 ｜ **日期**：2026-08-14 ｜ **影响范围**：`infra/error/handler.py`、`infra/error/error_code.py`

**背景**：服务端错误码包含子类与编号（如 `E3-THIRD-001`），若原样透传给外部调用方，会泄漏内部实现细节（具体哪个第三方/哪段链路），且调用方无法稳定消费（服务端每改一个子类，客户端就要跟着改）。

**方案**：出网边界收敛（规范 §4.6.1）：

- `E3`（基础设施类）与 `E5`（未知系统类）出网响应收敛为**大类前缀码 + 大类默认文案**（`E3` → "服务暂时不可用，请稍后重试"，`E5` → "系统繁忙，请稍后重试"）；
- `E1/E2/E4/S` 透传完整错误码（客户端/业务错误需要精确语义）；
- **服务端日志始终记录完整错误码**（收敛只作用于出网响应体，不影响排障）。

**取舍**：换来外部契约稳定、不泄漏内部细节；代价是调用方拿不到具体子类码（需要时经日志/追踪链路排查，或显式设计"需透传"的码）。

**后果**：`converge_error_code` 在全局异常处理器统一执行（`_converged_response`），业务无需感知；HTTP 状态码原样透传不收敛。

## 9. 错误码分段规则与可重试性（仅 E3 可重试）

**决定人**：花海 ｜ **日期**：2026-08-14 ｜ **影响范围**：`infra/error/error_code.py`、全部能力域错误码

**背景**：统一错误码体系需要同时承载「客户端/服务端归属、HTTP 映射、日志级别、是否可重试」多维语义；若每个错误码手写这些属性，将散乱且易错。

**方案**：错误码格式 `E<大类>-<子类>-<3位编号>`（成功码 `S0000`），按大类推导元数据：

| 大类 | 语义 | HTTP | 日志级别 | 可重试 |
| ---- | ---- | ---- | ---- | ---- |
| `E1` | 参数/请求错误 | 400 | INFO | 否 |
| `E2` | 认证/权限错误 | 401（`E2-PERM` 403） | INFO | 否 |
| `E3` | 基础设施/第三方错误 | 500（`E3-LOCK` 423） | ERROR | **是（唯一）** |
| `E4` | 业务规则错误 | 422 | WARN | 否 |
| `E5` | 未知系统错误 | 500 | ERROR | 否 |

- 子类按语义覆盖 HTTP（`E2-PERM→403`、`E3-LOCK→423`）；
- **仅 E3 可重试**（`_RETRYABLE_CATEGORIES = {"E3"}`）：重试只对基础设施类瞬时故障有意义，客户端/业务错误重试无意义，未知系统错误不可盲目重试；
- 枚举 + 注册表登记（`CommonErrorCodeEnum` 遍历注册进 `ErrorCodeRegistry`），模块导入即登记各域错误码。

**取舍**：换来「错误码语义自解释 + 重试判定统一（`is_retryable` 一处实现、全框架复用）」；代价是新增错误码必须遵循分段约定（分类错误会得到错误语义）。

**后果**：`retry` 装饰器、`CircuitBreaker`、`ModelGateway`、`WeChatPayClient` 的重试判定统一引用错误码的 `retryable` 标记，无重复实现。

## 10. 日志统一格式 + 敏感脱敏

**决定人**：花海 ｜ **日期**：2026-08-14 ｜ **影响范围**：`infra/logging/`、`Application._setup_logging`

**背景**：日志格式不统一导致集中采集解析困难；日志中可能打印手机号/身份证/卡号等敏感信息（尤其参数日志 `logger.info("phone=%s", phone)`），存在合规风险。

**方案**：

- **统一入口与格式**：`get_logger(name)` 统一前缀 `web_infra`；`configure_logging` 统一挂载格式器（`text`：`[时间][级别][TraceId][阶段][模块][类名.方法][用户ID] 消息`，或 `json`）+ `ContextFilter`（注入 trace_id/user_id）+ `SensitiveDataFilter`；输出通道可配置（`both/console/file` + `app.logging.sinks` 自定义通道 SPI）；
- **全局脱敏**：`SensitiveDataFilter` 作为 logging.Filter 全局挂载，对 `record.msg` 与 `record.args`（dict 与位置参数元组）统一执行 `mask`（正则匹配手机号/身份证/卡号等）；数值参数跳过脱敏（避免 `%.3f` 格式化崩溃与长数字串误判）；脱敏失败不阻断日志输出。

**取舍**：换来「采集格式统一 + 敏感信息默认不落盘」；代价是日志链路多一层 Filter 开销（可忽略），且脱敏正则需随新敏感类型维护（`masking.py`）。

**后果**：业务日志开箱即脱敏，`app.logging.output/format/file/retention_days/sinks` 全部可配置；自定义日志通道经 `LogSinkInterface` SPI 接入（[SPI-Extensions.md §16](../SPI-Extensions.md#16-日志模块logging)）。

## 11. 内存实现仅限单实例/测试（@Stateful 标注）

**决定人**：花海 ｜ **日期**：2026-08（S1-1 约束贯穿） ｜ **影响范围**：全部内存实现类（cache/mq/storage/registry/security/ai/outbox 等）

**背景**：框架大量提供内存实现（`MemoryCacheBackend`、`InMemoryMessageQueue`、`InMemoryServiceRegistry`、`InMemoryJwtTokenStore`、`InMemoryVectorStore` 等）保证单机/测试开箱即用；但内存状态是**进程内**的，多实例部署时若误用会造成状态不一致（如验证码、幂等键、JWT 凭证各实例各自独立）。

**方案**：

- 每个内存实现类文档标注 `@Stateful`（进程内内存存储，单实例/单进程部署，多实例需替换为分布式实现），如 `InMemoryIdempotencyStore`、`InMemoryQuotaStore`、`InMemorySearchEngine` 等 15+ 处；
- 配套生产实现：Redis（缓存/幂等/验证码/JWT Token/消息幂等）、MySQL（Outbox/任务记录）、RocketMQ、MinIO、Nacos、ES 等；
- [SPI-Extensions.md §17.6](../SPI-Extensions.md#176-常见替换对照) 给出「单实例 → 多实例」替换对照表。

**取舍**：换来「单机零依赖可用 + 文档明示边界」；代价是内存实现不能直接用于多实例（需要按替换对照表切换生产实现），误用风险靠标注与文档约束。

**后果**：装配默认值（`app.cache.type: memory` 等）在单实例/开发环境直接可用，生产环境由业务按对照表切换到分布式实现。

## 12. 优雅停机等待窗口（默认 0）

**决定人**：花海 ｜ **日期**：2026-08 ｜ **影响范围**：`Application._shutdown`、`app.graceful_shutdown_wait_seconds`

**背景**：停机时若立即关闭连接池/释放资源，正在处理的存量请求可能中断（连接被回收、任务半途而废）；但等待窗口过长会拖慢发布节奏。

**方案**：

- 停机流程：摘流量（部署层 preStop/注册中心下线）→ 等待窗口 `app.graceful_shutdown_wait_seconds` → 扩展点 shutdown 钩子（逆拓扑序）→ 组件 close/stop；
- **默认 `0`**（保持旧行为与测试兼容，存量测试不因等待变慢）；生产环境建议配置 ≥10s，让窗口内新流量不再进入、存量请求排空。

**取舍**：默认 0 换来「行为兼容、测试快速」；代价是生产环境若不配置则没有排空窗口（依赖部署层摘流量时机），需文档强调生产配置建议。

**后果**：生产部署模板（[使用说明.md](../使用说明.md) 最小微服务示例、部署文档）引导配置 `app.graceful_shutdown_wait_seconds: 10`；`/health/ready` 随组件关闭自然返回 DOWN，配合 K8s readiness 摘除。

## 13. Feign 统一 503 兜底

**决定人**：花海 ｜ **日期**：2026-08 ｜ **影响范围**：`capabilities/http/feign_client.py`、`default_service_fallback`

**背景**：微服务间调用熔断开启后，被调服务不可用时若无降级，调用方会直接抛错（`CircuitOpenError`/原始异常），每个业务都要重复实现"返回统一服务不可用"的兜底逻辑，且兜底格式不统一。

**方案**：

- `FeignClient` 未显式传 `fallback` 时采用框架默认兜底 `default_service_fallback(service_name)`：返回统一 `httpx.Response`（HTTP 503 + `code=E5-SYS-002` + "服务 {name} 暂不可用"），避免业务反复实现；
- 业务需自定义降级（如返回缓存数据）时，在构造 `FeignClient` 时传 `fallback` 参数覆盖（签名 `fallback(service_name) -> Response`，同步/异步皆可）。

**取舍**：换来「默认降级一致 + 自定义降级可覆盖」；代价是默认兜底语义固定为 503 服务不可用（业务需在语义不匹配时显式覆盖）。

**后果**：服务间调用链在目标服务熔断/不可用时返回统一 503 响应，调用方按统一结构消费；降级策略细节与归一化约定见 [订单兜底策略.md](../订单兜底策略.md)。

## 14. Outbox 本地事务表

**决定人**：花海 ｜ **日期**：2026-08-14 ｜ **影响范围**：`capabilities/mq/outbox/`、`OutboxStoreInterface`

**背景**：业务写库后直接发 MQ 存在经典一致性问题——「先发消息后提交事务」消息可能发到不存在的订单；「先提交后发消息」消息可能丢失（进程崩溃）。双写无法保证原子性。

**方案**：Outbox 本地事务表模式（规范 §21.3）：

- 业务数据与 `OutboxRecord`（待发送消息）在**同一个本地数据库事务**内写入（`append`），同生共死——事务提交即不丢消息；
- 后台任务轮询 `next_pending`（按创建时间升序，`batch_size=100`）投递到 MQ；投递成功 `mark_sent`，失败按指数退避调度重试（`base*2^retry_count`），重试超限投递死信主题并置 `DLQ` 状态；
- 已发送记录保留 7 天后由 `OutboxCleaner` 清理（`cleanup_sent`）；
- 实现 SPI 化（`OutboxStoreInterface`）：`InMemoryOutboxStore` 默认，`MysqlOutboxStore` 生产（DDL 见 `db/init/ddl/001-mq-init-ddl.sql`）；轮询任务经 `register_outbox_tasks` 由业务装配（多实例配分布式锁防重复执行）。

**取舍**：换来「业务数据与消息强一致（不丢消息）+ 可重试/死信治理」；代价是消息投递有延迟（轮询间隔，默认 5s）、本地事务表需建表维护、消费侧仍需幂等（`IdempotentConsumer`，bizId+msgId 联合幂等保留 7 天）。

**后果**：支付、订单等资金/关键链路可依赖 Outbox 保证「业务落库即消息不丢」；投递失败有退避重试与 DLQ 兜底，人工可介入。
